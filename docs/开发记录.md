# Workloom 开发记录（问题 · 偏差 · 决策 · 遗留）

> 用途：实施过程中出现的问题点、与冻结方案的偏差、spec 阶段拍板决定、留给后续里程碑的事项，统一记在这里。
> 任务系统（http://localhost:3422）与 git 历史是流水账，本文档是长期索引 —— 任务很长，结论不能只留在会话里。
>
> 维护方式：每完成一个里程碑步骤，把该步骤的结论追加到对应小节。条目格式：
> `[类别] 背景/现象 → 处理或决定 → 位置/引用`。类别：`[问题]`（缺陷、坑、环境限制）、
> `[偏差]`（与方案或实施计划不一致且被接受）、`[决策]`（契约与拍板）、`[遗留]`（后续里程碑接手）。
>
> 事实来源顺序：方案与实施计划（`docs/原始文档/`，冻结）> 本文档 > 任务 artifacts。

## M0.1 语言与工程骨架（提交 758c688、5777008）

- [决策] 实现语言 Go 1.26（实施计划决策门 D1）：单文件分发、标准库自带文件锁与子进程管理、三平台交叉编译。
- [决策] 行尾统一 LF，状态文件由仓库根 `.gitattributes` 固定（提交 5777008），避免跨机器合出幽灵 diff。
- [问题] Windows 上 `core.autocrlf` 默认值会污染状态文件行尾；`.gitattributes` 已兜底，手工把 `.devsys/` 拷到别的仓库时仍要留意。

## M0.2 CLI 骨架与 `devsys init`（提交 1a8581f）

- [偏差] 方案 §14.3 目录树未列 `.devsys/.gitignore`，但 §14.2 要求 `local/`、`.cache/` 不提交 → init 生成 `.devsys/.gitignore`。
- [偏差] 实施计划 M0.2 产出清单漏写 `workflows/`（§14.3 有；§7 工作流存 `.devsys/workflows/<id>.md`）→ 以 §14.3 为准，init 创建全部 14 个目录。
- [决策] 忽略规则放在 `.devsys/.gitignore` 而非仓库根：随项目走，换设备后仍生效。
- [决策] 退出码契约 0 成功 / 1 内部 / 2 用法 / 3 前置，由测试固定 → `internal/cli/cli.go`。
- [问题] 冒烟时误把临时目录当真实项目，在真实用户注册表写入一条记录；已清理，此后所有冒烟固定用 `DEVSYS_CONFIG_DIR` 隔离注册表。
- [遗留] `internal/minyaml` 是临时序列化实现 → 已由 M0.3 替换并删除。

## M0.3 文本存储基元（提交 2d5db1b）

- [决策] 采用 vendored `gopkg.in/yaml.v3` v3.0.1：本机直连 `proxy.golang.org` 实测超时，vendor 后 `GOPROXY=off` 也能构建；同步删除 `internal/minyaml`。
- [问题] Windows 标准库 `syscall` 不导出 `LockFileEx` → 用 `syscall.NewLazyDLL("kernel32.dll")` 动态调用，不引入锁库 → `internal/storage/lock_windows.go`。
- [问题] Windows 字节区间锁会阻塞其他句柄读取被锁区间，超时诊断读不到持有者 → 锁区间挪到偏移 1 GiB，锁文件头部保持可读 → `internal/storage/lock.go`。
- [问题] Windows `os.Rename` 覆盖被其他句柄打开的文件会 `Access is denied`（Go 的 `os.Open` 不带 `FILE_SHARE_DELETE`）→ 原子写对目标占用做 20–100ms 退避重试 5 次；读路径坚持「读即读即关」。
- [决策] 事务协议：journal（意图 + payload 摘要）→ `commit.yaml` 原子落盘即提交点 → 逐 op 应用 → 清理；恢复按事务 id 排序、幂等重放（Put 比摘要、append 比「前置长度 + 区间摘要」）；恢复失败拒绝读写但允许只读诊断。
- [决策] JSONL 断尾：末字节非 `\n` 即不完整尾部；追加要求「精确前置长度 + 尾部完整」，不完整时阻断追加。
- [问题] 本机无 gcc，`go test -race` 不可用（`cgo: gcc not found`）；并发结论来自多进程测试（4 进程同信号 CAS、跨进程锁超时、8 并发追加不交错）。
- [遗留] 断电持久性未验证且代码与文档均不宣称；仅验收「进程中断 + 单文件原子性」。
- [遗留] macOS/Linux 仅交叉编译通过、未实跑（锁走 `syscall.Flock` 分支）。

## M0.4 严格配置解析（提交：`feat(m0.4): 严格配置解析…`，见 `git log`）

- [决策] M0.4 白名单 = M0.2 占位键集：`project.yaml` 认 `schema_version/id/name/created_at`，`config.yaml` 只认 `schema_version`；方案 §5.1 的完整 Project 模型留给 M1.1，config 业务键留给后续里程碑（扩展时同步白名单 + README + 本文档）。
- [决策] 状态文件（`state/current.yaml`、`state/milestones.yaml`）在 M0.4 只校验 `schema_version`，其余键放行，严格模型归 M1.1。
- [决策] 错误规范：`Problem{file,line,field,reason}` 渲染为 `文件:行号: 字段: 原因`；一次收齐全部问题，不做首错即停。
- [决策] 版本不可解释原则：`schema_version` 缺失或不受支持时，对该文件只报版本问题并跳过键校验，避免用未知 schema 误报。
- [决策] 新增退出码 `4 = invalid managed state`；写命令（当前只有 `init`）在任何改动前校验既有受管文件，未知版本拒绝写入并提示迁移（迁移命令属 M9.2）。
- [决策] 只读诊断面新增 `devsys config check`（普通读取：不加锁、不触发恢复），未知版本时仍可运行 —— 方案 §14.1「仅允许只读诊断」的可观察落点。
- [问题] `yaml.Node` 对第二份文档给出的行号是内容首行而不是 `---` 行 → 改取 DocumentNode 的行号，才能指向文档分隔符本身。
- [遗留] `config.yaml` 尚无业务键；M3（工作流/门禁）、M5（知识）、M6（执行）引入配置项时需同步白名单、README 与本文档。
- [遗留] 迁移命令（如 `devsys migrate`）属 M9.2；当前对未知版本只报错、不动手。

## 全局遗留与跨里程碑事项

- [遗留] `-race` 检测器在本机不可用（无 gcc）；有编译环境时补跑 `CGO_ENABLED=1 go test -race ./...`。
- [遗留] macOS/Linux 实机未验证（仅交叉编译）；M8 设备接力前至少各跑一次全量测试。
- [遗留] 审批模型（方案 §4.9/§5.8，实施计划 M3.7）与知识生成器契约（§12.6，M5.6）已在方案 v1.8 定义，但均无实现。
- [遗留] 用户级注册表只存路径与标识（§14.4）；跨设备同时领取明确不支持，设备接力前必须停写。
- [决策] 仓库内 `AGENTS.md` 长期处于 git 暂存区未提交：历次里程碑提交均按路径提交（`git commit -- <paths>`）以排除它，避免把环境文件混入产品历史。
