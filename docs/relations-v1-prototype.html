四个关键专题

最容易误解的关系机制

Artifact 的两条归属通道 可选关联

artifact register --workitem WLM-1 → 主归属 workitem_id
artifact register --related WLM-1 → 关联 related_workitems

阶段门禁对两者等价：BelongsTo(id) 主归属或关联任一命中即算证据，且门禁按 Name 匹配、不看 Type。空 id 恒不匹配——「没填归属」不会成为对所有任务成立的万能证据。语义上该用 --workitem 时，不要图省事用 --related。

「工作流」是三个东西 模板全局

  • Policy 模板（workflows/<id>.md，项目全局）：steps / gates / 质量门，正文兼作 prompt 模板
  • 实例（内嵌 WorkItem）：只存 {ID, Step, StepEnteredAt, Paused}——任务走到哪一步
  • Run.WorkflowID：冗余记录，不参与判定

绑定两条路：任务声明实例 → 用它；未声明 → 回落 config.yaml 的 default_policy。回落失效会被报配置问题，且门禁 fail closed。

Run 生命周期与快照 强绑定

claim（lease）→Run running→run complete→workitem transition

ContextSnapshot 是全图唯一「按值冻结」的一环：ProjectStateVersion / WorkItemVersion / ArtifactVersions / KnowledgeRevision / WorkspaceHead / DecisionIDs。其余关系都是实时读当前文件；只有快照能重建「启动时看到的是什么」。

调度租约：被追踪的瞬时态 强绑定 · 瞬时

  • claim 在同一事务原子写 lease + workitem + 一条 claimed 事件
  • release / 过期清理时删除；不是历史记录，只表达「现在谁持有」
  • scheduling/ 会被 git 追踪（不在排除清单）——sync status 接力前由 reconcile.LeaseAudit 审计有效性
  • fencing token：16 字节随机 hex，每次 claim 重生成、绝不复用

七条容易搞错的关系

  1. Milestone ↔ WorkItem 没有外键。只有状态汇总，别把它当任务分组标签用。
  2. Decision / Finding 没有主归属字段。结构体里根本没有 workitem_id，不填 related 就是项目级。
  3. Artifact 主归属与关联是等价证据。门禁不区分「属于」和「关系到」，但语义上该用 --workitem 时不要用 --related。
  4. require_artifacts 匹配的是 Name 不是 Type。产物类型（spec / plan / verification…）不参与门禁判定。
  5. Run.WorkflowID 不决定策略。策略来自 WorkItem 的实例或 default_policy 回落。
  6. 蓝图是项目级产物。Project.BlueprintArtifactID 指向的 Artifact 通常不挂任何任务——它是项目入口，不是某个任务的交付物。
  7. scheduling/ 的 lease 会被 git 追踪，但只是瞬时状态。跨设备接力看到残留 lease 不等于任务仍被持有——以 reconcile.LeaseAudit 的过期判定为准。
