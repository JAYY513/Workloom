# 发布流程（Release Runbook）

> 适用：`JAYY513/Workloom`（公开仓库，MIT）。产物是 6 平台二进制 + `install.sh` / `install.ps1` + `checksums.txt`，
> 另有 `dist/npm/*.tgz`（只附 GitHub Release，不 `npm publish`）。二进制由 `scripts/install.sh` / `scripts/install.ps1` 消费；npm 包见 §5b。
> 自动化落点：`.github/workflows/release.yml`（推 `v*` tag 自动触发，或手动 dispatch）。

## 0. 触发方式与成本

| 触发 | 命令 | 说明 |
|---|---|---|
| 自动 | `git push origin v0.1.1` | tag 名匹配 `v*` 即触发；里程碑 tag（`m7`/`m8`/`m9`）不会触发 |
| 手动 | `gh workflow run release.yml -f tag=v0.1.1` | 需要 tag 已存在；可加 `-f draft=true` 先出草稿、`-f notes="…"` 自定义说明 |

- 单个 `ubuntu-latest` runner（Linux ×1 倍率），一次约 2–4 分钟。公开仓库的 Actions 分钟免费；私有 fork 消耗账号免费额度（Free 2,000 分钟/月）。
- 不要改成 windows/macos runner 矩阵：Go 交叉编译不需要（`scripts/build-release.sh` 就是一个 runner 上循环 `GOOS/GOARCH`）。
- 工作流只在 tag 推送或手动触发时运行，普通 push 不消耗额度。

## 1. 发版前检查（必须）

```bash
go test ./... -count=1          # 全量绿
gofmt -l internal cmd           # 空
go vet ./internal/... ./cmd/... # 净
git status --short              # 干净；按路径提交完成
```

- **tag 指向的树要与文档一致**：`v0.1.0` 的教训是 tag 打在 README 修正之前，发布树里的 README 还写着「Release 未发布」。先把文档改完、提交，再打 tag。
- 仓库根已有 MIT `LICENSE`。发版前确认 tag 指向的树包含它，不要发没有许可证的公开 tag。

## 2. 发版（自动路径，推荐）

```bash
git tag -a v0.1.1 -m "v0.1.1" <commit>
git push origin v0.1.1
gh run watch                    # 观察本次 run
gh release view v0.1.1          # 结束后核对资产
```

**Release notes 纪律**：自动路径默认 `--generate-notes`（commit 流水）。tag 推送后、CI 跑完前，用
`gh release edit v0.1.1 --notes "$(printf '…用户视角三行…\n\n**Full Changelog**: …')" `
或下次直接手动 dispatch（`gh workflow run release.yml -f tag=vX -f notes="…"`）补上**用户视角三行**：
①新用户能感知的变化（一句话）；②破坏性/行为变更（如 CLI 参数强制、档位调整）；③升级建议
（谁该升级、怎么升）。commit 流水对维护者有用，对决定是否升级的人没用。

工作流做的事：解析版本 → checkout tag → `setup-go`（按 `go.mod`）→ `scripts/build-release.sh --version <tag> --out dist` → 校验（`workloom-linux-amd64 --version` 必须报该 tag；`checksums.txt` 必须是 GNU 文本格式 `<hash>  <file>` 且列出 dist 全部资产；`sha256sum -c checksums.txt`）→ `scripts/pack-npm.sh`（不下载、不 `npm publish`）→ `gh release create --verify-tag`（含 `dist/npm/*.tgz`）。

> **校验和格式是发布契约**：`sha256sum -c` 同时接受 `<hash>  <file>`（GNU）与 macOS `shasum` 的 `<hash> *<file>`（二进制标记），所以格式错误不会在「哈希对不对」上暴露。`v0.1.0` 就是这样发布了 shasum 格式，安装脚本的校验项预过滤匹配不到 → 判「校验项缺失」并回退源码构建。现在 `release.yml` 与 `scripts/build-release.sh` 都会在生成后按严格格式自检，失败即中止发布。

## 3. 发版（手动路径）

```bash
gh workflow run release.yml -f tag=v0.1.1 -f draft=true   # 先草稿验证
gh release edit v0.1.1 --draft=false                      # 验证 OK 后转正
gh workflow run release.yml -f tag=v0.1.1 -f notes="…"    # 或直接正式发布
```

## 4. 无 Actions 的等价手工路径

```bash
make release VERSION=v0.1.1        # = bash scripts/build-release.sh --version v0.1.1 --out dist
bash scripts/pack-npm.sh --version v0.1.1 --dist dist --out dist/npm   # 不下载、不 npm publish
gh release create v0.1.1 dist/workloom-* dist/install.sh dist/install.ps1 dist/checksums.txt dist/npm/*.tgz \
  --verify-tag --title v0.1.1 --notes "…"
```

CI 与本地走同一个构建脚本，因此两条路径的产物一致。

## 5. 校验与消费

```bash
bash scripts/install.sh --tag v0.1.1                 # Linux/macOS：下载 + sha256 校验 + 安装
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/install.ps1 -Tag v0.1.1 -AddToPath
gh release download v0.1.1 --pattern 'workloom-*'      # 公开仓库可匿名下载；私有 fork 才需要鉴权
```

- 公开仓库的资产 URL 可匿名拉取。私有 fork 的资产 URL 需要鉴权：匿名 `curl` 会 404，脚本会回退 `git clone --branch <tag> + go build`（需 Go + Git 与仓库访问权限）。
- 手工核对：`cd dist && sha256sum -c checksums.txt`；若本机 Git Bash 的 `sha256sum -c` 异常（对任何格式都报 FAILED），改用逐项比对：`sha256sum <file>` 与清单里的哈希 + 文件名集合 `diff`——等价且同时校验资产齐全。

## 5b. npm 包（不发布到 registry）

`scripts/pack-npm.sh` 在 Release 二进制打完之后，把它们装进 `@jayy513/workloom` 的平台包并 `npm pack`。
没有 postinstall 下载。工作流把 `dist/npm/*.tgz` 附到 GitHub Release，不执行 `npm publish`。
unscoped `workloom` 在 registry 上是 404，但已有无关的 workloom 站点族，不能当成可注册；
`@jayy513/workloom` 同样未占用，npm 用户确认前不要发布。

## 6. 回退

| 情况 | 处理 |
|---|---|
| tag 指错 commit | `gh release delete v0.1.1 --yes` → `git push --delete origin v0.1.1` → 修正后重打 |
| 资产缺失/损坏 | `gh release upload v0.1.1 dist/workloom-* dist/install.sh dist/install.ps1 dist/checksums.txt dist/npm/*.tgz --clobber` |
| 只改校验和格式（不重发二进制） | 下载现有资产逐个核对哈希 → 按 `<hash>  <file>` 重生成 → `gh release upload <tag> checksums.txt --clobber`（`v0.1.0` 已按此法修正：6/6 哈希一致，仅格式改为 GNU 文本） |
| 只改说明 | `gh release edit v0.1.1 --notes "…"` |
| 用户侧回退 | `scripts/install.sh --tag <上一 tag>`；项目状态回退见 `docs/迁移指南.md`（`git checkout <tag> -- .devsys/`） |

## 7. 常见故障

- **403 `Resource not accessible by integration`**：工作流内已声明 `permissions: contents: write`；若仍失败，检查 Settings → Actions → General → Workflow permissions（本仓库当前默认是 read-only，组织策略可能限制工作流提权）。
- **`tag … does not exist`**：`--verify-tag` 主动拦截；先把 tag 推到 origin。
- **release 已存在**：`gh release delete <tag> --yes` 后重跑，或 `gh release upload --clobber`。
- **版本串不符**：看 run 日志的 `Resolve the version` 输出；通常是 tag 名与 checkout 的 ref 不一致（手动 dispatch 时传错 `tag`）。
- **`Caching for 'false' is not supported`**：`actions/setup-node` 的 `cache` 只接受包管理器名（`npm`/`yarn`/`pnpm`），写 `cache: false` 会在 `Set up Node` 处直接失败、Release 不发出（v0.1.9 首发 run `35687854367` 即此）。删掉该输入即不缓存，然后重新推 tag 或手动 dispatch。
