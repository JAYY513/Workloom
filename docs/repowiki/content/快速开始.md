- Go 1.26 工具链（`go.mod` 固定 `go 1.26`）和可在 PATH 调用的 Git。
- 唯一外部 Go 依赖是 `gopkg.in/yaml.v3`，已 `go mod vendor` 并提交 `vendor/`；离线构建时设 `GOPROXY=off` 或在 PowerShell 中设 `$env:GOPROXY='off'`。

```bash
go install github.com/JAYY513/Workloom/cmd/workloom@latest
# 只有私有 fork 才需要：go env -w GOPRIVATE=github.com/JAYY513/Workloom
```

**③ 源码构建（兜底，仓库已提交 `vendor/`，可离线完成）**：

```bash
git clone https://github.com/JAYY513/Workloom.git && cd Workloom
GOPROXY=off GOFLAGS=-mod=vendor go build -o bin/workloom ./cmd/workloom   # Windows 产物加 .exe 扩展名
```

**④ npm（Windows x64 推荐，一条命令）**：`npm install -g @kaki317/workloom`（需要 Node.js ≥ 18），bin 只有 `workloom`，安装时不下载 exe——平台二进制随平台包一起装（`optionalDependencies`），升级就是重跑同一条命令。**当前只发布了 `win32-x64`**：macOS / Linux / Windows ARM64 上会缺少平台二进制、运行时被明确拒绝（不会去下载），这些平台先用 ①–③，等对应平台包发布后同一条命令即可用。`npx` 不作为主安装路径（冷启动要联网、版本随 npx 缓存漂移）。发布侧：`scripts/publish-npm.sh` 把已打包的 tgz 发到 registry（平台包先、wrapper 后；已存在同版本则跳过、可重跑；`--dry-run` 只做本地校验；不构建、不 pack、不下载），`make npm-publish` 是同一入口；包模板带 `publishConfig.access = "public"`（scoped 包缺这项首次发布会失败）。细节见 INSTALL.md §1d 与 docs/发布流程.md §5b（纯文本路径）。

装完二进制的下一步是**接入项目**（每个项目一次）：`workloom setup` 一条命令完成 `init → workflow init --template quick-fix → wire（默认含 skill）→ config check → wire --check → prime → 蓝图检查 → doctor`，幂等、失败即停、已有文件一律保留（`internal/app/setup.go`）；**`setup` 不注册 MCP**。MCP 注册是另一步：`workloom mcp install` **默认只预览（dry-run）**，`--apply` 才写，`--force` 只替换已有的 `devsys` 条目；客户端是 codex / claude / opencode，支持 user / project 两种 scope，注册条目跑 `mcp serve --profile session,executor --tier core`，无法安全合并（JSONC、Codex 行内 `mcp_servers` 表）时即使 `--force` 也拒绝并指向 `workloom wire --print-mcp <codex|claude|opencode>`（`internal/app/mcpinstall.go:21-30`、`:55-56`、`:106-109`）。

排障速查（docs/使用手册.md §7「排障速查」症状→处置表）：装完 `workloom: command not found`（兼容别名 `devsys` 同理）→ 重开终端刷新 PATH，Windows 查 `%LOCALAPPDATA%\workloom` 是否已进 User PATH；`--version` 报 `0.1.0-dev` → 旧版或源码裸构建标记（Release 安装应报 `vX.Y.Z (短哈希)`，go install 报 `vX.Y.Z`）；install.sh 报 “go is not installed” → 多半在 WSL bash 里跑了 Linux 分支，改用 Git Bash（WSL 内通常没有 Go/Git，不是脚本故障）；下载 404 / 鉴权失败 → 先核对 tag 与资产名（v0.1.8 及更早是 `devsys-*`），私有 fork 才需 `gh auth login`；公开仓库匿名下载失败会自动回退源码构建；npm 装完运行报 `no workloom binary for <platform>-<arch>`（exit 1）→ 该平台包尚未发布（npm 目前只发 Windows x64）或安装跳过了 `optionalDependencies`（`--omit=optional`），改用 ①–③（它不会自动下载二进制）。

## 构建

在仓库根构建 `workloom` 二进制（入口 `cmd/workloom`；`cmd/devsys` 是同一 `cli.Run` 的**兼容别名**入口，两者产物行为一致）：

```sh
go build -o bin/workloom.exe ./cmd/workloom   # PowerShell/cmd
go build -o bin/workloom ./cmd/workloom        # Bash / Git Bash
bin/workloom.exe --version    # 版本解析：-ldflags > VCS 伪版本 > 0.1.0-dev
bin/workloom.exe --help
bin/workloom.exe bogus; echo $?   # 2
```

`.exe` 是此仓库 Windows 示例的产物名；其他平台可改为 `bin/workloom`。需要别名入口时另建 `go build -o bin/devsys ./cmd/devsys`；但发布矩阵只编 `./cmd/workloom`，别名由安装脚本以副本形式装入。发布构建需注入版本与短 SHA（与 `scripts/build-release.sh:21-23` 同款 `ldflags` 包路径）：

```sh
go build -ldflags "-X github.com/JAYY513/Workloom/internal/version.Version=0.1.0 -X github.com/JAYY513/Workloom/internal/version.Commit=$(git rev-parse --short HEAD)" -o bin/workloom.exe ./cmd/workloom
```

## init

`workloom init` 是唯一允许修改受管文件的写命令。它把 `.devsys/` 布局落到**当前目录**（项目身份是含 `.devsys/` 的目录，不是 git 根；Git 可选、`init` 从不自动 `git init`）、写入 4 份占位元数据、注册项目路径到用户级注册表，并保证 `.devsys/.gitignore` 至少覆盖 `local/` 与 `.cache/`；`.gitattributes` 只在 git toplevel 写。非 Git 目录与 git 子目录都可初始化，祖先已有 `.devsys/` 时才拒绝嵌套（`internal/project/init.go:42-46`、`:129-132`）。

```sh
cd /path/to/your/project
workloom --json init && workloom --quiet init && workloom config check
```

文本模式报告初始化目录、项目名称与 ID、实际创建的路径数量及注册表路径。JSON 模式返回实际创建路径与登记结果。不要把示例数量当成固定契约。

幂等行为：

- 缺失的 `.devsys/`、子目录和占位文件会被补建；现存占位元数据不重写。
- `.devsys/.gitignore` 若已存在，只追加缺失的 `local/`、`.cache/` 行，原有内容不变。
- 落盘前先校验现有受管元数据；若 `project.yaml` / `config.yaml` / `state/*.yaml` 出现未知 `schema_version`、未知键或类型错误，`init` 拒绝改动并报退出码 4。
- 祖先目录已有 `.devsys/`（禁止嵌套）→ 退出码 3（`PreconditionError`），无任何写入；非 Git 目录与 `git` 不在 PATH 均可正常 `init`（Git 可选）。
- 命令在子目录运行时，`resolveRoot` 从当前目录向上找最近的 `.devsys/` 祖先（环境变量 `DEVSYS_PROJECT_ROOT` 仍可强制覆盖）；找不到祖先时仍用当前目录，保留前置条件错误的旧文案。

## config check

`workloom config check` 是只读诊断：不加锁、不写盘、不恢复事务。它遍历四份受管元数据，逐条定位问题，并按 `文件:行号: 字段: 原因` 格式化输出。

```sh
workloom config check                # 通过：config ok: 4 files checked
workloom --json config check           # {ok,root,checked,project?,config?}
workloom config check; echo $?       # 0 / 4 / 3
```

四份受管文件（顺序固定）：`project.yaml`、`config.yaml`、`state/current.yaml`、`state/milestones.yaml`。问题示例：

```
project.yaml:5: unknown_field: unknown key
project.yaml:2: schema_version: unsupported version 99 (...)
```

`--json` 模式下问题进入 `error.problems` 数组（`code=4`、`kind=invalid`）；通过时返回完整 `project`、`config` 解析结果。

## search

`workloom search <keyword>` 在 `.devsys/` 下做无索引文本扫描：大小写不敏感子串匹配，单文件最多 5 条命中行，行内容截断 200 字节（UTF-8 安全），排除 `.cache/` 与 `local/`。缺少关键字参数或多于一个位置参数 → 退出码 2。

```sh
workloom search 密码
workloom --json search WLM-2
workloom search no-such-keyword; echo $?   # 0（零命中仍成功）
```

文本输出：`<相对路径>:<行号>: <行内容>`，末尾汇总 `<N> match(es) in .devsys/ for "<keyword>"`。

`--json` 字段：`ok`、`root`、`query`、`matches[]`（`path`、`line`、`text`）、`total`。零命中时 `matches` 是空数组、`total=0`，退出码仍为 0。

## M2 状态机与对账命令

M2 命令作用于 `.devsys/` 的领域记录：`workitem` 读写工作项状态，`doctor`/`recover`/`repair` 负责对账与修复。写命令要求 `--actor` 与 `--reason`（写入审计事件）；状态转换与领取用 `--expect <64-hex version>` 提交你读到的版本（`workitem get` 输出），旧快照被拒绝。

```sh
workloom workitem get WLM-1                                                       # 打印字段与 version: <64-hex>
workloom workitem create --title T --actor me --reason r [--description D] --acceptance "c1,c2"
workloom workitem update  --id WLM-1 --acceptance "c1,c2"            # 替换 acceptance 列表
workloom workitem transition/claim --id WLM-1 --actor me --reason r [--expect|--latest]
workloom doctor                                              # 只读：过期/孤儿领取、待恢复事务、修复提议
workloom recover --actor me --reason r
workloom repair --dry-run / --apply --confirm <digest> --actor me --reason r   # 摘要不符 → exit 3
```

- 非法状态转换 → 退出码 4，stderr 列允许的下一步。
- 版本哈希不匹配 → 退出码 4，错误附「the file changed after your read: re-read it and retry, or repeat with --latest」；重新 `workitem get` 取最新 version 或 `--latest` 重跑。
- `doctor` 是只读对账：不创建锁、不触发事务恢复；有待恢复事务时只报告事务、不输出业务事实。

- `recover` 先做确定性事务恢复，再释放过期/孤儿领取（每次释放写 `lease_recovered` 事件）。
- `repair --apply` 需要与当前状态一致的 `--confirm` 摘要；摘要不符或证据漂移 → 退出码 3，不写任何文件。
- M2 完整链路见 `scripts/smoke-m2.{ps1,sh}`。

## M3 工作流 / 审批 / next

M3 三族命令作用于工作流策略、审批生命周期与就绪判定。示例策略 `docs/examples/workflows/quick-fix.md` 给出最简单的端到端入口；更完整见 `feature-development.md` 与 `architecture-change.md`。

```sh
# 1) 准备策略与工作项
cp docs/examples/workflows/quick-fix.md .devsys/workflows/
workloom workflow check                          # 只读：issues + policies；exit 0/4
workloom workitem create --title "fix typo" --actor me --reason 建任务
for t in backlog ready; do workloom workitem transition --id WLM-1 --to $t --actor me --reason smoke --expect "$(workloom --json workitem get WLM-1 | jq -r .version)"; done

# 2) 工作流实例（租约未激活可不带 --owner/--token）
V=$(workloom --json workitem get WLM-1 | jq -r .version)
workloom workflow start --id WLM-1 --policy quick-fix --actor me --reason begin --expect "$V"
workloom workflow next / step-complete / pause / resume / cancel --id WLM-1 --actor me --reason r --expect "$V"

# 3) 领取质量门（policy.quality_gate.min_score 拦截 thin 任务）
workloom workitem claim --id WLM-1 --owner me --reason 开工 --expect "$V"   # exit 0 或 4

# 4) 审批门禁（policy.gates.stages.<stage>.require_approval: true）
workloom workitem transition --id WLM-1 --to in_progress --actor me --reason go --expect "$V"   # 缺审批 → exit 4
workloom approval request  --id WLM-1 --stage in_progress --actor me --reason 关键变更
workloom approval approve  --id approval-1 --by boss --comment ok
workloom workitem transition --id WLM-1 --to in_progress --actor me --reason go --expect "$V"   # 同事务消费
workloom approval reject    --id approval-2 --by boss --reason "risk too high"   # scope=stage_gate → 同事务 blocked

# 5) 就绪判定（只读）
workloom next                   # readiness: PASS|CONCERNS|FAIL + reasons + risks + next；exit 恒 0
workloom --json next            # 完整 Report JSON
```

退出码语义（M3 新增）：
- `workflow check` 策略错误升 `kind="invalid"` `code=4`；未知键 warning 仍 exit 0；`workflows/` 缺失 exit 4。
- 实例操作失败 `kind="workflow"` `code=4`；`--expect` 不匹配 → `kind="precondition"` `code=3`。
- 审批 `request/approve/reject` 失败 `kind="approval"` `code=4`；`request --id` 缺失等参数错误 → `kind="usage"` `code=2`。
- `next` exit 恒 0；按 `--json next` `readiness` 分支。
- 写命令支持 `--expect|--latest`，**互斥**；`version conflict` 由 `app.storeError` 改写为「re-read it and retry, or repeat with --latest」，exit 4 + `kind=workitem`。

## 门禁与策略口径

门禁与质量门只在工作项「有生效策略」时才参与判定，`internal/app/workitem.go:policyForWorkItem` 是唯一解析点：实例（`workflow start --policy <id>`）→ 项目级 `config.yaml: default_policy` → 空。常见用法：

```sh
# A) 按实例绑定（最常见；详见 M3）
workloom workflow start --id WLM-1 --policy quick-fix --actor me --reason begin --latest

# B) 项目级 default_policy：写到 .devsys/config.yaml
# default_policy: quick-fix
workloom workitem create --title "fix typo" --actor me --reason 建任务 \
    --acceptance "回归测试通过,smoke 绿" --description "≥40 字描述…"
workloom workitem transition --id WLM-1 --to ready --actor me --reason spec --latest
workloom workitem claim --id WLM-1 --owner me --reason 开工 --latest   # default_policy 生效
```

四种典型判定：

- **项目级 `default_policy` 已配置、config.yaml 合法**：与显式绑定实例等价；`claim` exit 0，`next` 输出 `quality_blocked` 风险（如有）。
- **`config.yaml` 非法**或 `default_policy` 在 `.devsys/workflows/` 找不到：`policyForWorkItem` 直接报错，`claim`/`transition`/`prompt` 全部拒绝（`code=4`），不会「配置静默丢失 → 绕过门禁」。`workloom config check` 是定位首选。
- **未绑定实例、无 `default_policy`，但 `.devsys/workflows/` 有策略文件**：`workitem claim` 退出 0 后打 `warning: <id> has no workflow instance and no config.yaml default_policy; quality and stage gates did not run`（仅 `--quiet` 抑制）。
- **既无实例也无 `default_policy`、`.devsys/workflows/` 也为空**：不打印 warning。

`next` 与 `claim` 复用同一份判定。ready 任务若 `claim` 会拒绝，会先作为 `quality_blocked` 风险冒出来，并附带 `workitem update --acceptance …` 补救命令。`retry_queued` 项给 `retry_pending` 风险。verdict 在两类风险都存在时仍取最严格的 `FAIL`/`CONCERNS`。

阶段门 `require_approval` 满足时，`workflow.GateEvidence.ApprovalNote` 字段会被 `internal/app/workitem.go:gateEvidence` 写入历史注解：当工作项曾批准、又因离开请求阶段而 `InvalidatedAt != nil` 时，注释为 `approval-N was invalidated at <t> when the work item left "<status>" (方案 §4.9); request a new approval with \`workloom approval request\``。

workloom finding  list/create/resolve [--expect|--latest]
workloom event    list/record
workloom artifact list/register/update/history
workloom run      list/get/create/update/heartbeat
# context 只读聚合（不创建锁、不写盘）

# 知识层（M5）：status exit 0/10/11；scan/validate/refresh [--full|--affected] [--force]

# 会话定向（`prime` = `session start --compact` 别名）
workloom prime / session start --harness <h> --agent <id> --intent <i> [--workspace <dir>] [--compact]

## M5 知识层 + M6 执行调度

M6 起 `workloom` 真正能跑 attempt：执行层（`internal/harness + workspace + dispatch + retry + prompt`）经 `internal/app` 接到 CLI/MCP。

```sh
# 1) worktree（git worktree 生命周期 + 幂等）
workloom worktree prepare --workitem WLM-1 --actor me --reason r [--run run-id] [--branch devsys/my-key]
workloom worktree list/remove --workitem WLM-1 --actor me --reason cleanup [--force]
# 2) dispatch tick（recover → sweep → plan → claim → spawn）
workloom dispatch --once / --watch --interval 30s / --dry-run --actor ops --reason r   # Ctrl-C 退出 0
# 3) attempt：Shell + Codex/OpenCode/ClaudeCode 适配器
workloom run exec --id run-... --actor me --reason r -- -- sh -c "echo hi"
workloom run exec --id run-... --harness codex --model gpt-5 --actor ops --reason r --timeout 120s
# 4) 提示词预览 + 完成校验 + 终态
workloom run prompt/verify/complete/fail/cancel --id run-... --actor me --reason r [--expect|--latest] [--note] [--force --by reviewer]
```

`DEVSYS_PROJECT_ROOT` 让 agent 在 worktree 内运行时把报告写回主仓库 `.devsys/`：

```sh
export DEVSYS_PROJECT_ROOT=/path/to/main/repo
workloom --json run exec --id run-... --harness codex --actor me --reason accept
```

退出码语义（M6 新增）：

- `workloom worktree prepare/remove --path` 越界（不在配置根内）→ exit 3（`kind="precondition"`）。
- `workloom run exec --harness <unknown>` → exit 2（`kind="usage"`）。
- `workloom run exec --harness codex` 但 codex 未安装 → exit 3（`kind="precondition"`）。
- `workloom run exec --timeout` 到期 → 整棵进程树被终止（POSIX 进程组 / Windows JobObject），run 终态 `timeout`。
- `workloom run complete` 验证未 advance → exit 4（`kind="workflow"`），run 进 `failed`，workitem 进 `review`；`--force --by reviewer` 接受。
- `workloom run fail|cancel` 在已终态时 → exit 4（不让两个 actor 抢结果）。
- `workloom run verify` / `workloom dispatch --dry-run` 是只读，exit 恒 0。
- `workloom dispatch --watch` Ctrl-C 退出 0（tick 内失败以 notice 回报）。

## M7 视图域（view/build/serve + 新鲜度提示）

`workloom workspace view` 把 `.devsys/` 状态、git 状态与知识层状态装配成**只读快照**（方案 §17）：不建锁、不恢复事务、不修断尾事件流、不写 `.devsys/.cache/`、不探测生成器。M7.2 起可落离线站、M7.3 起可由本地服务实时渲染。

```sh
# 人类输出：一行一事实（project / baseline / progress / readiness / runs / records / knowledge / trust / sources）
workloom workspace view [--json] [--limit N]

# 离线站 → .devsys/dist/site/（本地派生，不提交）；--out 指可跟踪位置即发布
workloom workspace build --static [--out DIR]
# 本地只读服务（缺省 127.0.0.1），Ctrl+C 停止；非环回须 --allow-remote
workloom workspace serve [--host 127.0.0.1] [--port N]
```

快照能信多少由 `trust.state` 明示：

`trust.state` 三态：`ok`（共享锁 + 无 pending）→ 全事实；`advisory_unlocked`（缺 `.devsys/local/lock`）→ 仍渲染但标快照；`pending_transaction` → 不渲染业务事实。

知识节（`knowledge`）另有四态：`fresh` / `stale`（列 `affected:`/`unverifiable:` + `workloom knowledge refresh`）/ `missing`（给 `--full`）/ `unavailable`（非 pending 给 `knowledge status`，pending 给 `workloom doctor`）——判定与 `workloom knowledge status` 同源（`knowledge.Evaluate`），workspace 退出码保持 0/1/2/3/4（10/11 专属 knowledge）。

退出码：成功 `0`；用法错误（如 `--limit 0`）`2`；当前目录不是已初始化项目 `3`。同一状态连续两次 `--json` 输出**逐字节相同**（模型无墙钟字段），可直接进 diff 或快照测试。

视角区分：`workloom workspace view` 是 §17 **视图域**（只读聚合），`workloom worktree` 是 §4.8 **执行工作区**（git worktree 生命周期 + 钩子），两者不是同一概念。

M7 收尾剧本 `scripts/smoke-m7.{sh,ps1}` 双平台 exit 0（view 只读零写入 / 静态站 8 文件离线 / serve 只读与环回绑定 / 新鲜度 stale-missing-pending 三态）。

## M8 协作层（sync status 接力判定 + archive 保守归档 + repair conflict 标注与 dispatch 门控 + contrabass 可选后端）

M8 把**跨设备接力**（M8.1）、**冲突标注与派发门控**（M8.2）、**保守归档**（M8.3）、**Contrabass 可选后端**（M8.4）四族命令接进 `workloom` CLI。`scripts/smoke-m8.{sh,ps1}` 双平台 PASS。

```sh
# 接力前旧设备必须停 --watch 并 release lease
workloom sync status                          # verdict：handoff: ready 还是 blocked [<code>]
# blocked [code]：uncommitted-devsys→commit；active-leases→release+commit；
# unmerged-paths→见冲突解决；pending-transactions→recover；diverged→fetch/pull；no-upstream→push -u

# 2) 冲突解决（M8.2）：git 保留双方，workloom 不自动合并、不按时间戳选赢家
workloom repair --dry-run --actor me --reason conflict > repair.txt   # 列 note_unmerged_paths
workloom repair --apply --confirm <digest> --actor me --reason conflict
workloom dispatch --dry-run --actor me --reason tick                # 合并未解时直接拒绝 (exit 3)

# 3) 归档（M8.3）：默认保守 —— 不删，只归档；running stop 优先
workloom archive events --before 2999-01 [--dry-run] --actor me --reason trim   # running run 拒绝 (exit 2)

# 4) Contrabass 可选后端（M8.4）：看板卡片是投递副本，不是事实来源；回流只调 CLI
py -3 scripts/contrabass/export.py --root <项目根> --out <board目录> [--id WLM-1,...]
py -3 scripts/contrabass/import.py --root <项目根> --board <board目录> [--dry-run] --actor board --reason verdict
```

接力剧本（原 README 详细章节内容，现 README 已瘦身为决策页）：旧设备停 `--watch` + `recover` 清 pending + 释放活跃租约 + `git push`（状态提交 `chore(devsys):` 前缀）→ 新设备 `git fetch` 后 `sync status` 报 `handoff: ready` 再接手。`sync status` 只读本地上游镜像（不 fetch），不能证明另一台设备已停写。

退出码语义（M8 新增）：

- `sync status` 阻塞仍 exit 0；git 缺失 / 非仓库 / 缺 `.devsys/` → exit 3。
- `dispatch`（含 `--dry-run`）合并未解时 → exit 3 + stderr「dispatch blocked: …」。
- `archive events --before` / `archive runs --id`：缺 `--actor`/`--reason`/`--before`/`--id` → exit 2；running run → exit 2 +「only terminal runs may be archived」；写入失败 → exit 1；前置条件错误 → exit 3。
- `repair --apply --confirm <digest>` digest 不符 → exit 3；冲突未解 → 整单 rejected、零写入。
- contrabass 脚本：非零退出写 `refused` 列表（export 解析失败回退；import 非法边/过期版本进 `refused`）。

M8 端到端剧本：`scripts/smoke-m8.{sh,ps1}` 双平台实跑通过四段：① sync status 阻断码 ② conflict+dispatch exit 3 ③ 归档可查+字节下降 ④ board 闭环。

```sh
bash scripts/smoke-m8.sh --keep   # PowerShell：powershell ... -File scripts/smoke-m8.ps1 -Keep
```

## 典型工作流与剧本

端到端最短路径（自 v0.1.1 起的主线剧本）：

```sh
# 0) 一次性接入
workloom wire --check / wire / wire --skill / wire --print-mcp codex
workloom workflow init --template quick-fix          # 或 cp docs/examples/workflows/quick-fix.md .devsys/workflows/

workloom prime / session start --compact                                 # 项目事实 + 推荐动作
workloom project status                                                 # 计数 + 风险
# 2) 建任务（一次性给 acceptance）
workloom workitem create --title "fix typo" --actor me --reason r \
    --description "≥40 字…" --acceptance "回归测试通过,smoke 绿"
# 3) 推进 + 领取
workloom workitem transition --id WLM-1 --to ready --actor me --reason spec --latest
workloom workflow start      --id WLM-1 --policy quick-fix --actor me --reason begin --latest
workloom next                                                         # ready 任务按 quality_gate 判定
workloom workitem claim --id WLM-1 --owner me --reason 开工 --latest
# 4) 提交 + 完成
git add -A && git commit -m "fix: typo"
workloom workitem complete --id WLM-1 --actor me --reason done --latest
```

全局开关（`--json`/`--jsonl`/`--quiet`/`--version`/`--help`）必须放在子命令之前；解析器遇到第一个非选项参数即停止收集开关。

JSON / JSONL 模式：
- `--json`：成功 stdout（`ok:true`），错误 stderr（`{ok:false, error:{code,kind,message,problems?}}`）。
- `--jsonl`：列表类命令「一行一条 JSON 记录」，字段名与 `--json` 信封内同名数组一致；空列表渲染零行（不是空文档）。

 `kind` 扩到 `"workitem"` / `"workflow"` / `"approval"`；又扩到 `"gate"` / `"quality"`。`config check` 不加锁、不写盘，只做只读诊断。
