## init

`devsys init` 是唯一允许修改受管文件的写命令。它把 `.devsys/` 布局落到 Git 仓库根目录、写入 4 份占位元数据、注册项目路径到用户级注册表，并保证 `.devsys/.gitignore` 至少覆盖 `local/` 与 `.cache/`。子目录不是仓库根时会拒绝执行。

```sh
cd /path/to/your/git-repo
devsys --json init
devsys --quiet init
devsys config check
```

文本模式报告初始化目录、项目名称与 ID、实际创建的路径数量及注册表路径；数量取决于已有布局。JSON 模式返回实际创建路径与登记结果。参见下方 CLI 源码引用；不要把示例数量当成固定契约。

幂等行为：

- 缺失的 `.devsys/`、子目录和占位文件会被补建；现存占位元数据不重写。
- `.devsys/.gitignore` 若已存在，只追加缺失的 `local/`、`.cache/` 行，原有内容不变。
- 落盘前先校验现有受管元数据；若已存在的 `project.yaml` / `config.yaml` / `state/*.yaml` 出现未知 `schema_version`、未知键或类型错误，`init` 拒绝改动并报退出码 4。
- 当前目录不在 Git 仓库或 `git` 不可用 → 退出码 3（前置条件），无任何写入。
- 命令在子目录运行时，`resolveRoot` 从当前目录向上找最近的 `.devsys/` 祖先（环境变量 `DEVSYS_PROJECT_ROOT` 仍可强制覆盖），所以从 `repos/foo/.devsys/scratch/` 直接调 `devsys workitem list` 也定位到 `repos/foo/`；找不到祖先时仍然用当前目录，以保留前置条件错误的旧文案。

## config check

`devsys config check` 是只读诊断：不加锁、不写盘、不恢复事务。它遍历四份受管元数据文件，逐条定位问题，并按 `文件:行号: 字段: 原因` 格式化输出。

```sh
devsys config check             # 通过：config ok: 4 files checked
devsys --json config check      # {ok,root,checked,project?,config?}
devsys config check; echo $?    # 0 / 4 / 3
```

四份受管文件（顺序固定）：`project.yaml`、`config.yaml`、`state/current.yaml`、`state/milestones.yaml`。问题示例：

```
project.yaml:5: unknown_field: unknown key
project.yaml:2: schema_version: unsupported version 99 (...)
config.yaml:2: timeout: unknown key
```

`--json` 模式下问题进入 `error.problems` 数组（`code=4`、`kind=invalid`）；通过时返回完整 `project`、`config` 解析结果。`init` 之前的项目目录 → 退出码 3。

## search

`devsys search <keyword>` 在 `.devsys/` 下做无索引文本扫描：大小写不敏感子串匹配，单文件最多 5 条命中行，行内容截断 200 字节（UTF-8 安全），排除 `.cache/` 与 `local/`。缺少关键字参数或多于一个位置参数 → 退出码 2。

```sh
devsys search 密码
devsys --json search WLM-2
devsys search no-such-keyword; echo $?   # 0（零命中仍成功）
```

文本输出：`<相对路径>:<行号>: <行内容>`，末尾汇总 `<N> match(es) in .devsys/ for "<keyword>"`。

`--json` 字段：`ok`、`root`、`query`、`matches[]`（`path`、`line`、`text`）、`total`。零命中时 `matches` 是空数组、`total=0`，退出码仍为 0。

## M2 状态机与对账命令

M2 命令作用于 `.devsys/` 的领域记录：`workitem` 读写工作项状态，`doctor` / `recover` / `repair` 负责对账与修复。写命令都要求 `--actor` 与 `--reason`（写入审计事件）；状态转换与领取用 `--expect <64-hex version>` 提交你读到的版本（`workitem get` 输出），旧快照会被拒绝。

```sh
bin/devsys.exe workitem get WLM-1                                   # 打印字段与 version: <64-hex>
bin/devsys.exe workitem create --title 任务标题 --actor me --reason 建任务 [--description D] --acceptance "criterion 1,criterion 2"
bin/devsys.exe workitem update  --id WLM-1 --acceptance "criterion 1,criterion 2"   # 替换 acceptance 列表
bin/devsys.exe workitem transition --id WLM-1 --to ready --actor me --reason 拆分完成 [--expect <hash> | --latest]
bin/devsys.exe workitem claim --id WLM-1 --owner me --reason 开工 [--expect <hash> | --latest]   # 无实例且无 default_policy 时打印 `warning:`
bin/devsys.exe doctor                                               # 只读：过期/孤儿领取、待恢复事务、修复提议
bin/devsys.exe recover --actor me --reason 恢复中断的领取
bin/devsys.exe repair --dry-run --actor me --reason 盘点             # 打印提议表与 digest
bin/devsys.exe repair --apply --confirm <digest> --actor me --reason 确认修复
```

- 非法状态转换（如 `draft → in_progress`）→ 退出码 4，stderr 列出允许的下一步。
- 版本哈希不匹配（旧视图）→ 退出码 4，错误附「the file changed after your read: re-read it and retry, or repeat with --latest where the command offers it」；推荐路径是重新 `workitem get` 取最新 version，或带 `--latest` 重跑（仍走 CAS）。
- `doctor` 是只读对账：不创建锁文件、不触发事务恢复；有待恢复事务时只报告事务、不输出业务事实。



- `recover` 先做确定性事务恢复，再释放过期/孤儿领取（每次释放写 `lease_recovered` 事件）；重复执行不产生重复事件。
- `repair --apply` 需要与当前状态一致的 `--confirm` 摘要；摘要不符或证据漂移 → 退出码 3，不写任何文件。
- M2 完整链路（领取 → 模拟崩溃 → `doctor` → `recover` → 确认修复）见 `scripts/smoke-m2.ps1` / `scripts/smoke-m2.sh`。

## M3 工作流 / 审批 / next

M3 三族命令作用于工作流策略、审批生命周期与就绪判定。示例策略 `docs/examples/workflows/quick-fix.md` 给出最简单的端到端入口；更完整的见 `feature-development.md` 与 `architecture-change.md`。

```sh
# 1) 准备策略与工作项
cp docs/examples/workflows/quick-fix.md .devsys/workflows/
bin/devsys.exe workflow check                       # 只读：issues + policies；exit 0/4
bin/devsys.exe workitem create --title "fix typo" --actor me --reason 建任务
for t in backlog ready; do bin/devsys.exe workitem transition --id WLM-1 --to $t --actor me --reason smoke --expect "$(bin/devsys.exe --json workitem get WLM-1 | jq -r .version)"; done

# 2) 启动工作流实例（租约未激活：可不带 --owner/--token）
V=$(bin/devsys.exe --json workitem get WLM-1 | jq -r .version)
bin/devsys.exe workflow start --id WLM-1 --policy quick-fix --actor me --reason begin --expect "$V"
bin/devsys.exe workflow next --id WLM-1                          # 列出当前步骤候选与首满足推荐
bin/devsys.exe workflow step-complete --id WLM-1 --actor me --reason go --expect "$V"   # 自动取首满足

bin/devsys.exe workflow cancel --id WLM-1 --actor me --reason abort --expect "$V"

V=$(bin/devsys.exe --json workitem get WLM-1 | jq -r .version)
bin/devsys.exe workitem claim --id WLM-1 --owner me --reason 开工 --expect "$V"      # exit 0 或 4

# 4) 审批门禁（policy.gates.stages.<stage>.require_approval: true）
V=$(bin/devsys.exe --json workitem get WLM-1 | jq -r .version)
```

## 门禁与策略口径

门禁与质量门只在工作项「有生效策略」时才参与判定，`internal/app/workitem.go:policyForWorkItem` 是唯一解析点：实例（`workflow start --policy <id>`）→ 项目级 `config.yaml: default_policy` → 空。任何写路径（`transition` / `claim` / 提示词装配 / `worktree` 钩子）都从这里取策略体，不再各写一份。常见用法：

```sh
# A) 按实例绑定（最常见；详见 M3）
devsys workflow start --id WLM-1 --policy quick-fix --actor me --reason begin --latest

# B) 项目级 default_policy：写到 .devsys/config.yaml
# default_policy: quick-fix
# 不绑定实例、但命中 default_policy 的工作项同样过质量门/阶段门/提示词/工作区钩子
devsys workitem create --title "fix typo" --actor me --reason 建任务 \
    --acceptance "回归测试通过,smoke 绿" --description "≥40 字描述…"
devsys workitem transition --id WLM-1 --to ready --actor me --reason spec --latest
devsys workitem claim        --id WLM-1 --owner me --reason 开工 --latest   # default_policy 生效
```

四种典型判定：

- **项目级 `default_policy` 已配置、config.yaml 合法**：与显式绑定实例等价，过质量门与阶段门；`claim` exit 0，`next` 输出 `quality_blocked` 风险（如有），`require_approval` 门禁按 `default_policy` 评估。
- **`config.yaml` 非法**或显式声明的 `default_policy` 在 `.devsys/workflows/` 找不到对应文件：`policyForWorkItem` 直接报错，`claim` / `transition` / `prompt` 全部拒绝（`code=4`），不会出现「配置静默丢失 → 绕过门禁」。`devsys config check` 是定位的首选命令。
- **未绑定实例、无 `default_policy`，但 `.devsys/workflows/` 有策略文件**：`workitem claim` 在退出 0 之后额外打印一行 `warning: <id> has no workflow instance and no config.yaml default_policy; quality and stage gates did not run`（仅在文本模式 `--quiet` 抑制），告诉操作者「没跑门禁」。`next` 对同一工作项会把质量门跑一遍判定 `quality_blocked`，但其他写路径不再补审。
- **既无实例也无 `default_policy`、`.devsys/workflows/` 也为空**：不打印 warning（没有可参考的策略集合）。

`next` 与 `claim` 复用同一份判定（`next.QualityBlocks` 在 `internal/app/next.go` 调用时按每条工作项解析 `DefaultPolicy` 或实例），所以 ready 任务若 `claim` 会拒绝，会先作为 `quality_blocked` 风险冒出来，并附带 `workitem update --acceptance …` / 补描述的补救命令（在 `internal/next/evaluate.go:Improvements` 里写明）。`retry_queued` 中的项给 `retry_pending` 风险，含 `next attempt at <RFC3339>` 时间戳。`next` 的 verdict 在上述两种风险都存在时仍取最严格的 `FAIL` / `CONCERNS`。

阶段门 `require_approval` 满足时，`workflow.GateEvidence.ApprovalNote` 字段会被 `internal/app/workitem.go:gateEvidence` 写入一段历史注解：当工作项曾经批准、但又因离开请求阶段而 `InvalidatedAt != nil` 时，注释为 `approval-N was invalidated at <t> when the work item left "<status>" (方案 §4.9); request a new approval with \`devsys approval request\``，告诉操作者该审批不是因为决定而消失、而是被状态机作废，需重新请求。

快照能信多少由 `trust.state` 明示：

| `trust.state` | 触发条件 | 快照里有什么 |
|---|---|---|
| `ok` | 在既有锁文件上取到共享锁，且无待恢复事务 | 全部业务事实 |
| `advisory_unlocked` | 项目从未写过状态（缺 `.devsys/local/lock`，典型是只读副本或新检出） | 仍渲染业务事实，但标注这次读取没有共享锁保护——视图是快照，不是判决 |
| `pending_transaction` | 存在未完成事务（与 `devsys doctor` 同类信号） | **不渲染业务事实**（方案 §15.4）：`trust.pending_transactions` 列出事务 ID，`progress.readiness` 给 FAIL + `devsys recover --actor … --reason …` 修复项 |

## M8 协作层（sync status 接力判定 + archive 保守归档 + repair conflict 标注与 dispatch 门控 + contrabass 可选后端）

M8 把 **跨设备接力**（M8.1）、**冲突标注与派发门控**（M8.2）、**保守归档**（M8.3）、**Contrabass 可选后端**（M8.4）四族命令接进 devsys CLI。`scripts/smoke-m8.{sh,ps1}` 双平台 PASS 走的就是下面这条最短路径（命令字面量照抄[脚本](file://scripts/smoke-m8.sh)，不编 flags）。

```sh
# 0) 起点：一台干净的设备，刚 push 完当前主分支
#    （接力前旧设备必须停 --watch 并 release lease —— 见 README §接力剧本）
bin/devsys.exe sync status                    # 看 verdict：handoff: ready 还是 blocked [<code>]

# 1) 若 ready：直接上手
#    若 blocked [<code>]：按 code 修复（uncommitted-devsys → commit；active-leases →
#    release + commit；unmerged-paths/merge-in-progress → 见下文冲突解决；pending-transactions
#    → recover；diverged-from-upstream → git fetch/pull；no-upstream → git push -u）

# 2) 冲突解决（M8.2）：git 保留双方，devsys 不自动合并、不按时间戳选赢家
"$D" repair --dry-run --actor me --reason conflict > repair.txt
#    → 列出 note_unmerged_paths（含 porcelain unmerged + MERGE_HEAD 等施工痕迹）
#    digest 在两次运行间稳定；apply 对所有 note_* 项恒 rejected、零写入
#    人工 git 解决（保留双方显式二选一或手动合并，状态提交用 chore(devsys): 前缀）
"$D" repair --apply --confirm <digest> --actor me --reason conflict   # 清租约残留
"$D" dispatch --dry-run --actor me --reason tick   # 合并未解时直接拒绝 (exit 3)

# 3) 归档（M8.3）：默认保守 —— 不删，只归档；running stop 优先
"$D" archive events --before 2999-01 --dry-run --actor me --reason trim   # 零写入预览
"$D" archive events --before 2999-01        --actor me --reason trim   # 实际移动
#    running run 流拒绝归档（exit 2）；归档后 event list / run log 自动合并 live + archive
#    （现役 .devsys/events+runs(*.jsonl) 字节下降；git 对象库不立即收缩）

# 4) Contrabass 可选后端（M8.4）：看板卡片是投递副本，不是事实来源；回流只调 CLI
py -3 scripts/contrabass/export.py --root <项目根> --out <board目录> [--id WLM-1,...] [--devsys ...]
#    看板侧执行（仿真或真 Contrabass）→ 改卡片 board_status + result.summary
py -3 scripts/contrabass/import.py --root <项目根> --board <board目录> \
    --dry-run --actor board --reason verdict [--devsys ...]   # 先预览零写入
py -3 scripts/contrabass/import.py --root <项目根> --board <board目录> \
    --actor board --reason verdict [--devsys ...]              # 真正回流
#    仅 done / review / blocked / closed→cancelled 四态做 transition --expect；
#    其余只 comment；非法边 / 过期版本进 refused，不直写 .devsys/
```

接力剧本（README §14.4）：旧设备停 `--watch` + `recover` 清 pending + 释放活跃租约 + `git push`（状态提交用 `chore(devsys):` 前缀）→ 新设备 `git fetch` 后 `sync status` 报 `handoff: ready` 再接手。`sync status` 只读本地上游镜像（不 fetch），不能证明另一台设备已停写 —— 交接完成前旧设备不得继续写入。

退出码语义（M8 新增）：

- `sync status`：阻塞仍 exit 0（被检查的状态不是命令失败）；git 缺失 / 非仓库 / 缺 `.devsys/` → exit 3（precondition）。
- `dispatch`（含 `--dry-run`）在合并未解时 → exit 3 + stderr 「dispatch blocked: …」。
- `archive events --before` / `archive runs --id`：用法错误（缺 `--actor`/`--reason`/`--before`/`--id`）→ exit 2；running run → exit 2 + 「only terminal runs may be archived」；写入失败 → exit 1；前置条件错误 → exit 3。
- `repair --apply --confirm <digest>`：digest 不符 → exit 3；冲突未解 → 整单 rejected、零写入。
- contrabass 脚本：非零退出会写 `refused` 列表（export 解析失败回退；import 非法边 / 过期版本进 `refused`），返回码非 0 表示有 refused 项。

M8 端到端剧本：`scripts/smoke-m8.{sh,ps1}` 双平台实跑通过四段：
1. **sync status 三类阻断码**：`handoff: ready`（clean pushed tree）→ `blocked [uncommitted-devsys]`（`event record` 后未 commit）→ `blocked [active-leases]`（claim 后）→ release + commit 恢复 `handoff: ready`。
2. **conflict 标注 + digest 稳定 + apply rejected + dispatch exit 3**：制造 base/side/main 三向冲突 → `repair --dry-run` 标 `note_unmerged_paths` + `MERGE_HEAD`，两次 digest 字节级一致 → `repair --apply` rejected `clash.txt`，`.devsys/` 树 hash 不变 → `dispatch --dry-run` exit 3 + `dispatch blocked` → git 解决 → `dispatch --dry-run` 恢复 + `sync status` ready。
3. **归档可查 + 字节下降**：dry-run 零写入 + 不留 untracked → apply 后 `live bytes: N -> 0` + `archive/manifest.yaml` 落地 → `event list` 条数前后一致 → running run 流拒绝（exit 2 + `only terminal runs may be archived`）。
4. **board 闭环**：workitem 走 `review → verification` → export 看到 `verification -> review` 映射 → 改卡片 `board_status=done` + `result.summary`（PowerShell 端用 `[Text.UTF8Encoding]::new($false)` 写无 BOM UTF-8） → import `--dry-run` 预览零写入 → import 真正回流 `verification -> done` + `[board] board executed OK` comment → 终态 `handoff: ready` + tree clean。
