## 安装

`v0.1.0` 起官方提供 Release 二进制：`v0.1.1` 由 GitHub Actions 跑 `scripts/build-release.sh` 一次性产出 6 平台矩阵 + `checksums.txt`（**GNU 文本格式** `<sha256>  <file>`；脚本严格自检，shasum 的 `*` 标记会让发布流中止）。`v0.1.1` 实跑：run `35496169845`，3m11s 全绿，7 资产；`v0.1.6` 起 `install.sh` / `install.ps1` 本身随 GitHub Release 资产发布。发布细节见 docs/发布流程.md（纯文本路径）；装机/接入完整流程见 INSTALL.md（纯文本路径）。安装方式三态：

**① Release 脚本直装（推荐，约 10 秒）**：打开 Releases 页（github.com/JAYY513/Workloom/releases/latest），下载 `install.sh`（Windows PowerShell 用 `install.ps1`），用同页 `checksums.txt` 校验后执行：

```bash
bash install.sh --tag v0.1.7            # Linux / macOS（Git Bash）→ ~/.local/bin
powershell -NoProfile -ExecutionPolicy Bypass -File install.ps1 -Tag v0.1.7 -AddToPath   # Windows → %LOCALAPPDATA%\devsys
```

装完用 `devsys --version` 自证（应输出 `devsys v0.1.7 (hash)`）。本仓库为私有仓库：脚本优先 `gh release download` 鉴权下载（要求 `gh auth login`），`gh auth status` 退出非 0 时不调用 gh，直接回退 `curl` / `Invoke-WebRequest` 匿名拉取；都失败时自动回退 `git -c advice.detachedHead=false clone --branch <tag> --depth 1 + go build`（本机需 Go + Git，回退构建经 `ldflags` 注入 tag，产物报 `devsys <tag>`）。`install.ps1` 装到 `%LOCALAPPDATA%\devsys\` 且只改 User PATH。手动核对（私有仓库同样需要 `gh auth login`）：`gh release download v0.1.7 --pattern 'devsys-*' && cd dist && sha256sum -c checksums.txt`。

**② go install 直装（v0.1.7 起，需已装 Go）**：模块路径规范化为 `github.com/JAYY513/Workloom` 并带版本兜底；私有仓库先让 Go 直连（跳过公共校验和数据库），`@latest` 解析为最新语义化 tag：

```bash
go env -w GOPRIVATE=github.com/JAYY513/Workloom
go install github.com/JAYY513/Workloom/cmd/devsys@latest
```

**③ 源码构建（兜底，仓库已提交 `vendor/`，可离线完成）**：

```bash
git clone https://github.com/JAYY513/Workloom.git && cd Workloom
GOPROXY=off GOFLAGS=-mod=vendor go build -o bin/devsys ./cmd/devsys   # Windows 产物加 .exe 扩展名
```

排障速查（docs/使用手册.md §7「排障速查」症状→处置表）：装完 `devsys: command not found` → 重开终端刷新 PATH，Windows 查 `%LOCALAPPDATA%\devsys` 是否已进 User PATH；`--version` 报 `0.1.0-dev` → 旧版或源码裸构建标记（release 安装应报 `vX.Y.Z (hash)`，go install 报 `vX.Y.Z`）；install.sh 报 “go is not installed” → 多半在 WSL bash 里跑了 Linux 分支，改用 Git Bash（WSL 内通常没有 Go/Git，不是脚本故障）；下载 404 / 鉴权失败 → 私有库先 `gh auth login`，未登录自动回退源码构建。

## 构建

在仓库根构建 `devsys` 二进制：

```sh
go build -o bin/devsys.exe ./cmd/devsys   # PowerShell/cmd
go build -o bin/devsys ./cmd/devsys        # Bash / Git Bash
bin/devsys.exe --version    # devsys 0.1.0-dev
bin/devsys.exe --help
bin/devsys.exe bogus; echo $?   # 2
```

`.exe` 是此仓库 Windows 示例的产物名；其他平台可改为 `bin/devsys`。发布构建需注入版本与短 SHA：

```sh
go build -ldflags "-X workloom/internal/version.Version=0.1.0 -X workloom/internal/version.Commit=$(git rev-parse --short HEAD)" -o bin/devsys.exe ./cmd/devsys
```

## init

`devsys init` 是唯一允许修改受管文件的写命令。它把 `.devsys/` 布局落到 Git 仓库根目录、写入 4 份占位元数据、注册项目路径到用户级注册表，并保证 `.devsys/.gitignore` 至少覆盖 `local/` 与 `.cache/`。子目录不是仓库根时拒绝执行。

```sh
cd /path/to/your/git-repo
devsys --json init && devsys --quiet init && devsys config check
```

文本模式报告初始化目录、项目名称与 ID、实际创建的路径数量及注册表路径。JSON 模式返回实际创建路径与登记结果。不要把示例数量当成固定契约。

幂等行为：

- 缺失的 `.devsys/`、子目录和占位文件会被补建；现存占位元数据不重写。
- `.devsys/.gitignore` 若已存在，只追加缺失的 `local/`、`.cache/` 行，原有内容不变。
- 落盘前先校验现有受管元数据；若 `project.yaml` / `config.yaml` / `state/*.yaml` 出现未知 `schema_version`、未知键或类型错误，`init` 拒绝改动并报退出码 4。
- 当前目录不在 Git 仓库或 `git` 不可用 → 退出码 3，无任何写入。
- 命令在子目录运行时，`resolveRoot` 从当前目录向上找最近的 `.devsys/` 祖先（环境变量 `DEVSYS_PROJECT_ROOT` 仍可强制覆盖）；找不到祖先时仍用当前目录，保留前置条件错误的旧文案。

## config check

`devsys config check` 是只读诊断：不加锁、不写盘、不恢复事务。它遍历四份受管元数据，逐条定位问题，并按 `文件:行号: 字段: 原因` 格式化输出。

```sh
devsys config check                # 通过：config ok: 4 files checked
devsys --json config check           # {ok,root,checked,project?,config?}
devsys config check; echo $?       # 0 / 4 / 3
```

四份受管文件（顺序固定）：`project.yaml`、`config.yaml`、`state/current.yaml`、`state/milestones.yaml`。问题示例：

```
project.yaml:5: unknown_field: unknown key
project.yaml:2: schema_version: unsupported version 99 (...)
```

`--json` 模式下问题进入 `error.problems` 数组（`code=4`、`kind=invalid`）；通过时返回完整 `project`、`config` 解析结果。

## search

`devsys search <keyword>` 在 `.devsys/` 下做无索引文本扫描：大小写不敏感子串匹配，单文件最多 5 条命中行，行内容截断 200 字节（UTF-8 安全），排除 `.cache/` 与 `local/`。缺少关键字参数或多于一个位置参数 → 退出码 2。

```sh
devsys search 密码
devsys --json search WLM-2
devsys search no-such-keyword; echo $?   # 0（零命中仍成功）
```

文本输出：`<相对路径>:<行号>: <行内容>`，末尾汇总 `<N> match(es) in .devsys/ for "<keyword>"`。

`--json` 字段：`ok`、`root`、`query`、`matches[]`（`path`、`line`、`text`）、`total`。零命中时 `matches` 是空数组、`total=0`，退出码仍为 0。

## M2 状态机与对账命令

M2 命令作用于 `.devsys/` 的领域记录：`workitem` 读写工作项状态，`doctor`/`recover`/`repair` 负责对账与修复。写命令要求 `--actor` 与 `--reason`（写入审计事件）；状态转换与领取用 `--expect <64-hex version>` 提交你读到的版本（`workitem get` 输出），旧快照被拒绝。

```sh
devsys workitem get WLM-1                                                       # 打印字段与 version: <64-hex>
devsys workitem create --title T --actor me --reason r [--description D] --acceptance "c1,c2"
devsys workitem update  --id WLM-1 --acceptance "c1,c2"            # 替换 acceptance 列表
devsys workitem transition/claim --id WLM-1 --actor me --reason r [--expect|--latest]
devsys doctor                                              # 只读：过期/孤儿领取、待恢复事务、修复提议
devsys recover --actor me --reason r
devsys repair --dry-run / --apply --confirm <digest> --actor me --reason r   # 摘要不符 → exit 3
```

- 非法状态转换 → 退出码 4，stderr 列允许的下一步。
- 版本哈希不匹配 → 退出码 4，错误附「the file changed after your read: re-read it and retry, or repeat with --latest」；重新 `workitem get` 取最新 version 或 `--latest` 重跑。
- `doctor` 是只读对账：不创建锁、不触发事务恢复；有待恢复事务时只报告事务、不输出业务事实。

- `recover` 先做确定性事务恢复，再释放过期/孤儿领取（每次释放写 `lease_recovered` 事件）。
- `repair --apply` 需要与当前状态一致的 `--confirm` 摘要；摘要不符或证据漂移 → 退出码 3，不写任何文件。
- M2 完整链路见 `scripts/smoke-m2.{ps1,sh}`。

## M3 工作流 / 审批 / next

M3 三族命令作用于工作流策略、审批生命周期与就绪判定。示例策略 `docs/examples/workflows/quick-fix.md` 给出最简单的端到端入口；更完整见 `feature-development.md` 与 `architecture-change.md`。

```sh
# 1) 准备策略与工作项
cp docs/examples/workflows/quick-fix.md .devsys/workflows/
devsys workflow check                          # 只读：issues + policies；exit 0/4
devsys workitem create --title "fix typo" --actor me --reason 建任务
for t in backlog ready; do devsys workitem transition --id WLM-1 --to $t --actor me --reason smoke --expect "$(devsys --json workitem get WLM-1 | jq -r .version)"; done

# 2) 工作流实例（租约未激活可不带 --owner/--token）
V=$(devsys --json workitem get WLM-1 | jq -r .version)
devsys workflow start --id WLM-1 --policy quick-fix --actor me --reason begin --expect "$V"
devsys workflow next / step-complete / pause / resume / cancel --id WLM-1 --actor me --reason r --expect "$V"

# 3) 领取质量门（policy.quality_gate.min_score 拦截 thin 任务）
devsys workitem claim --id WLM-1 --owner me --reason 开工 --expect "$V"   # exit 0 或 4

# 4) 审批门禁（policy.gates.stages.<stage>.require_approval: true）
devsys workitem transition --id WLM-1 --to in_progress --actor me --reason go --expect "$V"   # 缺审批 → exit 4
devsys approval request  --id WLM-1 --stage in_progress --actor me --reason 关键变更
devsys approval approve  --id approval-1 --by boss --comment ok
devsys workitem transition --id WLM-1 --to in_progress --actor me --reason go --expect "$V"   # 同事务消费
devsys approval reject    --id approval-2 --by boss --reason "risk too high"   # scope=stage_gate → 同事务 blocked

# 5) 就绪判定（只读）
devsys next                   # readiness: PASS|CONCERNS|FAIL + reasons + risks + next；exit 恒 0
devsys --json next            # 完整 Report JSON
```

退出码语义（M3 新增）：
- `workflow check` 策略错误升 `kind="invalid"` `code=4`；未知键 warning 仍 exit 0；`workflows/` 缺失 exit 4。
- 实例操作失败 `kind="workflow"` `code=4`；`--expect` 不匹配 → `kind="precondition"` `code=3`。
- 审批 `request/approve/reject` 失败 `kind="approval"` `code=4`；`request --id` 缺失等参数错误 → `kind="usage"` `code=2`。
- `next` exit 恒 0；按 `--json next` `readiness` 分支。
- 写命令支持 `--expect|--latest`，**互斥**；`version conflict` 由 `app.storeError` 改写为「re-read it and retry, or repeat with --latest」，exit 4 + `kind=workitem`。

## 门禁与策略口径

门禁与质量门只在工作项「有生效策略」时才参与判定，`internal/app/workitem.go:policyForWorkItem` 是唯一解析点：实例（`workflow start --policy <id>`）→ 项目级 `config.yaml: default_policy` → 空。常见用法：

```sh
# A) 按实例绑定（最常见；详见 M3）
devsys workflow start --id WLM-1 --policy quick-fix --actor me --reason begin --latest

# B) 项目级 default_policy：写到 .devsys/config.yaml
# default_policy: quick-fix
devsys workitem create --title "fix typo" --actor me --reason 建任务 \
    --acceptance "回归测试通过,smoke 绿" --description "≥40 字描述…"
devsys workitem transition --id WLM-1 --to ready --actor me --reason spec --latest
devsys workitem claim --id WLM-1 --owner me --reason 开工 --latest   # default_policy 生效
```

四种典型判定：

- **项目级 `default_policy` 已配置、config.yaml 合法**：与显式绑定实例等价；`claim` exit 0，`next` 输出 `quality_blocked` 风险（如有）。
- **`config.yaml` 非法**或 `default_policy` 在 `.devsys/workflows/` 找不到：`policyForWorkItem` 直接报错，`claim`/`transition`/`prompt` 全部拒绝（`code=4`），不会「配置静默丢失 → 绕过门禁」。`devsys config check` 是定位首选。
- **未绑定实例、无 `default_policy`，但 `.devsys/workflows/` 有策略文件**：`workitem claim` 退出 0 后打 `warning: <id> has no workflow instance and no config.yaml default_policy; quality and stage gates did not run`（仅 `--quiet` 抑制）。
- **既无实例也无 `default_policy`、`.devsys/workflows/` 也为空**：不打印 warning。

`next` 与 `claim` 复用同一份判定。ready 任务若 `claim` 会拒绝，会先作为 `quality_blocked` 风险冒出来，并附带 `workitem update --acceptance …` 补救命令。`retry_queued` 项给 `retry_pending` 风险。verdict 在两类风险都存在时仍取最严格的 `FAIL`/`CONCERNS`。

阶段门 `require_approval` 满足时，`workflow.GateEvidence.ApprovalNote` 字段会被 `internal/app/workitem.go:gateEvidence` 写入历史注解：当工作项曾批准、又因离开请求阶段而 `InvalidatedAt != nil` 时，注释为 `approval-N was invalidated at <t> when the work item left "<status>" (方案 §4.9); request a new approval with \`devsys approval request\``。

## M5 知识层 + M6 执行调度


退出码语义（M6 新增）：

- `devsys worktree prepare/remove --path` 越界（不在配置根内）→ exit 3（`kind="precondition"`）。

- `devsys dispatch --watch` Ctrl-C 退出 0（tick 内失败以 notice 回报）。

## M7 视图域（view/build/serve + 新鲜度提示）

`devsys workspace view` 把 `.devsys/` 状态、git 状态与知识层状态装配成**只读快照**（方案 §17）：不建锁、不恢复事务、不修断尾事件流、不写 `.devsys/.cache/`、不探测生成器。M7.2 起可落离线站、M7.3 起可由本地服务实时渲染。

```sh
# 人类输出：一行一事实（project / baseline / progress / readiness / runs / records / knowledge / trust / sources）
devsys workspace view [--json] [--limit N]

# 离线站 → .devsys/dist/site/（本地派生，不提交）；--out 指可跟踪位置即发布
devsys workspace build --static [--out DIR]

devsys workspace serve [--host 127.0.0.1] [--port N]
```

快照能信多少由 `trust.state` 明示：

`trust.state` 三态：`ok`（共享锁 + 无 pending）→ 全事实；`advisory_unlocked`（缺 `.devsys/local/lock`）→ 仍渲染但标快照；`pending_transaction` → 不渲染业务事实。

知识节（`knowledge`）另有四态：`fresh` / `stale`（列 `affected:`/`unverifiable:` + `devsys knowledge refresh`）/ `missing`（给 `--full`）/ `unavailable`（非 pending 给 `knowledge status`，pending 给 `devsys doctor`）——判定与 `devsys knowledge status` 同源（`knowledge.Evaluate`），workspace 退出码保持 0/1/2/3/4（10/11 专属 knowledge）。

退出码：成功 `0`；用法错误（如 `--limit 0`）`2`；当前目录不是已初始化项目 `3`。同一状态连续两次 `--json` 输出**逐字节相同**（模型无墙钟字段），可直接进 diff 或快照测试。

视角区分：`devsys workspace view` 是 §17 **视图域**（只读聚合），`devsys worktree` 是 §4.8 **执行工作区**（git worktree 生命周期 + 钩子），两者不是同一概念。

## M8 协作层（sync status 接力判定 + archive 保守归档 + repair conflict 标注与 dispatch 门控 + contrabass 可选后端）

M8 把**跨设备接力**（M8.1）、**冲突标注与派发门控**（M8.2）、**保守归档**（M8.3）、**Contrabass 可选后端**（M8.4）四族命令接进 devsys CLI。`scripts/smoke-m8.{sh,ps1}` 双平台 PASS。

```sh
# 接力前旧设备必须停 --watch 并 release lease
devsys sync status                          # verdict：handoff: ready 还是 blocked [<code>]
# blocked [code]：uncommitted-devsys→commit；active-leases→release+commit；
# unmerged-paths→见冲突解决；pending-transactions→recover；diverged→fetch/pull；no-upstream→push -u

# 2) 冲突解决（M8.2）：git 保留双方，devsys 不自动合并、不按时间戳选赢家
devsys repair --dry-run --actor me --reason conflict > repair.txt   # 列 note_unmerged_paths
devsys repair --apply --confirm <digest> --actor me --reason conflict
devsys dispatch --dry-run --actor me --reason tick                # 合并未解时直接拒绝 (exit 3)

# 3) 归档（M8.3）：默认保守 —— 不删，只归档；running stop 优先
devsys archive events --before 2999-01 [--dry-run] --actor me --reason trim   # running run 拒绝 (exit 2)

# 4) Contrabass 可选后端（M8.4）：看板卡片是投递副本，不是事实来源；回流只调 CLI
py -3 scripts/contrabass/export.py --root <项目根> --out <board目录> [--id WLM-1,...]
py -3 scripts/contrabass/import.py --root <项目根> --board <board目录> [--dry-run] --actor board --reason verdict
```

接力剧本（原 README 详细章节内容，现 README 已瘦身为决策页）：旧设备停 `--watch` + `recover` 清 pending + 释放活跃租约 + `git push`（状态提交 `chore(devsys):` 前缀）→ 新设备 `git fetch` 后 `sync status` 报 `handoff: ready` 再接手。`sync status` 只读本地上游镜像（不 fetch），不能证明另一台设备已停写。

退出码语义（M8 新增）：

- `sync status` 阻塞仍 exit 0；git 缺失 / 非仓库 / 缺 `.devsys/` → exit 3。
- `dispatch`（含 `--dry-run`）合并未解时 → exit 3 + stderr「dispatch blocked: …」。
- `archive events --before` / `archive runs --id`：缺 `--actor`/`--reason`/`--before`/`--id` → exit 2；running run → exit 2 +「only terminal runs may be archived」；写入失败 → exit 1；前置条件错误 → exit 3。
- `repair --apply --confirm <digest>` digest 不符 → exit 3；冲突未解 → 整单 rejected、零写入。
- contrabass 脚本：非零退出写 `refused` 列表（export 解析失败回退；import 非法边/过期版本进 `refused`）。

全局开关（`--json`/`--jsonl`/`--quiet`/`--version`/`--help`）必须放在子命令之前；解析器遇到第一个非选项参数即停止收集开关。

JSON / JSONL 模式：
- `--json`：成功 stdout（`ok:true`），错误 stderr（`{ok:false, error:{code,kind,message,problems?}}`）。
- `--jsonl`：列表类命令「一行一条 JSON 记录」，字段名与 `--json` 信封内同名数组一致；空列表渲染零行（不是空文档）。

 `kind` 扩到 `"workitem"` / `"workflow"` / `"approval"`；又扩到 `"gate"` / `"quality"`。`config check` 不加锁、不写盘，只做只读诊断。
