## 编码规范

### Project 模型与受管文件白名单必须同步演进

M1 起 `internal/domain` 统一八类模型与序列化，`project.yaml` 白名单已扩展为完整 `Project`（[internal/domain/models.go:8-24](file://internal/domain/models.go#L8-L24)）；`config.Load` 通过 `domain.DecodeYAML` 解析为 `*domain.Project`（[internal/config/config.go:142-152](file://internal/config/config.go#L142-L152)）。新增字段必须同步三处：

1. `internal/config/validate.go` 的 `projectSpec` 等白名单（[internal/config/validate.go:41-57](file://internal/config/validate.go#L41-L57)）+ 嵌套结构对应 `fieldKind` 与 `checkNested` 分支（[internal/config/validate.go:17-25](file://internal/config/validate.go#L17-L25)、[internal/config/nested.go:18-26](file://internal/config/nested.go#L18-L26)）。
2. `internal/domain/models.go` 中对应的 struct（M1 起 `domain.Project` 是唯一来源；config/init/CLI 不再重复定义 Project）。
3. `internal/project/tree.go` 的占位 builder（[internal/project/tree.go:60-66](file://internal/project/tree.go#L60-L66)），通过 `domain.EncodeYAML` 序列化保证字段顺序与 struct 一致。

`config.Load` 在写命令前置校验会把第三处漏改的字段立刻暴露为"未知键"；`domain.DecodeYAML` 先调用 `storage.CheckSchemaVersion`，再调用 `storage.DecodeYAML`（开启 `KnownFields(true)` 拒绝未知字段）——schema_version 校验在严格解码**之前**进行（[internal/domain/serialize.go:73-78](file://internal/domain/serialize.go#L73-L78)、[internal/storage/serialize.go:35-53](file://internal/storage/serialize.go#L35-L53)）。`config.yaml` 仍只接受 `schema_version`（[internal/config/validate.go:59-61](file://internal/config/validate.go#L59-L61)），业务键留给后续里程碑。状态文件 `state/current.yaml`（`summary/risks/blockers/next_focus`）与 `state/milestones.yaml`（`milestones` 序列）已被收紧（[internal/config/validate.go:63-73](file://internal/config/validate.go#L63-L73)）。

### Workflow 策略白名单必须同步演进（M3 新增）

`internal/workflow.Parse` 用 `knownTopLevel` 与各段嵌套 `mapping(known)` 静态校验（[internal/workflow/parse.go:25-31](file://internal/workflow/parse.go#L25-L31)）。新增字段必须同步三处：

1. `internal/workflow/parse.go` 的 `knownTopLevel` 或嵌套 `mapping(known)`（新增字段 + 类型 + 必填 + 形状校验 + 状态/hook 等封闭枚举校验）。
2. `internal/workflow/policy.go` 的对应 struct（让 `Parse` 能解码、让 `Load` 能产出 `Policy`）。
3. 示例 `docs/examples/workflows/*.md`（端到端 `smoke-m3` 覆盖）。

写命令前置校验通过 `workflow.Load` 把 issue 转 `config.Problem`，问题定位保持 `file[:line][: field]: reason` 一致风格。**未知键**（任意层级）= warning（记录、加载成功、`workflow check` 仍 exit 0）；**结构/类型/必填/交叉引用错误** = error（该文件 Policy 为 nil，exit 4）。值域失败（hook 名 / stage / `on_reject` 格式）一律 fail-closed，防止拼错门禁/钩子被静默丢弃（M3Reviewer ②）。

### 领域序列化保留 null 与空集合的差异

`yaml.v3` 默认把 nil slice 编为 `[]`，丢失"未记录"与"空集合"的区别；`domain.EncodeYAML` 在编码前用 `preserveNulls` 走一遍节点，区分 `null` / `[]` / 缺省（[internal/domain/serialize.go:14-52](file://internal/domain/serialize.go#L14-L52)）。`DecodeYAML` 配套使用 `storage.DecodeYAML` 的 `KnownFields(true)` 拒绝未知字段，并在调用严格解码**之前**用 `storage.CheckSchemaVersion` 校验版本（[internal/domain/serialize.go:73-78](file://internal/domain/serialize.go#L73-L78)、[internal/storage/serialize.go:35-53](file://internal/storage/serialize.go#L35-L53)）。

### 分清有效状态读取与诊断

业务一致性读取使用 `Store.Read`，跨文件提交使用 `Store.Write`：读取遇到待恢复事务先恢复，写入先取独占锁并恢复（[internal/storage/store.go:140-190](file://internal/storage/store.go#L140-L190)）。`config.Diagnose` 故意直接读取、不加锁、不恢复，适用于报告无效或未知版本元数据，不能用它替代有效状态查询（[internal/config/config.go:101-104](file://internal/config/config.go#L101-L104)）。

`init` 先调用 `config.Load` 校验既有受管文件，再补建目录并用单文件原子写生成占位；它**没有**把整个初始化过程包装为 `Store.Write`（[internal/project/init.go:55-110](file://internal/project/init.go#L55-L110)）。调用者不要推导出未实现的全局事务保证。

M3 起 `devsys next` 与 `workflow next` / `workflow check` 也是只读：经 `reconcile.Doctor` 或 `workflow.Load` 收集信息，不持锁、不触发恢复、不可信状态不输出业务事实（§15.4）。

### 乐观更新与 CAS 分配：守卫源于读快照原始字节

`Reader.Expect`（[internal/storage/store.go:127-138](file://internal/storage/store.go#L127-L138)）只返回两种守卫：目标缺失时 `ExpectAbsent()`，目标存在时 `ExpectHash(HashBytes(data))`——`ExpectAny()` 是 `Expect{}` 的零值，由调用方在知道不关心版本时直接构造（[internal/storage/txn.go:24-37](file://internal/storage/txn.go#L24-L37)）。后续更新若文件被别人改写则 `commitLocked` 在写锁内重读并校验失败（[internal/storage/txn.go:258-280](file://internal/storage/txn.go#L258-L280)）。**文件锁解决协作进程的本机访问协调，不等于 Git 跨设备同时领取仲裁**——设备交接前停写（[README.md:126-128](file://README.md#L126-L128)）。

- **CAS 分配**：`workitem.Create` / `run.Create` / `record.create` / `approval.nextNumber` 共享同一形态：写事务内 `nextNumber` 扫目录 `max+1` → `PutYAML(..., ExpectAbsent())`；`ErrConflict` 即 `continue` 重扫，最多 5 次（[internal/workitem/workitem.go:55-88](file://internal/workitem/workitem.go#L55-L88)、[internal/run/run.go:51-92](file://internal/run/run.go#L51-L92)、[internal/record/record.go:124-153](file://internal/record/record.go#L124-L153)、[internal/approval/approval.go:405-421](file://internal/approval/approval.go#L405-L421)）。`SchemaVersion == 0` 在写事务内改写为 `domain.SchemaVersion=1`。
- **乐观更新**：`Update` 把 `ReadSnapshot` 返回的 raw bytes 原封不动传回 `Write`，由 `ExpectHash(HashBytes(expected))` 守卫（[internal/workitem/workitem.go:156-164](file://internal/workitem/workitem.go#L156-L164)、[internal/workitem/workitem.go:169-195](file://internal/workitem/workitem.go#L169-L195)）；并发写抛 `ErrConflict`，**永不**被静默覆盖。
- **Artifact 不可变链**：`NewArtifactVersion` 用 `tx.ReadForExpect` 在写锁内取当前字节 → `*next = *cur` 浅拷贝 → 重置 `next.ID/Version/PreviousID` → `PutYAML` 写**新文件**（[internal/record/record.go:280-325](file://internal/record/record.go#L280-L325)）。现有版本文件**永不**被改写；`ArtifactHistory` 沿 `previous_id` 反查，环检测用 `seen[cursor]` → `ErrBadID`。M3 起 `record.ListArtifacts`（[internal/record/record.go:243-258](file://internal/record/record.go#L243-L258)）按 ID 升序列出全部 artifact 版本，门禁证据收集从中提取 `Name` 集。
- **事件流追加**：`events.Append` 用事件自身 UTC 时间派生 shard（12 月事件 1 月写仍落 12 月分片），ID 由时间戳 + 4 字节 `crypto/rand`（十六进制输出为 8 hex）派生（M3Reviewer2 ①），**无全局计数器**（[internal/events/events.go:44-93](file://internal/events/events.go#L44-L93)、[internal/events/events.go:150-157](file://internal/events/events.go#L150-L157)）。写路径只校验 `reply_to` 必须是 comment 类型（[internal/events/events.go:69-71](file://internal/events/events.go#L69-L71)）；subject 一致性与二级回复（parent 也是 reply）由 `Comments` 聚合阶段校验（[internal/events/events.go:240-264](file://internal/events/events.go#L240-L264)）。
- **M3 多事件同事务**（[internal/storage/txn.go:179-199](file://internal/storage/txn.go#L179-L199)）：`Tx.AppendJSONLRaw` 接收多行 JSONL payload（拒绝空行、CR、缺终止符），`events.AppendBatchTx` 按 shard 分组一次 append。M3 起 `workitem.changeStatus` 提交批 = `status_changed` + Guard 事件 + 失效事件 + 传播事件，每个 shard 仅一次 append（[internal/workitem/state.go:165-182](file://internal/workitem/state.go#L165-L182)）。
- **M3 事务内已暂存查询**（[internal/storage/txn.go:241-247](file://internal/storage/txn.go#L241-L247)）：`Tx.Staged(rel)` 用于 `approval.InvalidateForStatusTx` 跳过本事务已被消费路径写过的文件，避免 `staged twice` 断言。

### M2 写路径契约：状态、领取与修复

状态变更**只**经 `workitem.Transition` / `ApplyRepair`：`Update` 拒绝状态字段变更，租约活跃时普通 `Update` 被阻断（元数据改用 `UpdateClaimed`）；所有状态与领取变更要求 raw 快照作 `Expected`（CLI 的 `--expect` 版本哈希由 `expectedSnapshot` 校验后转字节），旧视图直接 `ErrConflict`/拒绝（[internal/workitem/state.go:46-59](file://internal/workitem/state.go#L46-L59)、[internal/cli/cli.go:493-511](file://internal/cli/cli.go#L493-L511)、[internal/workitem/workitem.go:169-200](file://internal/workitem/workitem.go#L169-L200)）。事件与记录必须同事务：`events.AppendTx`（[internal/events/events.go:95-110](file://internal/events/events.go#L95-L110)）。修复路径额外要求 `Confirmation`（计划摘要）与 `Guard`（写事务内复核全部证据），`ApplyRepair` 缺任一即拒绝（[internal/workitem/state.go:53-59](file://internal/workitem/state.go#L53-L59)）。

### M3 写路径契约：Guard / 失效 / 传播 / 工作流实例（M3 新增）

`workitem.changeStatus`（[internal/workitem/state.go:66-188](file://internal/workitem/state.go#L66-L188)）在 M2 单一事务基础上承担四件事：

1. **租约 fencing**（M2 沿用）：租约活跃时要求 `Token/Owner/RunID/LeaseUntil` 全部匹配。
2. **Guard**（M3 新增，[internal/workitem/state.go:128-134](file://internal/workitem/state.go#L128-L134)）：`req.Guard(tx) ([]*domain.Event, error)` 在事务内、状态字段改写之前被调用。典型 `approval.ConsumeTx` 在 Guard 内把门禁所依赖的审批标记为 consumed 并返回 `approval_consumed` 事件；`ApplyRepair` 的 Guard 走 `reconcile.RepairApply` 的证据复核路径，不返回事件。Guard 返回事件与 `status_changed` 同批 `AppendBatchTx`。
3. **审批失效**（M3 新增，[internal/workitem/state.go:136-141](file://internal/workitem/state.go#L136-L141)）：离开 `from` 状态时 `approval.InvalidateForStatusTx` 把同源未消费、非失效、非 rejected 的审批标记为 `invalidated_at`，事件并入提交批；通过 `Tx.Staged(rel)` 跳过本事务已暂存文件。
4. **记录传播**（M3 新增，[internal/workitem/state.go:175-181](file://internal/workitem/state.go#L175-L181)）：仅在目标 `done` 且来自非 `done` 时触发 `propagateRecordsTx`（[internal/workitem/propagate.go:28-225](file://internal/workitem/propagate.go#L28-L225)），扫描 `decisions/` 与 `findings/` 中 `RelatedWorkItems` 命中的记录，把 `decision://<id>` / `finding://<id>` 追加到父与直接兄弟的 `context_refs`；无 parent 不广播；父子自环拒绝并回滚。

`workflow_instance.go` 五类实例操作（[internal/workitem/workflow_instance.go:108-381](file://internal/workitem/workflow_instance.go#L108-L381)）共用 `workflowWrite`：`ReadForExpect` → `bytes.Equal` 校验 `--expect` → 租约活跃要求 `Owner + Token` fencing → `mutate` 重写 `wi.Workflow` → `PutYAML(ExpectHash)` + `AppendTx` 事件。**不**写工作项状态、不写调度态/租约/`scheduling/`；目标步骤声明 `status` 时当前状态必须匹配（不隐式改状态）；`paused` / 终态 / `--to` 命中声明且条件成立且不等于当前步均给出明确拒绝面。

### M2 中断与恢复诊断

### M3 工作流 / 审批 / next 诊断（M3 新增）

- **LKG 失效**：检查 `.devsys/.cache/workflows/<id>.md` 是否存在；可手动删除强制重建（缓存可重建）。
- **条件白名单报错**：策略编辑期就拒绝；运行时不会因条件语法失败而报错（M3Reviewer5 ②）。
- **门禁证据漂移**：门禁在事务外收集，M3 阶段 `checkTransitionGate` 注释明确 TOCTOU 窗口（M3Reviewer2 ④）；M4.2 提取为应用服务后消除此窗口。
- **审批 `invalidated_at`**：离开 `from` 状态自动失效；M3.7 起同源回退也失效；需重新 `request`。
- **`pending_approval` 风险**：`next` 把存在未决审批的工作项加入 `review` 推荐类，理由 `waiting for <approval-id>`。
- **`workflow next` 在 paused 时不输出 `next:` 推荐**（M3Reviewer5 ⑤）：候选仍展示；`resume` 后再次 `next` 才会给推荐。
- **`workflowWrite` 在租约活跃时拒绝**：CLI 必须传 `--owner` / `--token`；无人持有租约时不强制。
- **`workflow check` warning vs error**：未知键 warning；结构/类型/必填/值域错误 error；非 `.md` 文件 warning `ignored`。
- **`next` 缺业务事实**：待恢复事务或缺锁文件时仅打印风险与修复项，不列 workitems（§15.4）。
- **审批 `scope=action` 无消费路径**：M3.7 显式记遗留；M16.2 接入；当前 `Request --scope action` 可成功但不会被自动消费。

### 搜索诊断的边界

`search` 是无索引的逐行子串扫描：大小写不敏感、单行截断 200 字节（UTF-8 安全）、单文件最多 5 条命中行（[internal/search/search.go:20-37](file://internal/search/search.go#L20-L37)）。多 worker 扇出但每文件独立槽位保证输出顺序与单线程遍历一致（[internal/search/search.go:70-105](file://internal/search/search.go#L70-L105)）。它**不**解析 front matter、不**识别 YAML 结构**——命中就是 raw 文本里出现的子串，key 与 value 等价、M1 / "M1" / "任务: M1" 等所有出现形式都会被命中。M5.1 知识页面解析接入时按页面 front matter 增强过滤；具体升级时再测性能数字（[docs/开发记录.md:66](file://docs/开发记录.md#L66)）。

### 事件流边界

`events.Append` 把分片路径由事件自身的 UTC `t.Year()/Month()` 派生（12 月事件 1 月写仍落 12 月分片）；ID `ev-<UTC时间戳.微秒>-<8hex>` 由时间戳 + 4 字节 `crypto/rand`（十六进制输出为 8 hex）派生，无全局计数器（[internal/events/events.go:44-93](file://internal/events/events.go#L44-L93)、[internal/events/events.go:150-157](file://internal/events/events.go#L150-L157)）。写路径只校验 `reply_to` 必须是 comment 类型（[internal/events/events.go:69-71](file://internal/events/events.go#L69-L71)）；subject 一致性、悬空 reply 与二级回复（parent 也是 reply）由 `Comments` 聚合阶段校验（[internal/events/events.go:240-264](file://internal/events/events.go#L240-L264)）。`ErrIncompleteTail` 由 `internal/storage/jsonl.go` 的 `InspectJSONL` / `appendJSONL` 透传，事件层不做断尾判定（[internal/events/events.go:27](file://internal/events/events.go#L27)、[internal/storage/jsonl.go:22-95](file://internal/storage/jsonl.go#L22-L95)）。

M3 起多事件同事务由 `events.AppendBatchTx`（[internal/events/events.go:108-144](file://internal/events/events.go#L108-L144)）按 shard 分组一次 `AppendJSONLRaw` 完成；状态事件 + Guard 事件 + 失效事件 + 传播事件同批提交，每个 shard 仅一次 append（违反 `staged twice` 由 `Tx.Staged(rel)` 在失效 pass 跳过本事务已写文件解决）。
