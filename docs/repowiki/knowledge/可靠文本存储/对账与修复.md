# 对账与修复

本卡描述 `devsys doctor` / `recover` / `repair` 三条命令的内部实现、契约边界与 M3 起 `RepairApply` 的 Guard 签名变更（`func(*storage.Tx) ([]*domain.Event, error)`，事件并入提交批）。

## 职责分层

| 层 | 入口 | 物理动作 |
|---|---|---|
| `doctor` | `devsys doctor` / `internal/reconcile.Doctor` | 只读扫描（`storage.Inspect`），**不**创建锁文件、**不**触发事务恢复、**不**释放租约、**不**写盘 |
| `recover` | `devsys recover --actor … --reason …` | `storage.Recover`（确定性事务恢复）+ 释放过期/孤儿租约（写 `lease_recovered` 事件）；幂等 |
| `repair --dry-run` | `devsys repair --dry-run --actor … --reason …` | 收集 proposals + 计算确定性 `digest`（不含墙钟） |
| `repair --apply --confirm <digest>` | 同上 + `--confirm` | 重跑 `dry-run` → 比对 `digest` → `ApplyRepair` 在事务内用 Guard 重核证据 → 失败整单回滚 |

## `doctor`：只读对账

### 入口

`reconcile.Doctor(ctx, root, reconcile.Options{})` ([internal/reconcile/reconcile.go:142-208](file://internal/reconcile/reconcile.go#L142-L208))。CLI 层在 `devsys doctor` ([internal/cli/cli.go:1442-1484](file://internal/cli/cli.go#L1442-L1484)) 调用。

### 流程

1. `storage.InspectUnlocked` 列出 `.devsys/local/txn/` 目录与 `scheduling/` 目录，调用 callback 收集信息。
2. **不在 callback 内调 `storage.Read`**——这是只读路径的硬约束（[internal/reconcile/reconcile.go:1-20](file://internal/reconcile/reconcile.go#L1-L20)）。
3. 解析 lease YAML：通过 `reconcile_io.listSchedulingEntries` + 直接 `os.ReadFile` + `domain.DecodeYAML` 读取租约字节——但**只**在 `Inspect` 的 callback 闭包内调用，物理上等价于「共享锁下读」但不走 `storage.Read`。
4. 判定租约状态：
   - `LeaseUntil < now` → 过期租约
   - `WorkItemID` 不存在 → 孤儿租约
   - 不可读 YAML → 不可读租约
5. 收集 repair proposals（状态漂移：工作项 `Status` 与 `SchedulingState` 不一致）。
6. 缺锁文件 → `InspectionOK = false`，附 `InspectionNote`；有待恢复事务 → `InspectionOK = false`。

### 输出

```go
type InspectionReport struct {
    Root                string
    InspectionOK        bool
    Note                string
    PendingTransactions []storage.PendingTxn
    ExpiredLeases       []LeaseProbe
    OrphanLeases        []LeaseProbe
    UnreadableLeases    []LeaseProbe
    Proposals           []Proposal
}
```

### 退出码与行为边界

- `CodeInvalid = 4` 当 `InspectionReport.Proposals` 非空但 caller 是只读命令时**不**报错——doctor 是诊断工具，仅打印 proposals。
- 待恢复事务存在时 `InspectionReport.Orphans` 留空并附恢复提示（[internal/reconcile/reconcile.go:155-208](file://internal/reconcile/reconcile.go#L155-L208)）——不在不可信状态输出业务事实。
- `--json` 输出完整结构。

## `recover`：确定性恢复 + 释放过期租约

### 入口

`reconcile.Recover(ctx, root, opts)` ([internal/reconcile/reconcile.go:209-280](file://internal/reconcile/reconcile.go#L209-L280))。CLI 层 `devsys recover --actor … --reason …` ([internal/cli/cli.go:559-592](file://internal/cli/cli.go#L559-592))，强制 `--actor` / `--reason`。

### 流程

1. `storage.Recover` 完成所有 `.devsys/local/txn/` 的事务重放（commit 前丢弃 / commit 后幂等重放）。
2. 释放过期租约：`workitem.Release`，写 `lease_recovered` 事件。
3. 释放孤儿租约（同上）。
4. 不可读租约**只报告不释放**——避免破坏未知语义的状态。
5. **引用缺失 workitem 的租约只报告不释放**——避免破坏 workitem 状态图。

### 幂等性

`workitem.Release` 是 `ExpectHash` 守卫；重复执行（`ErrConflict`）跳过——多次 recover 不会产生重复 `lease_recovered` 事件。

## `repair`：推断 → 确认 → 重写

### 入口

- `reconcile.RepairDryRun(ctx, root, opts)` ([internal/reconcile/reconcile.go:282-355](file://internal/reconcile/reconcile.go#L282-L355))：只读扫描，输出 `Plan{Proposals, Digest}`。
- `reconcile.RepairApply(ctx, root, plan, opts)` ([internal/reconcile/reconcile.go:357-513](file://internal/reconcile/reconcile.go#L357-L513))：在事务内用 Guard 重核证据后写盘。

### DryRun 输出

```go
type Plan struct {
    Proposals []Proposal
    Digest    string  // sha256-hex of proposals，不含墙钟
}

type Proposal struct {
    WorkItemID string
    From       string  // 推断的当前状态
    To         string  // 修复目标状态
    Evidence   []Evidence
}

type Evidence struct {
    Kind   string  // lease / run / artifact
    Path   string  // 相对路径
    SHA256 string
    State  string  // present / absent
}
```

`Digest = sha256(encode(proposals))`，墙钟不参与——相同证据输入产生相同 digest。

### Apply 流程（M3 Guard 签名变更）

`reconcile.RepairApply` 在写事务内：

1. **重跑 `RepairDryRun`** 取得当前 `Plan.Digest`。
2. 用 caller 提供的 `--confirm` 覆盖 `Plan.Digest`（即 caller 的 digest 必须与当前 digest 严格相等，否则 `ErrDigestMismatch`）。
3. 对每个 proposal：
   - 写事务内 `tx.ReadForExpect(workitemRel(id))` 取当前字节
   - 构造 `TransitionRequest{TargetStatus: To, Confirmation: digest, AllowRepair: true, Guard: <evidence guard>}`
   - `workitem.ApplyRepair(ctx, id, req, raw)`
4. **`changeStatus` 内的 Guard** 是 M3 新签名：`func(*storage.Tx) ([]*domain.Event, error)`。`reconcile` 的证据 Guard 不返回事件（仅复审）；`applyRepair` 路径在 `changeStatus` 内 `req.Guard != nil` 但 guard 不产出事件（[internal/workitem/state.go:128-134](file://internal/workitem/state.go#L128-L134)）。

### 错误与退出码

- 摘要不符：`reconcile.ErrDigestMismatch` → CLI 升为 `CodePrecondition = 3`，错误提示 `run `devsys repair --dry-run` again`。
- Guard 证据漂移：`changeStatus` 内的 Guard 返回错误 → 整单回滚；摘要无意义——因为 digest 在事务内重算。
- 修复成功：返回 `RecoveryReport{Repaired: [...], Proposals: [...]}`。

## Guard 签名：M2 → M3 演化

| 路径 | M2 | M3 |
|---|---|---|
| `reconcile.RepairApply` Guard | `func() error` | `func(*storage.Tx) ([]*domain.Event, error)` |
| `approval.DecideTx` (reject 路径) 编排 | n/a | 通过 `workitem.Transition` 的 Guard 调 `DecideTx(rejected)`，返回 `approval_rejected` 事件 |
| `approval.ConsumeTx` (approve 路径) | n/a | 通过 `workitem.Transition` 的 Guard 调 `ConsumeTx`，返回 `approval_consumed` 事件 |

`changeStatus` 把 `status_changed` 事件、Guard 事件、失效事件、传播事件一并送入 `events.AppendBatchTx` 一次 append（[internal/workitem/state.go:165-182](file://internal/workitem/state.go#L165-L182)）。

## M3 决策与独立评审处置

[docs/开发记录.md](file://docs/开发记录.md) 记录的 M3Reviewer6 P1（离开后回到原状态旧批准仍可用）由 `approval.InvalidateForStatusTx` 在 `changeStatus` 的离开分支解决；M3Reviewer6 P1（拒绝处置与决定非原子）由 `rejectStageGate` 在 `workitem.Transition` 的 Guard 内同时完成 `DecideTx(rejected)` 与状态变更解决；M3Reviewer6 ③（消费 + 失效同文件触发 `staged twice`）由 `Tx.Staged(rel)` 在失效 pass 跳过已暂存路径解决。

## 调用契约示例

```sh
# 只读对账
bin/devsys.exe doctor                         # 待恢复事务 + 过期/孤儿租约 + 修复提议
bin/devsys.exe --json doctor                  # 完整 JSON

# 显式恢复（事务重放 + 释放过期/孤儿租约）
bin/devsys.exe recover --actor alice --reason "interrupted claim"

# 确认式修复：先推断、再确认、后重写
DIGEST=$(bin/devsys.exe --json repair --dry-run --actor alice --reason audit | jq -r .plan.digest)
bin/devsys.exe repair --apply --confirm "$DIGEST" --actor alice --reason audit
```
