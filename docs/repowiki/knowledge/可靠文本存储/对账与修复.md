# 对账与修复

本卡描述 `workloom doctor` / `recover` / `repair` 三条命令的内部实现、契约边界与 M3 起 `RepairApply` 的 Guard 签名变更（`func(*storage.Tx) ([]*domain.Event, error)`，事件并入提交批）。

## 职责分层

| 层 | 入口 | 物理动作 |
|---|---|---|
| `doctor` | `workloom doctor` / `internal/reconcile.Doctor` | 只读扫描（`storage.Inspect`），**不**创建锁文件、**不**触发事务恢复、**不**释放租约、**不**写盘 |
| `recover` | `workloom recover --actor … --reason …` | `storage.Recover`（确定性事务恢复）+ 释放过期/孤儿租约（写 `lease_recovered` 事件）；幂等 |
| `repair --dry-run` | `workloom repair --dry-run --actor … --reason …` | 收集 proposals + 计算确定性 `digest`（不含墙钟） |
| `repair --apply --confirm <digest>` | 同上 + `--confirm` | 重跑 `dry-run` → 比对 `digest` → `ApplyRepair` 在事务内用 Guard 重核证据 → 失败整单回滚 |

## `doctor`：只读对账

### 入口

`reconcile.Doctor(ctx, root, reconcile.Options{})` ([internal/reconcile/reconcile.go:175-236](file://internal/reconcile/reconcile.go#L175-L236))。CLI 层在 `workloom doctor` ([internal/cli/cli.go:1444-1486](file://internal/cli/cli.go#L1444-L1486)) 调用。

### 流程

1. `storage.InspectUnlocked` 列出 `.devsys/local/txn/` 目录与 `scheduling/` 目录，调用 callback 收集信息。
2. **不在 callback 内调 `storage.Read`**——这是只读路径的硬约束（[internal/reconcile/reconcile.go:1-20](file://internal/reconcile/reconcile.go#L1-L20)）。
3. 解析 lease YAML：通过 `reconcile_io.listSchedulingEntries` + 直接 `os.ReadFile` + `domain.DecodeYAML` 读取租约字节——但**只**在 `Inspect` 的 callback 闭包内调用，物理上等价于「共享锁下读」但不走 `storage.Read`。
4. 判定租约状态：
   - `LeaseUntil < now` → 过期租约
   - `WorkItemID` 不存在 → 孤儿租约
   - 不可读 YAML → 不可读租约
5. 收集 repair proposals（状态漂移：工作项 `Status` 与 `SchedulingState` 不一致）。
6. **M#337** 走 `readAllWorkitems` 扫 `.devsys/workitems/*.yaml`，对每条记录 `domain.DecodeYAML`；失败的文件记入 `InspectionReport.InvalidFiles` 并继续扫其余文件，由 `buildProposals` 把 invalid 列表一并返回（[internal/reconcile/reconcile.go:968-1000](file://internal/reconcile/reconcile.go#L968-L1000)、[internal/reconcile/reconcile.go:894-896](file://internal/reconcile/reconcile.go#L894-L896)）。
7. 缺锁文件 → `InspectionOK = false`，附 `InspectionNote`；有待恢复事务 → `InspectionOK = false`；**M#337** 当 `len(InvalidFiles) > 0` 时把 `Note` 追加 `one or more work item files are unreadable; the state cannot be fully trusted`（[internal/reconcile/reconcile.go:226-233](file://internal/reconcile/reconcile.go#L226-L233)）。

### 输出

```go
type InspectionReport struct {
    Root                string
    InspectionOK        bool
    Note                string
    PendingTransactions []storage.PendingTxn
    ExpiredLeases       []LeaseProbe
    OrphanLeases        []LeaseProbe
    UnreadableLeases    []LeaseProbe
    Proposals           []Proposal
    InvalidFiles        []InvalidFile  // M#337：解码失败的工作项文件，继续扫其余；exit 4 见本卡 §本批
}
```

### 退出码与行为边界
- `CodeInvalid = 4` 当 `InspectionReport.Proposals` 非空但 caller 是只读命令时**不**报错——doctor 是诊断工具，仅打印 proposals。
- 待恢复事务存在时 `InspectionReport.Orphans` 留空并附恢复提示（[internal/reconcile/reconcile.go:175-236](file://internal/reconcile/reconcile.go#L175-L236)）——不在不可信状态输出业务事实。
- `--json` 输出完整结构。
- **M#337**：`len(InvalidFiles) > 0` 时 doctor 仍**不**写盘、**不**报错为内部错，但 CLI 在 JSON / 人类两种模式下都 `exitWithCode(CodeInvalid = 4)`（[internal/cli/diagnostics.go:133-173](file://internal/cli/diagnostics.go#L133-L173)）——exit 4 语义在 doctor / repair / next / prime / project status 全链路一致（详见本卡 §本批）。

## `recover`：确定性恢复 + 释放过期租约

### 入口

`reconcile.Recover(ctx, root, opts)` ([internal/reconcile/reconcile.go:238-304](file://internal/reconcile/reconcile.go#L238-L304))。CLI 层 `workloom recover --actor … --reason …` ([internal/cli/cli.go:561-594](file://internal/cli/cli.go#L561-L594))，强制 `--actor` / `--reason`。

### 流程

1. `storage.Recover` 完成所有 `.devsys/local/txn/` 的事务重放（commit 前丢弃 / commit 后幂等重放）。
2. 释放过期租约：`workitem.Release`，写 `lease_recovered` 事件。
3. 释放孤儿租约（同上）。
4. 不可读租约**只报告不释放**——避免破坏未知语义的状态。
5. **引用缺失 workitem 的租约只报告不释放**——避免破坏 workitem 状态图。

v0.1.4（9aab68f，#342）起，过期 / 孤儿租约 proposal 的文案从「release with ForExpired=true / ForOrphan=true」改为「release with `workloom recover`」（[internal/reconcile/reconcile.go:876-885](file://internal/reconcile/reconcile.go#L876-L885)）——释放入口统一到 `workloom recover`，`Release` 缺 owner/token 的报错也指向同一命令。

### 幂等性

`workitem.Release` 是 `ExpectHash` 守卫；重复执行（`ErrConflict`）跳过——多次 recover 不会产生重复 `lease_recovered` 事件。

## `repair`：推断 → 确认 → 重写

### 入口

- `reconcile.RepairDryRun(ctx, root, opts)` ([internal/reconcile/reconcile.go:306-353](file://internal/reconcile/reconcile.go#L306-L353))：只读扫描，输出 `Plan{Proposals, Digest}`。
- `reconcile.RepairApply(ctx, root, plan, opts)` ([internal/reconcile/reconcile.go:505-660](file://internal/reconcile/reconcile.go#L505-L660))：在事务内用 Guard 重核证据后写盘。

### DryRun 输出

```go
type Plan struct {
    Proposals []Proposal
    Digest    string  // sha256-hex of proposals，不含墙钟
    Note      string  // 软失败（git 探针不可用等）
}

type Proposal struct {
    Kind       ProposalKind  // release_expired_lease / release_orphan_lease / mark_done_to_in_progress / note_unmerged_paths
    WorkItemID string
    From       string  // 推断的当前状态
    To         string  // 修复目标状态
    Evidence   []Evidence
}

type Evidence struct {
    Kind   string  // file / absent
    Path   string  // 相对路径
    SHA256 string
    State  string  // present / absent
    Note   string
}
```

`Digest = sha256(encode(proposals))`，墙钟不参与——相同证据输入产生相同 digest。

**M#337**：`RepairDryRun` 在 `buildProposals` 返回 `len(invalid) > 0` 时直接 `fmt.Errorf("cannot plan repairs: %s", strings.Join(names, "; "))` 拒绝，保持 fail-closed——在不可信树上构造的 plan 不可信（[internal/reconcile/reconcile.go:320-333](file://internal/reconcile/reconcile.go#L320-L333)）。错误信息列出全部无效文件，便于人工定位。`RepairApply` 永远不会在 `InvalidFiles` 路径上被调用。

### Apply 流程（M3 Guard 签名变更）

`reconcile.RepairApply` 在写事务内：

1. **重跑 `RepairDryRun`** 取得当前 `Plan.Digest`。
2. 用 caller 提供的 `--confirm` 覆盖 `Plan.Digest`（即 caller 的 digest 必须与当前 digest 严格相等，否则 `ErrDigestMismatch`）。
3. 对每个 proposal：
   - 写事务内 `tx.ReadForExpect(workitemRel(id))` 取当前字节
   - 构造 `TransitionRequest{TargetStatus: To, Confirmation: digest, AllowRepair: true, Guard: <evidence guard>}`
   - `workitem.ApplyRepair(ctx, id, req, raw)`
4. **`changeStatus` 内的 Guard** 是 M3 新签名：`func(*storage.Tx) ([]*domain.Event, error)`。`reconcile` 的证据 Guard 不返回事件（仅复审）；`applyRepair` 路径在 `changeStatus` 内 `req.Guard != nil` 但 guard 不产出事件（[internal/workitem/state.go:142-147](file://internal/workitem/state.go#L142-L147)）。

### 错误与退出码

- 摘要不符：`reconcile.ErrDigestMismatch` → CLI 升为 `CodePrecondition = 3`，错误提示 `run `workloom repair --dry-run` again`。
- Guard 证据漂移：`changeStatus` 内的 Guard 返回错误 → 整单回滚；摘要无意义——因为 digest 在事务内重算。
- 修复成功：返回 `RecoveryReport{Repaired: [...], Proposals: [...]}`。

## Guard 签名：M2 → M3 演化

| 路径 | M2 | M3 |
|---|---|---|
| `reconcile.RepairApply` Guard | `func() error` | `func(*storage.Tx) ([]*domain.Event, error)` |
| `approval.DecideTx` (reject 路径) 编排 | n/a | 通过 `workitem.Transition` 的 Guard 调 `DecideTx(rejected)`，返回 `approval_rejected` 事件 |
| `approval.ConsumeTx` (approve 路径) | n/a | 通过 `workitem.Transition` 的 Guard 调 `ConsumeTx`，返回 `approval_consumed` 事件 |

`changeStatus` 把 `status_changed` 事件、Guard 事件、失效事件、传播事件一并送入 `events.AppendBatchTx` 一次 append（[internal/workitem/state.go:167-190](file://internal/workitem/state.go#L167-L190)）。

## M3 决策与独立评审处置

M3 独立评审（M3Reviewer6）记录的三个问题已在当前代码中闭合：P1「离开后回到原状态旧批准仍可用」由 `approval.InvalidateForStatusTx` 在 `changeStatus` 的离开分支解决（回原状态后必须重新 `Request`）；P1「拒绝处置与决定非原子」由 `rejectStageGate` 在 `workitem.Transition` 的 Guard 内同时完成 `DecideTx(rejected)` 与状态变更解决；③「消费 + 失效同文件触发 `staged twice`」由 `Tx.Staged(rel)` 在失效 pass 跳过已暂存路径解决（原始评审依据见 git 历史中的 docs/开发记录.md）。

## 调用契约示例

```sh
# 只读对账
bin/workloom.exe doctor                         # 待恢复事务 + 过期/孤儿租约 + 修复提议
bin/workloom.exe --json doctor                  # 完整 JSON

# 显式恢复（事务重放 + 释放过期/孤儿租约）

# 确认式修复：先推断、再确认、后重写

bin/workloom.exe repair --apply --confirm "$DIGEST" --actor alice --reason audit
```

## M8.1 接力前的租约审计（被 `sync status` 复用）

`internal/syncstatus/syncstatus.go` 的 `Check` 是 `workloom sync status` 的只读探针（[internal/syncstatus/syncstatus.go:82-199](file://internal/syncstatus/syncstatus.go#L82-L199)），其租约分支**直接调用** `reconcile.LeaseAudit` 而不重写逻辑：

1. 先看 `storage.Diagnose` 的待恢复事务：`len(Pending) > 0` → `CodePendingTransactions` 阻塞器，并把 `st.LeasesDeferred = true` + `st.Note = "lease audit deferred: pending transactions make the lease snapshot partial"`（[internal/syncstatus/syncstatus.go:165-171](file://internal/syncstatus/syncstatus.go#L165-L171)）。理由：pending 的事务材料**可能**还要 apply，截一段租约快照会比「不报」更误导。
2. 无 pending 时按四态分流到 `st.Leases` 与 `Blockers`：
   - `lp.Owner == "<unreadable>"` → `CodeUnreadableLeases`（[internal/syncstatus/syncstatus.go:179-181](file://internal/syncstatus/syncstatus.go#L179-L181)）
   - `lp.ReasonKind == "orphan"` → `CodeOrphanLeases`（[internal/syncstatus/syncstatus.go:182-184](file://internal/syncstatus/syncstatus.go#L182-L184)）
   - `lp.Expired || lp.ReasonKind == "expired"` → `CodeExpiredLeases`（[internal/syncstatus/syncstatus.go:185-187](file://internal/syncstatus/syncstatus.go#L185-L187)）
   - 其它 → `CodeActiveLeases`（[internal/syncstatus/syncstatus.go:188-193](file://internal/syncstatus/syncstatus.go#L188-L193)）
3. `HandoffReady = len(Blockers) == 0`。

`sync status` 的出口约束是**只读**：不 fetch、不创建锁、不触发 recover、不写任何东西（[internal/syncstatus/syncstatus.go:1-9](file://internal/syncstatus/syncstatus.go#L1-L9)）；写入侧的修复仍走 `recover` / `repair --apply`。对账分叉不自动选赢家：sync status 只把分叉报成 blocker，由人/执行命令族（dispatch 阻塞见 `执行命令族`）决定下一步。

## M8.2 冲突人工项（`ProposalNoteUnmerged`）

`reconcile.RepairDryRun` 在原 proposals 之外追加 `conflictNotes` 探针（调用点 [internal/reconcile/reconcile.go:334-338](file://internal/reconcile/reconcile.go#L334-L338)，实现 [internal/reconcile/reconcile.go:355-392](file://internal/reconcile/reconcile.go#L355-L392)）。探针本身不破坏只读路径——与 `sync status` 共享底层 `internal/knowledge` 的 `PorcelainStatus` + `MergeHeads`（[internal/reconcile/reconcile.go:355-384](file://internal/reconcile/reconcile.go#L355-L384)）：

1. `knowledge.PorcelainStatus(root)` 读 porcelain v1 的 unmerged 项；`knowledge.MergeHeads(root)` 读 `MERGE_HEAD` 等合并机械残留。
2. 任一调用失败 → `conflictNotes` 返回 `(nil, "git conflict probe unavailable: ...")`；`RepairDryRun` 把这条 message 接续到 `plan.Note`（[internal/reconcile/reconcile.go:334-338](file://internal/reconcile/reconcile.go#L334-L338)）——**不会**让 `RepairDryRun` 自身报错；测试环境常见于非 git checkout。
3. 成功时每条 unmerged 路径 / 每个 merge head 合成一条 `Proposal`：`Kind = ProposalNoteUnmerged`（[internal/reconcile/reconcile.go:49](file://internal/reconcile/reconcile.go#L49)）、`Note = "human-only"`、`Evidence = [{Kind: EvidenceAbsent, Path: "git:<path>", Note: "human resolution required"}]`。
4. sort by `Description` 稳定输出（[internal/reconcile/reconcile.go:387-389](file://internal/reconcile/reconcile.go#L387-L389)）。

形态特征（**只描述 proposal，不写 tick 流程**）：

- `Kind` 是独立枚举值 `ProposalNoteUnmerged = "note_unmerged_paths"`（[internal/reconcile/reconcile.go:45-49](file://internal/reconcile/reconcile.go#L45-L49)）；冲突路径在 working tree 中、不在 storage-managed 树内，故 `Evidence` 只能给 `Kind: EvidenceAbsent`、`Path: "git:" + path`，**不**携带 SHA256。
- `Note: "human-only"` 是显式语义标签，让后续 apply 与 dispatch（执行命令族）据此阻塞。
- description 形如 `unmerged path <path>: resolve with git (keep both sides explicit), then \`workloom repair --dry-run\`` 或 `unfinished merge machinery <name>: finish or abort the merge with git first`。

### Apply 全 rejected（零写）

`RepairApply` 在循环里第一个分支就是 `ProposalNoteUnmerged`（[internal/reconcile/reconcile.go:529-541](file://internal/reconcile/reconcile.go#L529-L541)）：把 `Evidence[0].Path` 去掉 `git:` 前缀得到人类可读路径，加 `: requires human resolution; no automatic merge` 推到 `rep.Rejected`，`continue`。**没有** `tx.Put*`、**没有** 走 `Guard`、**没有** 走 `ApplyRepair`——这是硬约束：workloom 不自动合并、不写侧车、不按时间戳选赢家。`digest` 必须包含这些 proposal 才能让 apply 进入循环，但循环本身把它们从写路径里完全跳过；dispatch 端的合并冲突门控见 `执行命令族`。

### Digest 第三键

`ComputeDigest` 把每个 proposal 序列化为 `P|Kind|WorkItemID|RunID|From|To|Description|` + 逐条 `E|Kind|Path|SHA256|Note|`（[internal/reconcile/reconcile.go:447-464](file://internal/reconcile/reconcile.go#L447-L464)），`canonicalProposals` 的排序键是 `(Kind, WorkItemID, firstEvidence.Path)`——第三键 `firstEvidence.Path` 只为 disambiguate 当前单条 evidence 的 `note_unmerged_paths`（[internal/reconcile/reconcile.go:466-493](file://internal/reconcile/reconcile.go#L466-L493)）；未来若有多 evidence 且首路径相同的 kind，需要再加第四键。注释原话："every current kind emits at most one proposal per (kind, workitem) with its own path. A future multi-evidence kind sharing one first path needs a fourth key."

## 本批（M#337，commit 362b637）

M#337 把「不可读的工作项文件」作为一类新的失败可见信号加入 Doctor / RepairDryRun 的契约，并把 CLI / next / prime / project status 收敛到统一的 `exit 4` 语义：

### `InvalidFile` 与 `InspectionReport.InvalidFiles`

`internal/reconcile/reconcile.go` 新增类型：

```go
type InvalidFile struct {
    Path string `json:"path" yaml:"path"`
    Err  string `json:"error" yaml:"error"`
}

func (f InvalidFile) String() string { return f.Path + ": " + f.Err }
```

`InspectionReport` 增字段 `InvalidFiles []InvalidFile`（json/yaml tag `invalid_files,omitempty`）——紧贴 `UnreadableLeases` 之后（[internal/reconcile/reconcile.go:90-115](file://internal/reconcile/reconcile.go#L90-L115)）。它和 `UnreadableLeases`（租约 YAML 解码失败）的区别：`UnreadableLeases` 是「调度侧的某条 lease 不可信」，`InvalidFiles` 是「领域工作项文件的某条记录不可信」——前者由 `walkScheduling` 报告，后者由 `readAllWorkitems` 报告。

### `readAllWorkitems` 与 `buildProposals`：解码失败继续扫

`readAllWorkitems`（[internal/reconcile/reconcile.go:968-1000](file://internal/reconcile/reconcile.go#L968-L1000)）走 `storage.Inspect` 列 `.devsys/workitems/*.yaml`，对每条记录 `domain.DecodeYAML`：成功 → 追加到 `items`；失败 → `invalid = append(invalid, InvalidFile{Path: rel, Err: derr.Error()})` 并 `continue`——一个坏文件不掩盖其余工作项。`buildProposals` 在调用 `readAllWorkitems` 后把 `invalidFiles` 合并进自己的 `invalid` 返回值（[internal/reconcile/reconcile.go:894-896](file://internal/reconcile/reconcile.go#L894-L896)）。

### `Doctor`：填充 + Note

`Doctor` 末尾（[internal/reconcile/reconcile.go:226-233](file://internal/reconcile/reconcile.go#L226-L233)）：

```text
proposals, invalid, err := buildProposals(ctx, st, now(), probes)
if err != nil { return rep, err }
if len(invalid) > 0 {
    rep.Note = strings.TrimSpace(rep.Note + "; " + "one or more work item files are unreadable; the state cannot be fully trusted")
}
rep.Orphans = proposals
rep.InvalidFiles = invalid
```

——Doctor 自身**不**报错，InvalidFiles 只是把证据不可信的信号带在 report 里。

### `RepairDryRun`：fail-closed

`RepairDryRun` 在 `buildProposals` 之后、`conflictNotes` 之前（[internal/reconcile/reconcile.go:320-333](file://internal/reconcile/reconcile.go#L320-L333)）：

```text
proposals, invalid, err := buildProposals(ctx, st, now(), probes)
if err != nil { return plan, err }
if len(invalid) > 0 {
    names := make([]string, 0, len(invalid))
    for _, f := range invalid {
        names = append(names, f.String())
    }
    return plan, fmt.Errorf("cannot plan repairs: %s", strings.Join(names, "; "))
}
```

——在不可信树上构造的 plan 不可信；`RepairDryRun` 直接 `error` 拒绝。这是与 git 冲突 `ProposalNoteUnmerged`（M8.2）路径的对比：后者走 dry-run + apply 流程，apply 全 rejected；`InvalidFiles` 在 dry-run 就 fail-closed，因为没有任何 proposal 可以基于不完整的树构造。

### CLI / next / project status 的 exit 4 收敛

- `internal/cli/diagnostics.go:runDoctor` 在人类模式打 `INVALID  <path>  <err>` 行（[internal/cli/diagnostics.go:157-159](file://internal/cli/diagnostics.go#L157-L159)）；`--json` 编码完整 report 后若 `len(InvalidFiles) > 0` 同样 `exitWithCode(CodeInvalid)`（[internal/cli/diagnostics.go:133-136](file://internal/cli/diagnostics.go#L133-L136)），人类模式末尾同样 `exitWithCode(CodeInvalid)`（[internal/cli/diagnostics.go:172-174](file://internal/cli/diagnostics.go#L172-L174)）。`INVALID` 行是 CLI 侧的诊断输出，与「reconcile 是否写盘」无关。

- 健康项目仍然 `InspectionOK = true`、`len(InvalidFiles) == 0`，doctor 退出 0，next / project status 给出正常推荐。
