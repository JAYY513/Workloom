# 状态机与调度

本卡描述工作项的**九状态机、保守转换矩阵、调度态分离、文件级领取/心跳/释放/重试**，以及 M3 起 `TransitionRequest.Guard`（事务内复审证据）、`workflow_instance.go` 五类实例操作（只动 `workflow` 字段，租约 fencing）。M3 曾有的 `propagateRecordsTx`（完成事务内把决策/发现记录引用广播到父与直接兄弟）**已在本批删除**，见 [「记录传播已移除」](#记录传播已移除)。

## 状态机

工作项九状态由 [internal/domain/state.go](file://internal/domain/state.go) 定义：

| 状态 | 含义 |
|---|---|
| `draft` | 起草，初始状态 |
| `backlog` | 待规划池 |
| `ready` | 可领取 |
| `in_progress` | 已被领取且有活跃租约 |
| `review` | 实施完成等待审阅 |
| `verification` | 审阅完成等待验证 |
| `done` | 已完成（终态） |
| `blocked` | 阻塞（保留 `PreviousStatus` 以便恢复） |
| `cancelled` | 已取消（终态） |

`done` 与 `cancelled` 是终态，**不可再转换**（除 `ApplyRepair` 路径）。

### 转换矩阵

由 `domain.IsTransitionLegal(from, to)` 判定（[internal/domain/state.go](file://internal/domain/state.go)），`domain.AllowedFrom(from)` 给出所有合法下一步。完整矩阵：

| from \ to | draft | backlog | ready | in_progress | review | verification | done | blocked | cancelled |
|---|---|---|---|---|---|---|---|---|---|
| draft | — | ✓ | ✓ | — | — | — | — | ✓ | ✓ |
| backlog | ✓ | — | ✓ | — | — | — | — | ✓ | ✓ |
| ready | ✓ | ✓ | — | ✓ | — | — | — | ✓ | ✓ |
| in_progress | — | — | — | — | ✓ | — | — | ✓ | ✓ |
| review | — | — | ✓ | ✓ | — | ✓ | — | ✓ | ✓ |
| verification | — | — | — | — | ✓ | — | ✓ | ✓ | ✓ |
| done | — | — | — | — | — | — | — | — | — |
| blocked | ✓ ① | ✓ ① | ✓ ① | — | — | — | — | ✓ | ✓ |
| cancelled | — | — | — | — | — | — | — | — | — |

① 仅在 `blocked.PreviousStatus` 等于目标状态时合法（[internal/workitem/state.go:96-98](file://internal/workitem/state.go#L96-L98)）。其余 `blocked` 仅可转 `cancelled` 或保持 `blocked`。

`ApplyRepair` 的合法转换走 `legalRepairTransition`（[internal/workitem/state.go:206-217](file://internal/workitem/state.go#L206-L217)），比 `Transition` 更宽松；调用方必须提供 `Confirmation` digest 与 `Guard`，两者缺一即拒绝（[internal/workitem/state.go:58-61](file://internal/workitem/state.go#L58-L61)）。

## 调度态与业务状态分离

工作项的两套字段必须**始终一致**：

| 业务状态 | `SchedulingState` |
|---|---|
| `draft` / `backlog` / `ready` | `SchedulingUnclaimed` |
| `in_progress` | `SchedulingClaimed`（必须有租约文件 `.devsys/scheduling/<id>.yaml`） |
| `review` / `verification` / `done` / `cancelled` | `SchedulingReleased`（租约必须已释放） |

`changeStatus` 写入新状态前会自动设置 `SchedulingState`（[internal/workitem/state.go:172-177](file://internal/workitem/state.go#L172-L177)）；离开 `in_progress` 时若租约仍活跃 → `ErrAlreadyClaimed: release claim before advancing status`（[internal/workitem/state.go:165-171](file://internal/workitem/state.go#L165-L171)），必须先 `Release` 或 `Heartbeat` 续约。d726ed4 起租约 fencing 失败细节升级为「`workitem <id> is leased by "<owner>" (run <run-id>); release the claim before leaving execution: workloom workitem release --id <id> --owner <owner> --token <token from .devsys/local/leases/<id>.token> --actor <actor> --reason <reason>`」——`transition` 没有 `--token` 标记，提示明确指向释放路径，token 从本机侧车 `local/leases/<id>.token` 取（[internal/workitem/state.go:119-137](file://internal/workitem/state.go#L119-L137)）。

## 状态机写路径：单一 `changeStatus`

**所有状态变更**都走 `workitem.changeStatus`（[internal/workitem/state.go:66-195](file://internal/workitem/state.go#L66-L195)）。它是 M2 起既有的唯一入口，M3 在事务内额外承担 Guard、审批失效两件事（M3 曾有的第三件事「记录传播」已在本批删除）。

事务流程（一次 `storage.Write`）：

```mermaid
flowchart TD
    A[changeStatus 取独占锁] --> B[tx.ReadForExpect 取原字节]
    B --> C[DecodeYAML 解码到 wi]
    C --> D[legalTransition 校验 from→to]
    D --> E{存在租约?}
    E -- 是 --> F[租约 fencing: Token/Owner/RunID/LeaseUntil]
    E -- 否 --> G{req.Token != ""?}
    G -- 是 --> H[ErrLeaseTokenMismatch]
    G -- 否 --> I[Guard 在事务内复审证据]
    F --> I
    I --> J[approval.InvalidateForStatusTx 失效同源审批]
    J --> K[wi.Status 改写 + SchedulingState 同步]
    K --> L[构造 status_changed 事件]
    L --> O[events.AppendBatchTx 一次 append]
```

任何步骤失败都回滚整个事务；状态字段由 `changeStatus` 改写，`Update` 拒绝状态变更（[internal/workitem/workitem.go:173-227](file://internal/workitem/workitem.go#L173-L227)）。

### M3 Guard：事务内复审证据

`TransitionRequest` 新增 `Guard func(*storage.Tx) ([]*domain.Event, error)`（[internal/workitem/state.go:23-34](file://internal/workitem/state.go#L23-L34)）。Guard 在事务内、状态字段改写**之前**被调用：

- 典型用法：`approval.ConsumeTx` 在 Guard 内把门禁所依赖的审批标记为 consumed，返回 `approval_consumed` 事件。
- `ApplyRepair` 的 Guard 走 `reconcile.RepairApply` 的证据复核路径，不返回事件。

Guard 返回的事件与 `status_changed` / 失效事件**一起**送入 `events.AppendBatchTx`（[internal/workitem/state.go:187-189](file://internal/workitem/state.go#L187-L189)），保证状态、Guard、失效三类事件在同事务内一次 append（本批起不再有第四类传播事件）。

`Transition`（非 repair）也支持 Guard；`ApplyRepair` 强制 `Guard != nil` 且 `len(Confirmation) > 0`（[internal/workitem/state.go:58-61](file://internal/workitem/state.go#L58-L61)）。

### M3 审批失效：离开阶段即作废

离开 `from` 状态时，`changeStatus` 调用 `approval.InvalidateForStatusTx(tx, devsysDir, id, from, now, reason)`（[internal/workitem/state.go:151-157](file://internal/workitem/state.go#L151-L157)）：

- 仅作用域内同 `WorkItemID` 且 `RequestedStatus == from` 的审批会被处理。
- 已 consumed 或已 invalidated 的审批跳过。
- 通过 `tx.Staged(rel)` 跳过本事务已暂存的文件——防止消费后被失效 pass 二次写违反 `staged twice`。
- 每条失效审批写一份 `approval_invalidated` 事件，事件 join 提交批。

这是 M3Reviewer6 P1「离开后回到原状态旧批准仍可用」的修：回原状态后必须重新 `Request`。

## 租约：文件级 token fencing

### 文件与字段

`.devsys/scheduling/<workitem-id>.yaml`，ID 与工作项 ID 同形。结构由 `domain.SchedulingLease` 定义：

```yaml
schema_version: 1
workitem_id: WLM-1
owner: alice
claimed_at: 2026-09-18T12:00:00Z
lease_until: 2026-09-18T13:00:00Z
run_id: run-20260918-1
head_sha: …
agent_id: …
agent_harness: …
```

**#342（v0.1.4，9aab68f）起持久化文件不携带 token**：`token` 字段仍留在 `domain.SchedulingLease` 结构里（解码旧树兼容），但 `Claim` 写租约时不再填充它——token 由 `crypto/rand` 生成 32 字符 hex（16 字节随机，128 bit，[internal/workitem/claim.go:1043-1050](file://internal/workitem/claim.go#L1043-L1050)），经 `ClaimResult.Token` 交给领取方，同时以**本地侧车** `local/leases/<id>.token` 写在同一事务内（`local/` 已被 `.gitignore` 与 `search` 排除，[internal/workitem/lease_token.go:13-28](file://internal/workitem/lease_token.go#L13-L28)）。租约文件保留 `owner / claimed_at / lease_until / run_id` 等元数据随 git 可见，用于跨设备漂移检测；`Heartbeat` / `Release` / `workflowWrite` 经 `tokenFromTx` 对照侧车校验 presented token，侧车缺失时回落 persisted 值，旧树在 claim 轮换前保持可校验（[internal/workitem/lease_token.go:31-49](file://internal/workitem/lease_token.go#L31-L49)）。`Store.LeaseToken(ctx, id)` 供本地操作者（dispatch tick、`workloom recover`）在不持有 token 时读取当前 token（[internal/workitem/lease_token.go:78-100](file://internal/workitem/lease_token.go#L78-L100)）。没有续签秘密、过期由 `doctor` 报告、`recover` 释放。

### 领取（`workitem.Claim`）

[internal/workitem/claim.go:199-355](file://internal/workitem/claim.go#L199-L355) 在**一个** `storage.Write` 独占事务里写齐四件事：

1. `run.CreateTx` 写入 `runs/run-<YYYYMMDD>-<N>.yaml`。
2. `leaseRel` 用 `ExpectAbsent` 创建租约文件（恰好一个胜者，输方拿 `ErrAlreadyClaimed`）。
3. `workitemRel` 用 `ExpectHash` 写 `status=in_progress, scheduling_state=claimed, lease_owner, lease_claimed_at, lease_until`（#342 起不写 `lease_token`）。
4. `stageToken(tx, id, token)` 写本地侧车 + `events.AppendTx(tx, ev)` 追加一条 `claimed` 事件。

并发争抢：租约文件 `ExpectAbsent` 让恰好一方胜出；输方拿到 `ErrAlreadyClaimed`（[internal/workitem/claim.go:331-334](file://internal/workitem/claim.go#L331-L334)）。若输方发现的租约**仍然活跃**，报错会附带释放提示，指引 `workloom workitem release`（[internal/workitem/claim.go:234-236](file://internal/workitem/claim.go#L234-L236)）。

`Heartbeat` / `Release` / `UpdateClaimed` / `FenceRunUpdate` 复用同一锁内事务，但要求调用方持有当前 `Owner + Token + RunID`（与 `--expect` 类似但针对租约；token 以侧车为准）。

### 心跳 / 释放 / 重试

- `Heartbeat` 续约 `lease_until` 与 `heartbeat_at`；要求 `Token/Owner` 匹配（经侧车校验）且 `now < lease_until`。
- `Release` 删除租约文件、删除侧车（`dropToken`），并把工作项调度态回到 `released`（要求 `Token/Owner` 匹配，经侧车校验；[internal/workitem/claim.go:456-628](file://internal/workitem/claim.go#L456-L628)）。缺 owner/token 时报错并指明「expired or orphaned leases are recovered with `workloom recover` instead」（[internal/workitem/claim.go:499-502](file://internal/workitem/claim.go#L499-L502)）。
- `ReleaseOptions` 的恢复路径 `ForExpired=true`（要求已验证 `lease_until < now`）与 `ForOrphan=true`（要求绑定 run 文件缺失）**绕过 owner/token**，由 `workloom recover` 使用；#342 起新增 run-bound 释放 `ForCompleted=true`（要求租约属于已 `succeeded` 的绑定 run）与 `ForRefused=true`（要求绑定 run 带有记录的拒绝 `Verification.Advanced=false`），以 run 记录为证明、不要求 owner/token，也不会误杀更新的 claim（[internal/workitem/claim.go:99-118](file://internal/workitem/claim.go#L99-L118)）。
- `QueueRetry` 把工作项转 `blocked`（保留 `PreviousStatus`）并释放租约；恢复时从 `PreviousStatus` 回到原状态。
- `doctor` 通过 `storage.Inspect` 报告过期/孤儿租约；`recover` 在写事务内调用 `storage.Recover` + `workitem.Release` 释放并写 `lease_recovered` 事件；`repair` 不处理租约（`lease_recovered` 是显式恢复路径的事件）。

### 条件求值

`transitions[].when` 是声明式条件（[internal/workflow/condition.go](file://internal/workflow/condition.go)），`<field> <op> <literal>` 形态：

- 操作符：`==` `!=` `<` `>` `in` `exists`
- 白名单字段（`factWhitelist`）：`workitem.id` / `workitem.status` / `workitem.type` / `workitem.priority` / `workitem.clarification_needed` / `workitem.approval_required` / `workitem.parent_id`
- 类型规则：`<` `>` 仅 int；`in` 仅 string；`exists` 仅 `workitem.parent_id`
- 字符串字面量支持单/双引号包裹；`in` 字面量列表支持逗号后空格、去重、拒绝空成员
- 不支持复合表达式（`&&` / `||` / `()`）；未知字段/操作符/类型不匹配在**加载期**报错（`workflow.Parse`）

## 策略推荐 Recommend

本批新增。以下是 `workflow.Recommend` 的完整口径。

`internal/workflow/recommend.go`（88 行，本批新增）是**确定性**策略推荐：给定一个工作项 + 项目 `default_policy` 字符串，返回一个 `Recommendation`。它**不调模型、不生成策略数据、不写盘**——纯函数、纯规则、无 I/O。

### 返回类型与常量

[internal/workflow/recommend.go:9-28](file://internal/workflow/recommend.go#L9-L28)：

```go
const (
    ConfidenceHigh   = "high"
    ConfidenceMedium = "medium"
    ConfidenceLow    = "low"

    RecommendationSourceRule     = "rule"
    RecommendationSourceDefault  = "default"
)

type Recommendation struct {
    PolicyID       string   `json:"policy_id"`
    Confidence     string   `json:"confidence"`
    Signals        []string `json:"signals,omitempty"`
    Reasons        []string `json:"reasons,omitempty"`

```

`ConfidenceMedium` 已声明但**当前无任何返回路径使用**——实际只会产出 `High`（前四条规则）与 `Low`（兜底）。写这条时以源码为准。

### 入口与决策顺序

`Recommend(wi *domain.WorkItem, defaultPolicy string) Recommendation`（[internal/workflow/recommend.go:30-70](file://internal/workflow/recommend.go#L30-L70)）自上而下短路，**第一条命中即返回**：

| # | 条件 | `PolicyID` | `Confidence` | `Source` | 附加 |
| --- | --- | --- | --- | --- | --- |
| 1 | `wi == nil` | `defaultPolicy` | `Low` | `Default` | 无 reasons |
| 2 | `wi.Workflow != nil && Workflow.ID != ""` | `wi.Workflow.ID` | `High` | `Explicit` | reason：已声明实例 |
| 3 | `architectureSignal` | `architecture-change` | `High` | `Rule` | signal `architecture_or_boundary_change` |
| 4 | `wi.Type == "feature"` | `feature-development` | `High` | `Rule` | signal `workitem.type=feature` |
| 5 | `quickFixType(wi.Type)` | `quick-fix` | `High` | `Rule` | signal `workitem.type=<kind>` |
| 6 | 兜底 | `intake` | `Low` | `Default` | `RequiresTriage=true`；`LegacyDefault = (defaultPolicy=="quick-fix")` |

两个信号函数（[internal/workflow/recommend.go:72-88](file://internal/workflow/recommend.go#L72-L88)）：

- `architectureSignal(kind, text)`：先在 `标题 + 描述 + 验收标准` 拼接后小写文本里找 9 个词（`architecture` / `architectural` / `protocol` / `data model` / `database schema` / `migration` / `module boundary` / `cross-module` / `api contract`）；再退到 `Type` 白名单（`architecture` / `architectural-change` / `protocol` / `data-model`）。
- `quickFixType(kind)`：`Type` 白名单 `bug` / `chore` / `docs` / `documentation` / `config` / `configuration` / `maintenance`。

⚠️ 返回的 `PolicyID` 是**硬编码字面量**（`architecture-change` / `feature-development` / `quick-fix` / `intake`），不读候选策略集——策略 ID 拼错时消费方拿到的就是一个解析不出文件的 ID。
