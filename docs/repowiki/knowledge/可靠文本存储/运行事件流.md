# 运行事件流

`.devsys/runs/<run-id>.jsonl` 是 M6 引入的 **attempt 事件流**：每个 attempt round 在 spawn / 终止 / 各阶段写一条 JSONL 记录；`app.Service` 与 `internal/harness.Session` 共同维护这条流，agent 与 reviewer 都从这里读证据。本卡描述它的物理布局、字段表、sync 策略、断尾重建与 M6 新增的阶段事件。

## 物理布局

```text
.devsys/
  runs/
    <run-id>.jsonl              # 一条 attempt 一次 attempt round（多条 run 共用一个文件）
    <run-id>.jsonl.torn         # 写过程中崩溃留下的断尾，由 openRunStream 重建
```

- **路径**：`logRelFor(runID) = .devsys/runs/<run-id>.jsonl`（[internal/app/runexec.go:695-697](file://internal/app/runexec.go#L695-L697)）。
- **格式**：JSONL（一行一条 record），UTF-8，LF 行尾（仓库统一）。
- **追加语义**：`runStream.write` 调 `storage.AppendJSONLRaw` 在事务内追加；事务回滚则该记录消失。
- **断尾**：`openRunStream` 在打开时检测 `*_torn` 副本（写过程中崩溃留下的不完整行），把完整记录复制到主文件并截断。

## 字段表（[internal/app/runstream.go:24-51](file://internal/app/runstream.go#L24-L51)）

```go
type streamRecord struct {
    Time       time.Time  `json:"t"`              // RFC3339Nano
    Type       string     `json:"type"`           // 见下文事件类型表
    Stream     string     `json:"stream,omitempty"`         // "stdout" | "stderr"
    Line       string     `json:"line,omitempty"`           // 一行（无终止符）
    Adapter    string     `json:"adapter,omitempty"`        // harness 名（"codex" / "shell" / …）
    Command    string     `json:"command,omitempty"`        // argv 的人类可读渲染
    Argv       []string   `json:"argv,omitempty"`           // 结构化 argv
    Cwd        string     `json:"cwd,omitempty"`            // 工作目录（worktree 路径）
    TimeoutMS  int64      `json:"timeout_ms,omitempty"`
    Code       *int       `json:"code,omitempty"`           // 退出码；-1 = killed / never started
    TimedOut   bool       `json:"timed_out,omitempty"`
    Canceled   bool       `json:"canceled,omitempty"`
    DurationMS int64      `json:"duration_ms,omitempty"`
    Text       string     `json:"text,omitempty"`           // 控制记录的人类可读文本
    Removed    int64      `json:"removed_bytes,omitempty"`  // 断尾重建时删掉的字节数
    Round      int        `json:"n,omitempty"`              // round 序号（1-based）
    Mode       string     `json:"mode,omitempty"`           // "first" | "continuation"
    PromptHash string     `json:"prompt_hash,omitempty"`   // sha256(prompt.Text)
    PromptFile string     `json:"prompt_file,omitempty"`   // .devsys/local/runs/<id>/round-<N>.md
    Refs       []string   `json:"refs,omitempty"`           // input_context_refs 指针
    Phase      string     `json:"phase,omitempty"`          // M6 阶段标识
    Status     string     `json:"status,omitempty"`         // run.status
    DueAt      *time.Time `json:"continuation_due_at,omitempty"` // 干净轮次写
}
```

`omitempty` 保持每条 record 小；MCP 客户端读取时 `nil` 字段省略。

## 事件类型表

| `type` | 写入点 | 字段子集 | 用途 |
|---|---|---|---|
| `line` | `runStream.write` per line | `t, stream, line` | 来自 harness 的每行输出 |
| `record_exec_phase` | `advancePhase(stream, runID, phase)` | `t, phase, text` | §4.8 阶段：`workspace_prepared` / `prompt_assembled` / `run_started` / `run_stopped` |
| `run_exec_started` | `recordAgent + markRunning` 后 | `t, adapter, command, argv, cwd, timeout_ms` | attempt 启动记录 |
| `run_finished` | `finishAttempt` / `recordExecOutcome` | `t, code, timed_out, canceled, duration_ms, status, summary, note` | attempt 终态 |
| `record_prompt` | `RunPrompt.writePromptFile` 后 | `t, n, mode, prompt_hash, prompt_file, refs` | 提示词已写入 |
| `review_routed` | `refuseCompletion` | `t, run_id, reason` | verify 拒绝，workitem 进 review |
| `review_accepted` | `RunFinish --force --by` | `t, run_id, by, force` | reviewer 接受 verify 拒绝 |

`record_prompt` / `review_routed` / `review_accepted` 是 M6 新增；M3 的 `status_changed` / `repair_applied` / `lease_recovered` 等通用事件仍在 `.devsys/events/<month>.jsonl`。

v0.1.5（fffbff9，#345 N1）起 `refuseCompletion` / `routeToReview` 回报工作项**是否真的进入 review**：阶段门未满足时工作项留在 `in_progress`，报错文案改为「did not enter review (its review gate is unmet — add a comment first: `workloom workitem comment …`)」并给补救命令，不再谎称「in review」；run 保持非终态，供 reviewer 看完证据后 `--force --by` 接受。

## Sync 策略（[internal/app/runexec.go:788-809](file://internal/app/runexec.go#L788-L809)）

```text
runStream.write(rec, sync)
  ↓
encoder.Encode(rec)            # 单行 JSON
buffer.Write(line)
  ↓
if sync || rec.Type == "record_exec_phase" || lineCount % syncEvery == 0:
    appendJSONL + f.Sync()      # 强制 fsync 落盘
```

- `syncEvery = 128`：每 128 行 + 控制记录 + 末次 flush——crash 至多丢 127 行。
- `Close()` 调一次强制 flush。
- `torn` 文件在 `openRunStream` 重建时记录 `removed_bytes`——reviewer 可看到断尾重建的代价。

## 断尾重建（[internal/app/runexec.go:758-784](file://internal/app/runexec.go#L758-L784)）

```text
openRunStream(root, runID)
  ↓
检查 main 文件末尾是否能解析为完整 record
  ↓
不能 → 找到 torn 副本（如果存在）
  ↓
解析 torn 的最后完整行（直到第一个解析失败）→ 写回 main → 删 torn
  ↓
write recordExecPhase {phase: "stream_repaired", removed_bytes: ...}
```

保证：reader 看到的 stream 永远从第一行开始完整；torn 永远不被读侧信任。

## 推断助手（[internal/app/runstream.go:116-155](file://internal/app/runstream.go#L116-L155)）

| 函数 | 返回 | 用途 |
|---|---|---|
| `nextRound(lines) int` | `max(Round) + 1`，空 stream = 1 | `RunExec` 不显式传 `--round` 时按当前最大 round + 1 继续 |
| `lastRound(lines) (streamRecord, bool)` | 最新 round record（任意 type） | `RunPrompt` 默认 `--round` 推断 |
| `lastExit(lines) (streamRecord, bool)` | 最新 `run_finished` record | `RunExec` 续轮时若上一轮 succeeded → 短延迟续轮；否则按 retry 重排 |

`RunExec` 在 `req.Round == 0` 时调 `nextRound` 推断——这是 M6.3 续 session 的实现边界。

## 阶段事件与 §4.8 对应

| §4.8 phase | streamRecord.Phase | 触发点 |
|---|---|---|
| workspace prepared | `workspace_prepared` | `app.RunExec` 启动前 `WorkspacePrepare` 成功 |
| prompt assembled | `prompt_assembled` | `prompt.Assemble` 完成 + 写 `.devsys/local/...` |
| run started | `run_started` | `harness.Session.Start` 成功；同一 record 携带 `run_exec_started` 类型 |
| run stopped | `run_stopped` | `Session.Stop(ctx)` 触发（Ctrl-C / timeout） |
| run finished | `run_finished` | `finishAttempt` 写终态 |

`recordedPhases` 返回这五个值的子集；缺一个阶段意味着 attempt 在该点前中断——reviewer 可借此定位失败位置。

## M8.3 归档（`internal/archive`）

M8.3 把 JSONL 流——`.devsys/events/<YYYY-MM>.jsonl` 与 `.devsys/runs/<run-id>.jsonl`——保守地搬到 `.devsys/archive/`，只归档、不删除。

### 归档布局

`internal/archive` 的 managed rels（[internal/archive/archive.go:37-44](file://internal/archive/archive.go#L37-L44)）：

```text
.devsys/archive/
  manifest.yaml            # 归档清单（CAS 守卫）
  events/<YYYY-MM>.jsonl   # 归档事件分片
  runs/<run-id>.jsonl      # 归档 run 流
```

入口是 `archive.Apply(ctx, root, Spec)`（[internal/archive/archive.go:201-360](file://internal/archive/archive.go#L201-L360)），`Spec.BeforeMonth` 触发 `PlanEvents` 选 `< beforeMonth` 的 live 分片，`Spec.RunIDs` 触发 `PlanRuns` 校验每个 run 已终态。两类源共享同一前缀：`eventsPrefix = "archive/events/"`、`runsPrefix = "archive/runs/"`、`liveEvents = "events/"`、`liveRuns = "runs/"`（[internal/archive/archive.go:38-44](file://internal/archive/archive.go#L38-L44)）。

### Plan：终态门

- `PlanEvents`（[internal/archive/archive.go:117-144](file://internal/archive/archive.go#L117-L144)）只列出 `month < beforeMonth` 且 `.jsonl` 后缀的分片；`storage.Open` 校验项目存在；目录不存在视为零结果。
- `PlanRuns`（[internal/archive/archive.go:149-190](file://internal/archive/archive.go#L149-L190)）逐 ID 校验：`run.ValidID` → `st.Read` 读 live yaml → `isTerminal` 判定 `succeeded/failed/timed_out/stalled/canceled`。**非终态 run 直接拒绝归档**——归档运行中流会破坏 `nextRound` / `lastExit` 推断与 dispatch stall sweep（[internal/archive/archive.go:146-149](file://internal/archive/archive.go#L146-L149)）。

### Apply：单事务 + manifest CAS

整个归档是一次 `st.Write`（[internal/archive/archive.go:308-349](file://internal/archive/archive.go#L308-L349)）：

1. **事务内重读 + hash 一致**：每个 staged 文件先 `tx.ReadForExpect(f.src)` 再 `sha256Hex(cur) != sha256Hex(f.data)` 校验，杜绝 Apply 与探测之间被改动（[internal/archive/archive.go:310-319](file://internal/archive/archive.go#L310-L319)）；不一致 → `archive: %s changed during apply`。
2. **同事务写新位 + 删旧位**：`tx.Put(f.dst, f.data, storage.ExpectAbsent())` 写 archive，`tx.Delete(f.src, storage.ExpectHash(HashBytes(f.data)))` 删 live——`ExpectAbsent` 防止二次归档同分片，`ExpectHash` 把归档与删除绑定到原 hash。
3. **manifest 读写都在事务内**：`tx.ReadForExpect(manifestRel)` → 不存在则 `ExpectAbsent`、存在则解码 + `ExpectHash` 守卫 → `man.Entries = append(...)` → `sort.Slice by Source` → `tx.PutYAML(manifestRel, man, guard)`（[internal/archive/archive.go:327-348](file://internal/archive/archive.go#L327-L348)）。两条并发 Apply 在 manifest CAS 上序列化：输方拿 `storage.ErrConflict` 必须整单重试（[internal/archive/archive.go:286-290](file://internal/archive/archive.go#L286-L290)）。
4. `--dry-run` 只算 `bytes_archived` 不入事务（[internal/archive/archive.go:273-280](file://internal/archive/archive.go#L273-L280)）；`Plan` 为空 → `note: "nothing to archive"`、`Manifest` 不变。

每条 `Entry`（[internal/archive/archive.go:46-56](file://internal/archive/archive.go#L46-L56)）带 `kind`（`events` / `run_stream`）、`source`、`sha256`、`bytes`、`lines`、`archived_at`（RFC3339 UTC）、`archived_by`、`reason`——后续查询 history 的指针。

### 读侧合并：events.Read 双树

`events.Read` 改为跨 live + archive 双树读（[internal/events/events.go:192-223](file://internal/events/events.go#L192-L223)）：

1. `listShards` 顺序扫描 `dirRel = "events"` 与 `"archive/" + dirRel = "archive/events"` 两个目录（[internal/events/events.go:256-279](file://internal/events/events.go#L256-L279)），`filepath.Glob(*.jsonl)` 收集路径；月份名过 `time.Parse("2006-01", name)` + `overlaps(f, month)` 过滤（[internal/events/events.go:281-294](file://internal/events/events.go#L281-L294)）。
2. `readShard` 对每个 rel 共享锁 `st.Read` → `r.Read` → 按行 `DecodeJSON` → `f.matches` 收集。
3. `Read` 末尾 `sort.SliceStable` 按 `(Time, ID)` 排序——shard 顺序无关，事件时间决定最终顺序。

读侧约定：归档分片里的事件是归档那一刻的**快照**，live 分片上随后追加的事件保持「live 优先」语义。run 流的归档回退同理（注释原话："readRunStream-equivalents fall back to the archived stream when the live one is gone"），由 run 侧实现遵循同一约定（[internal/archive/archive.go:11-13](file://internal/archive/archive.go#L11-L13)）。

### search 排除 archive

`search.excluded` 把 `archive` 加入黑名单（[internal/search/search.go:20-21](file://internal/search/search.go#L20-L21)），与 `.cache` / `local` 同列；`Search` 在 `WalkDir` 遇到 `excluded[d.Name()]` 时 `fs.SkipDir`——archive 仅供历史查询入口（manifest + 归档读侧）使用，不参与当前态关键字检索。

### 默认保守：不删只归档

archive 包**有意**没有 delete/purge 形（[internal/archive/archive.go:14-15](file://internal/archive/archive.go#L14-L15)）；dropping archived history 是手动 git 操作——这是「保守不删」的硬边界。

## 本批（v0.1.9，ca58d27→19b9149）

run 流（`.devsys/runs/<id>.jsonl`）的 record 类型、sync 策略与断尾重建**未改**；本轮变化都在它的邻接面——完成判定与工作区绑定变成 Git 可选：

- **完成事件类型回落**：`RunFinish` 在 `req.Outcome == succeeded` 时先跑 `verifyCompletion`。非 Git 项目或目录工作区（`r.Workspace.Branch == ""`）返回 `CompletionCheck.Skipped = true`（`Advanced` 保持 false，reason `git completion check is not applicable`），此时不再走 `refuseCompletion`，`.devsys/events/<month>.jsonl` 的完成事件类型回落为 `run_finished`（不是 `completion_verified`），content 的 verdict 写 `git check not applicable`（[internal/app/runverify.go:15-27](file://internal/app/runverify.go#L15-L27)、[internal/app/runverify.go:45-56](file://internal/app/runverify.go#L45-L56)、[internal/app/run.go:358-372](file://internal/app/run.go#L358-L372)）。
- **事件类型优先级**：`--force` 仍是 `completion_overridden`（优先级最高）；`Skipped` 时 `run_finished`；其余 succeeded 走 `completion_verified`（[internal/app/run.go:358-372](file://internal/app/run.go#L358-L372)）。
- **目录工作区记空 claim head**：`bindWorkspaceToRun` 只在 `ws.Branch != ""`（git worktree）时读 `HeadSHA`；目录工作区记空 head 而不是报错，避免「绑定一个谁都无法验证的 run」与「直接拒绝目录工作区」二选一（[internal/app/workspace.go:110-125](file://internal/app/workspace.go#L110-L125)）。
- **`run exec` 用法文案**：缺命令时报 `run exec requires a command (workloom run exec --id <run-id> -- <command...>) or --harness <name>`（[internal/app/runexec.go:108-111](file://internal/app/runexec.go#L108-L111)）；`refuseCompletion` / `routeToReview` 的 `workloom workitem comment …` 提示同批改名（[internal/app/run.go:342](file://internal/app/run.go#L342)）。
- 未受影响：`streamRecord` 字段表、`syncEvery = 128` + 控制记录 + 末次 flush、`openRunStream` 的 `stream_repaired` 重建、`nextRound` / `lastRound` / `lastExit` / `recordedPhases` 推断、`internal/archive` 的归档与双树读侧合并（本卡行锚 `runexec.go:695-697` / `758-784` / `788-809`、`runstream.go:24-51` / `116-155` 均未位移）。
