# 领域记录与事件

本卡覆盖 `.devsys/` 内**领域记录**（WorkItem / Run / Artifact / Decision / Finding / Approval）与**事件流**（按月分片 JSONL）的存储路径、ID 规则、并发写路径与不变式。M3 新增 `record.ListArtifacts`（门禁证据收集）、`Approval` 全生命周期、`events.AppendBatchTx`（按 shard 分组一次 append）、`propagateRecordsTx`（完成事务内广播决策/发现引用）。

## WorkItem（`internal/workitem`）

### 路径与 ID

`.devsys/workitems/<id>.yaml`，`<id>` = `<PREFIX>-<N>`，`<PREFIX>` 默认 `WLM`，创建时由 `workitem.Create` 通过 CAS 分配（[internal/workitem/workitem.go:59-100](file://internal/workitem/workitem.go#L59-L100)）。状态字段由 `changeStatus` 唯一改写；`Update` 拒绝状态变更。

### 关键不变式

- **CAS 分配**：写事务内 `nextNumber` 扫目录 `max+1` → `PutYAML(..., ExpectAbsent())`；`ErrConflict` 即 `continue` 重扫，最多 5 次。
- **乐观更新**：`Update` 把 `ReadSnapshot` 返回的原字节传给 `Write`，由 `ExpectHash(HashBytes(expected))` 守卫；并发写抛 `ErrConflict`，**永不**被静默覆盖（[internal/workitem/workitem.go:173-227](file://internal/workitem/workitem.go#L173-L227)）。
- **状态字段**：`Status` / `SchedulingState` / `LeaseOwner` / `LeaseToken` / `LeaseUntil` / `Workflow` 全部由对应写路径改写，普通 `Update` 阻断；租约活跃时仅 `UpdateClaimed` 能改 metadata。
- **M3 Guard**：`TransitionRequest.Guard` 在事务内、状态字段改写之前被调用，返回事件与 `status_changed` 同批提交。
- **M3 审批失效**：离开 `from` 时 `approval.InvalidateForStatusTx` 把同源未消费审批标记为 `invalidated_at`，事件并入同批。
- **M3 记录传播**：进入 `done` 时 `propagateRecordsTx` 把 `decision://<id>` / `finding://<id>` 追加到父与直接兄弟的 `context_refs`；无 parent 不广播；父子自环拒绝并回滚。

## Artifact（`internal/record`）

### 路径与 ID

`.devsys/artifacts/artifact-<N>.yaml`，`<N>` 由 `nextNumber` 扫目录得到。Artifact 是**不可变版本链**：每个版本是独立文件，`previous_id` 指向上一个版本，链由 `ArtifactHistory` 沿 `previous_id` 反查，环检测 `seen[cursor]` → `ErrBadID`。

### 写路径：`NewArtifactVersion`

[internal/record/record.go:297-344](file://internal/record/record.go#L297-L344) 写锁内：

1. `tx.ReadForExpect` 取当前版本字节 → `DecodeYAML` 到 `cur`。
2. `*next = *cur` 浅拷贝所有字段。
3. `next.ID = newID`、`next.Version = cur.Version + 1`、`next.PreviousID = &currentID`。
4. `tx.PutYAML(... newID.yaml ..., ExpectAbsent())` 写新文件。

现有版本文件**永不**被改写。

### M3 门禁证据收集：`ListArtifacts`

[internal/record/record.go:244-260](file://internal/record/record.go#L244-L260) 按 ID 升序列出全部 artifact 版本，门禁从中提取 `Name` 集与 `gate.RequireArtifacts` 做集合包含校验（[internal/cli/cli.go:1211-1226](file://internal/cli/cli.go#L1211-L1226)）。`Name` 是 artifact 的逻辑名称（同一 `Name` 可能多版本），跨版本聚合。

## 事件流（`internal/events`）

### 路径与 ID

`.devsys/events/<YYYY-MM>.jsonl`，按 UTC 年月分片；ID `ev-<UTC时间戳.微秒>-<8hex>`（[internal/events/events.go:150-157](file://internal/events/events.go#L150-L157)），无全局计数器，4 字节随机后缀保证同微秒多事件去重（M3Reviewer2 ①）。

### 关键不变式

- shard 路径由事件自身 `UTC t.Year()/Month()` 派生，12 月事件 1 月写仍落 12 月分片。
- 写路径只校验 `reply_to` 必须是 comment 类型（[internal/events/events.go:69-71](file://internal/events/events.go#L69-L71)）。
- subject 一致性、悬空 reply、二级回复（parent 也是 reply）由 `Comments` 聚合阶段校验（[internal/events/events.go:240-264](file://internal/events/events.go#L240-L264)）。
- `ErrIncompleteTail` 由 `storage/jsonl.go` 的 `InspectJSONL` / `appendJSONL` 透传；事件层不做断尾判定。
- append 用 `tx.AppendJSONL`（单事件）或 `tx.AppendJSONLRaw`（M3 多事件），由事务协议统一中断恢复。

### M3 事务内多事件：`AppendBatchTx`

[internal/events/events.go:108-144](file://internal/events/events.go#L108-L144) 按 shard 分组，把同 shard 事件合并为一次 `AppendJSONLRaw` 调用。典型场景：

- `workitem.changeStatus` 提交批 = `status_changed` + Guard 事件 + 失效事件 + 传播事件
- `approval.ConsumeTx` + `InvalidateForStatusTx` 同事务内提交 `approval_consumed` + `approval_invalidated` + `status_changed`

每个 shard 在事务内只一次 append，违反 `staged twice` 校验的路径（消费 + 失效同文件）由 `Tx.Staged(rel)` 显式跳过。

type Event struct {

    Type          string  // status_changed / repair_applied / claim / heartbeat / release / lease_recovered / comment / workflow_started / workflow_step_completed / workflow_paused / workflow_resumed / workflow_cancelled / approval_requested / approval_approved / approval_rejected / approval_consumed / approval_invalidated / record_propagated
    Subject       Reference  // {Type, ID}

## M3 记录传播

`workitem.propagateRecordsTx`（[internal/workitem/propagate.go:28-57](file://internal/workitem/propagate.go#L28-L57)）在 `changeStatus` 目标为 `done` 且来自非 `done` 时触发：

1. `relatedRecordRefs` 按文件名字典序扫描 `decisions/` 与 `findings/`，挑出 `RelatedWorkItems` 命中的记录，返回 `decision://<id>` / `finding://<id>` 引用。
2. `propagationTargets` 取父与所有直接兄弟（按 id 排序）。
3. `propagateToTarget` 对每个目标 `tx.ReadForExpect` → `DecodeYAML` → 追加缺失引用 → `PutYAML(ExpectHash)` → 返回 `record_propagated` 事件。
4. 目标已包含全部引用 → 跳过写盘与事件（幂等）。
5. 父子自环（`parent_id == self`）显式拒绝并回滚。
6. 无 `ParentID` / 空字符串 → 不广播。

事件 `record_propagated` 与 `status_changed` / Guard / 失效事件并入 `events.AppendBatchTx` 同批提交。

## 本批（M#337，commit 362b637）

M#337 在工作项读取路径与对账探针两侧各加了一处「不可信集合的稳定序列化 / 收集语义」：

### `Store.List` 空集合非 nil

`internal/workitem/workitem.go:Store.List`（[internal/workitem/workitem.go:131-164](file://internal/workitem/workitem.go#L131-L164)）把 `items` 初始化为 `items := []*domain.WorkItem{}`，空集合 → `(non-nil empty slice, nil)`；非空 → `(slice, nil)`。下游消费者（`workloom workitem list --json` / MCP `workitem_list` / `app.workitemsForView` 等）现在空集合序列化 `[]` 而非 `null`。

### `reconcile.readAllWorkitems` 解码失败继续扫

`internal/reconcile/reconcile.go:readAllWorkitems`（[internal/reconcile/reconcile.go:968-1000](file://internal/reconcile/reconcile.go#L968-L1000)）走 `storage.Inspect` 列 `.devsys/workitems/*.yaml`，对每条记录 `domain.DecodeYAML`：成功 → 追加；失败 → `InvalidFile{Path: rel, Err: derr.Error()}` 并 `continue`。这是与 `Store.List` 的对比：`Store.List` 单条失败 → `error`（调用方决定重试或返回），`readAllWorkitems` 单条失败 → 记录 + 继续扫（对账需要「完整不可信集合」）。

### `buildProposals` 合并 invalid

`buildProposals`（[internal/reconcile/reconcile.go:889-894](file://internal/reconcile/reconcile.go#L889-L894)）把 `readAllWorkitems` 返回的 `invalidFiles` 合并进自己的 `invalid` 返回值，交给 `Doctor` 填入 `InspectionReport.InvalidFiles`。`RepairDryRun` 在 `len(invalid) > 0` 时直接 `fmt.Errorf("cannot plan repairs: %s", …)` 拒绝。

——M#337 不修改工作项的写路径（`Create` / `Update` / `changeStatus` / `Claim` / 等），它只影响读取语义与对账诊断。

## 本批（v0.1.9，ca58d27→19b9149）

领域记录的文件布局、ID 规则与写事务本轮**未变**；变化在「完成事件类型」与几条文案：

- **完成事件类型（Git 可选化）**：`RunFinish` 在 succeeded 时按 `verifyCompletion` 结果选类型——`--force` → `completion_overridden`；`CompletionCheck.Skipped`（非 Git 项目或目录工作区，reason `git completion check is not applicable`）→ `run_finished`，content 的 verdict 写 `git check not applicable` 且 `Verification.Advanced` 保持 false；其余 → `completion_verified`。subject 仍是 `{Type: "run", ID}`，`Related` 仍带 `workitem`（[internal/app/run.go:358-372](file://internal/app/run.go#L358-L372)、[internal/app/runverify.go:45-56](file://internal/app/runverify.go#L45-L56)）。
- **`Run` 记录的 claim head 可为空**：目录工作区（`Workspace.Branch == ""`）由 `bindWorkspaceToRun` 记空 head 而不是报错——`Claim.HeadSHA` 为空即「无 Git 证据」，不是「验证失败」（[internal/app/workspace.go:110-125](file://internal/app/workspace.go#L110-L125)）。
- **文案改名**：活跃租约下 `workitem.Store.Update` 报 `workloom workitem release …`（[internal/workitem/workitem.go:184](file://internal/workitem/workitem.go#L184)）；未绑定策略的 claim 提示改指 `workloom workflow start …`（[internal/app/workitem.go:63-66](file://internal/app/workitem.go#L63-L66)）；失效审批提示改指 `workloom approval request`（[internal/app/workitem.go:633-637](file://internal/app/workitem.go#L633-L637)）。
- **未受影响**：`.devsys/{workitems,runs,artifacts,decisions,findings,approvals,events}` 的路径与 ID 规则、`Store.List` 非 nil 空集合、`readAllWorkitems` 的 `InvalidFile` 语义、`propagateRecordsTx`、审批生命周期与五类审批事件、`AppendBatchTx` 的同 shard 合并、`Event.Type` 的既有取值。
