# 可靠文本存储 · 事务与恢复

> 自定义维度卡：五维默认卡无法覆盖事务协议层面的细节。本卡聚焦 commit point、redo 协议与读者恢复路径，区分 commit point / redo / `Expect` / reader recovery 四条恢复线。

## Commit point

`txn.go:193-200`：`commitMarker` 是一个独立的小 YAML 文件，其**原子出现**即代表"事务已决定被重放完成"。

```yaml
# commit.yaml
txn_id: 20260917T120000.000000000Z-1234-abcdef0123456789
committed_at: 2026-09-17T12:00:00.123456789Z
journal_sha256: <journal.yaml 的 sha256>
op_count: 2
```

写协议 `commitLocked`（`txn.go:246-332`）严格按以下顺序：

1. `os.MkdirAll(<txnDir>/<id>/payload, 0o755)`
2. 逐 op `WriteFileSync(payload/<i>.bin)`（基元，`atomic.go:79-99`：先 open + trunc，写入后 `Sync()` 然后 `Close()`）
3. `AtomicWrite(journal.yaml)` → `txnStage(stageJournalDurable)`
4. `AtomicWrite(commit.yaml)` → `txnStage(stageCommitted)` ← **commit point**
5. 逐 op `applyPayload` → `txnStage(stageApplied(i))`
6. `os.RemoveAll(dir)` → `txnStage(stageCleaned)`

由于第 4 步用 `AtomicWrite`（temp + rename），POSIX 下它要么完全存在要么完全不存在；commit marker 的可见性就是"事务是否被决定"的单点判据。

`commitLocked` 在每个阶段之间调用 `txnStage(stage string)`（`txn.go:98-104`）。生产环境 `txnStageHook` 为 `nil`；测试可通过包级变量在指定 stage 之后注入 `os.Exit(exitCodeCrash)`，从而模拟进程在两次盘写之间被杀——`TestCrashRecoveryMatrix`（`txn_test.go:46-116`）枚举五个 stage 验证恢复结果。

## Journal 结构

`txn.go:176-191`：

```go
type journal struct {
    TxnID     string      `yaml:"txn_id"`
    CreatedAt string      `yaml:"created_at"`
    PID       int         `yaml:"pid"`
    Ops       []journalOp `yaml:"ops"`
}

type journalOp struct {
    Kind          string `yaml:"kind"`             // opKindPut | opKindAppend
    Rel           string `yaml:"rel"`              // 受管路径（相对 .devsys）
    Expect        string `yaml:"expect,omitempty"` // Put 的守卫（"any" / "absent" / "sha256:..."）
    Payload       string `yaml:"payload"`          // 相对路径 "payload/NNN.bin"
    PayloadSHA256 string `yaml:"payload_sha256"`
    PayloadSize   int64  `yaml:"payload_size"`
    PreSize       int64  `yaml:"pre_size,omitempty"` // Append 起始偏移
}
```

`j.validate()`（`txn.go:202-228`）拒绝：空 ops、`Rel/Payload/PayloadSHA256` 缺失、负 `PayloadSize`、`payloadRel` 校验失败、`Kind` 未知、`opKindPut` 但 `Expect` 无法解析、`opKindAppend` 但 `PreSize < 0`。

## 重放（Redo）协议

`recover.go:181-248` `replayTxn`：

| 步骤 | 决策 |
|---|---|
| `readTxnPayload`（`recover.go:251-264`） | 读 payload 文件并校验 sha256；不等 → `payload changed since commit (sha256 mismatch)` |
| `parseExpect`（`txn.go:65-82`） | 还原 `Expect`；坏字符串 → `invalid expect %q` |
| `opKindPut` | 若当前文件 sha256 == `o.PayloadSHA256` → `skipped++`；否则 `Expect.satisfiedBy` 必须成立，然后 `AtomicWrite(abs, payload, 0o644)` → `applied++`；否则报错"target is neither the expected old version ... nor the committed new content; refusing to guess" |
| `opKindAppend` | `InspectJSONL` 取 size + complete；`size == PreSize` → `appendJSONL`（再校验 `Complete`，`recover.go:225-227`）；`size >= PreSize+PayloadSize` 且 `readRegion(abs, PreSize, PayloadSize)` 与 payload 字节一致 → `skipped++`；其它 → 错误 |

幂等性保证：

- Put 通过 sha256 比较短路。
- Append 通过 `PreSize` 与已存在区间比较短路。
- 重放同一事务任意次不会重复写。

`recover.go:287-293` `removeTxnDir` 删除事务目录并 best-effort `fsyncDir(<parent>)`。

## Expect / 乐观并发

`txn.go:15-82`：

| 构造器 | 含义 |
|---|---|
| `ExpectAny()` | 不检查版本 |
| `ExpectAbsent()` | 目标必须不存在 |
| `ExpectHash(h)` | 目标必须存在且 sha256 == h |

`commitLocked` 在落盘前对每个 Put 重新读取并校验（`txn.go:247-267`）；失败 → `ErrConflict`。`Describe` 错误消息携带期望版本与实际版本摘要（`describeCurrent` 截取 sha256 前 12 位，`txn.go:368-374`）。

`Tx.claim`（`txn.go:167-173`）保证同一事务内同一个受管路径不会被重复 stage。

## Reader 恢复

`store.go:143-166` 的 `Read` 流程（详见 [架构设计](架构设计.md) 关键流程）：

1. 取共享锁。
2. `pendingTxns` 列残留事务。
3. 有残留 → 释放共享锁 → `Recover`（取独占锁执行 `recoverLocked`）→ 重新尝试。
4. `maxAttempts = 3`；耗尽后 → `ErrRecoveryFailed`。

读者始终先看是否有 commit marker / journal 残留，再决定是否需要恢复；恢复在独占锁下进行以避免与新写入冲突。

## 不声明的能力

- **断电一致性**：commit marker 之前的部分写入（payload 已写、journal 未写；journal 已写、commit 未写）若发生断电，恢复协议**只在 commit marker 存在时**重放；commit marker 不存在时通过 `verifyUntouched` 校验后丢弃——但目录 fsync 在 Windows 为 no-op、`atomic.go:17-18` 与 `errors.go:6-9` 明确不保证 power-loss 语义。
- **跨事务隔离**：仅靠项目级锁串行化；不存在 MVCC 或快照读。
- **失败恢复语义**：单进程意外中断可恢复；多进程同时进入 `commitLocked` 由锁阻止，但极端时序（例如锁释放与新事务启动之间）仅通过 `Expect` 守卫保护。
