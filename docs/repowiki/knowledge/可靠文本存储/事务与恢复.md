# 可靠文本存储 · 事务与恢复

> 自定义维度卡：五维默认卡无法覆盖事务协议层面的细节。本卡聚焦 commit point、redo 协议与读者恢复路径，区分 commit point / redo / `Expect` / reader recovery 四条恢复线，并补上 M2 引入的只读 `Inspect` 路径、`Tx.Delete` 操作以及落盘层对父目录的自动补建。

## Commit point

`txn.go:205-212`：`commitMarker` 是一个独立的小 YAML 文件，其**原子出现**即代表"事务已决定被重放完成"。

```yaml
# commit.yaml
txn_id: 20260917T120000.000000000Z-1234-abcdef0123456789
committed_at: 2026-09-17T12:00:00.123456789Z
journal_sha256: <journal.yaml 的 sha256>
op_count: 2
```

写协议 `commitLocked`（`txn.go:288-384`）严格按以下顺序：

1. 重做每 op 的前置校验（`txn.go:289-318`）：Put/Delete 用 `readFileMaybe` 复核 `Expect`；Append 用 `InspectJSONL` 复核尾部完整并把当前 `Size` 写回 `preSize`。
2. `os.MkdirAll(<txnDir>/<id>/payload, 0o755)`（`txn.go:325`）。
3. 逐 op（除 Delete）`WriteFileSync(payload/<i>.bin)`（基元，`atomic.go:82-99`：先 open + trunc，写入后 `Sync()` 然后 `Close()`，并且**自动补建父目录**）。
4. `AtomicWrite(journal.yaml)` → `txnStage(stageJournalDurable)`（`txn.go:352-355`）。
5. `AtomicWrite(commit.yaml)` → `txnStage(stageCommitted)` ← **commit point**（`txn.go:367-370`）。
6. 逐 op `applyPayload` → `txnStage(stageApplied(i))`（`txn.go:372-377`）。
7. `os.RemoveAll(dir)` → `txnStage(stageCleaned)`（`txn.go:378-382`）。

由于第 5 步用 `AtomicWrite`（temp + rename），POSIX 下它要么完全存在要么完全不存在；commit marker 的可见性就是"事务是否被决定"的单点判据。`AtomicWrite` 自身也补建父目录（`atomic.go:19-23`），并 `fsyncDir(dir)`（POSIX best-effort）。

`commitLocked` 在每个阶段之间调用 `txnStage(stage string)`（`txn.go:98-104`）。生产环境 `txnStageHook` 为 `nil`；测试可通过 `TxnStageHookForTest` 在指定 stage 之后注入 `os.Exit(exitCodeCrash)`，从而模拟进程在两次盘写之间被杀——`TestCrashRecoveryMatrix`（`txn_test.go:46-116`）枚举五个 stage 验证恢复结果。

## Journal 结构

`txn.go:188-203`：

```go
type journal struct {
    TxnID     string      `yaml:"txn_id"`
    CreatedAt string      `yaml:"created_at"`
    PID       int         `yaml:"pid"`
    Ops       []journalOp `yaml:"ops"`
}

type journalOp struct {
    Kind          string `yaml:"kind"`             // opKindPut | opKindAppend | opKindDelete
    Rel           string `yaml:"rel"`              // 受管路径（相对 .devsys）
    Expect        string `yaml:"expect,omitempty"` // Put / Delete 的守卫（"any" / "absent" / "sha256:..."）
    Payload       string `yaml:"payload,omitempty"`          // 相对路径 "payload/NNN.bin"（Delete 为空）
    PayloadSHA256 string `yaml:"payload_sha256,omitempty"`   // Delete 为空
    PayloadSize   int64  `yaml:"payload_size"`               // Delete 时记录 0
    PreSize       int64  `yaml:"pre_size,omitempty"`         // Append 起始偏移
}
```

`j.validate()`（`txn.go:235-270`）拒绝：空 ops、`Rel/Payload/PayloadSHA256` 缺失（Delete 例外，参见 `txn.go:244`）、负 `PayloadSize`、`payloadRel` 校验失败、`Kind` 未知、`opKindPut/opKindDelete` 但 `Expect` 无法解析、`opKindAppend` 但 `PreSize < 0`。

## 重放（Redo）协议

`recover.go:194-284` `replayTxn`：

| 步骤 | 决策 |
|---|---|
| `readTxnPayload`（`recover.go:287-300`） | 读 payload 文件并校验 sha256；不等 → `payload changed since commit (sha256 mismatch)` |
| `parseExpect`（`txn.go:67-84`） | 还原 `Expect`；坏字符串 → `invalid expect %q` |
| `opKindPut` | 若当前文件 sha256 == `o.PayloadSHA256` → `skipped++`；否则 `Expect.satisfiedBy` 必须成立，然后 `AtomicWrite(abs, payload, 0o644)` → `applied++`；否则报错"target is neither the expected old version ... nor the committed new content; refusing to guess" |
| `opKindAppend` | `InspectJSONL` 取 size + complete；`size == PreSize` → `appendJSONL`（再校验 `Complete`，`recover.go:239-244`）；`size >= PreSize+PayloadSize` 且 `readRegion(abs, PreSize, PayloadSize)` 与 payload 字节一致 → `skipped++`；其它 → 错误 |
| `opKindDelete` | `parseExpect` + `readFileMaybe`：目标不存在 → `skipped++`；存在则 `Expect.satisfiedBy` 必须成立再 `os.Remove` → `applied++`；否则报错"target is neither the expected old version ... nor absent; refusing to guess"（`recover.go:259-281`） |

`verifyUntouched`（`recover.go:147-192`）对应未提交事务的反向校验：Put/Append 比对当前文件与期望，Delete 则要求目标仍然满足 `Expect`（否则拒绝丢弃，因为它本应被删除但实际还在）。

幂等性保证：

- Put 通过 sha256 比较短路。
- Append 通过 `PreSize` 与已存在区间比较短路。
- Delete 通过"目标已不存在"短路。
- 重放同一事务任意次不会重复写。

`recover.go:323-329` `removeTxnDir` 删除事务目录并 best-effort `fsyncDir(<parent>)`。

## Expect / 乐观并发

`txn.go:15-82`：

| 构造器 | 含义 |
|---|---|
| `ExpectAny()` | 不检查版本 |
| `ExpectAbsent()` | 目标必须不存在 |
| `ExpectHash(h)` | 目标必须存在且 sha256 == h |

`commitLocked` 在落盘前对每个 Put / Delete 重新读取并校验（`txn.go:289-318`），失败 → `ErrConflict`。Append 用 `InspectJSONL` 校验尾部完整，失败 → `ErrIncompleteTail`（`txn.go:301-307`）。`Describe` 错误消息携带期望版本与实际版本摘要（`describeCurrent` 截取 sha256 前 12 位，`txn.go:431-437`）。

`Tx.claim`（`txn.go:200-206`）保证同一事务内同一个受管路径不会被重复 stage。

## Tx.Delete：可恢复删除

`Tx.Delete`（`txn.go:176-186`）把删除也纳入同一套事务协议：与 Put 一样用 `Expect` 做守卫，`claim` 阻断同事务重复，校验在 `commitLocked` 的 Put/Delete 分支（`txn.go:309-316`）一并在持锁下重做。

落盘与重放要点：

- Delete op 不写 payload，journal 里 `Payload/PayloadSHA256` 为空，`PayloadSize=0`，但 `Expect` 仍被序列化（`txn.go:329-346`、`txn.go:386-393`）。
- `expectField`（`txn.go:388-393`）仅对 Put/Delete 输出 `Expect` 字段。
- `j.validate()` 对 Delete 跳过 `Payload/PayloadSHA256` 的非空检查（`txn.go:244-248`）。
- 重放走 `replayTxn` 的 Delete 分支（`recover.go:259-281`）：目标已不存在直接 `skipped++`；否则按 `Expect` 校验后 `os.Remove`。
- 删除与 Put/AppendJSONL 共享同一个 commit marker，所以半提交删除永远不可见；详见 `recover.go:259-281` 的 Delete 重放分支。

## Reader 恢复

`store.go` 的 `Read` 流程（详见 [架构设计](架构设计.md) 关键流程）：

1. 取共享锁。
2. `pendingTxns` 列残留事务。
3. 有残留 → 释放共享锁 → `Recover`（取独占锁执行 `recoverLocked`）→ 重新尝试。
4. `maxAttempts = 3`；耗尽后 → `ErrRecoveryFailed`。

读者始终先看是否有 commit marker / journal 残留，再决定是否需要恢复；恢复在独占锁下进行以避免与新写入冲突。

### 只读检查：Inspect / InspectUnlocked

M2 引入两条**绝不自动恢复、绝不创建锁文件**的只读路径，给 `reconcile.Doctor` / `reconcile.RepairDryRun` 等纯诊断命令使用（`internal/storage/inspect.go:1-98`）。

`Inspect`（`inspect.go:43-81`）：

1. `pendingTxns()` 扫事务目录：非空 → 返回 `*PendingTxnError{IDs: ...}`（`inspect.go:50-56`），不输出任何业务事实。
2. `os.Stat(s.lockPath)`：文件不存在 → 返回 `ErrLockUnavailable`（`inspect.go:61-63`），让上层报告"inspection unavailable"而不是凭空声称"no activity"。
3. 否则以 `O_RDONLY`（**不带 O_CREATE**）打开锁文件，取共享锁，运行 `fn(&Reader{...})`，释放锁与文件。
4. 共享锁的获取带 `LockTimeout` 与 ctx 取消（`inspect.go:102-127`）；失败时尝试从锁文件读出 best-effort holder 描述拼进错误。

`InspectUnlocked`（`inspect.go:89-98`）：当从未有写入、因此没有锁文件时，医生/干跑路径的保守回退。同样先查 pending 事务，非空仍返回 `PendingTxnError`；否则直接 `fn(&Reader{...})`。每个读仍然是单文件原子替换目标，但**无锁不阻塞并发首写**——上层必须把这种快照视作"建议值"，关键证据仍要在真实事务内复检（`inspect.go:83-88` 注释）。

两个错误（`inspect.go:20-41`）：

- `ErrLockUnavailable`：锁文件不存在，只读命令无法在不创建状态的情况下取共享锁。
- `ErrPendingTxn` 与 `PendingTxnError{IDs []string}`：等待 `recover` 之后才能给出业务快照；调用方可直接渲染 `IDs`。


## 落盘基元：父目录自动补建

M2 起所有"写到新位置"的基元都补建缺失的父目录，避免调用方预先 `MkdirAll`：

- `AtomicWrite`（`atomic.go:19-58`）：第一行 `os.MkdirAll(filepath.Dir(path), 0o755)`，随后 `os.CreateTemp` 在该目录建临时文件、写入、`Sync`、`Close`、`Chmod`、`renameWithRetry` 覆盖目标，最后 best-effort `fsyncDir(dir)`。
- `WriteFileSync`（`atomic.go:82-99`）：第一行同样 `os.MkdirAll(filepath.Dir(path), 0o755)`，随后 `O_WRONLY|O_CREATE|O_TRUNC` 打开、写入、`Sync`、`Close`。
- `appendJSONL`（`jsonl.go:90-93`）：第一行 `os.MkdirAll(filepath.Dir(path), 0o755)`，随后 `InspectJSONL` → 写入 → `Sync` → `Close`。

事务载荷落到 `<txnDir>/<id>/payload/<i>.bin` 的路径因父目录已被 `commitLocked` 第 2 步 `MkdirAll` 创建而不需要再补；写入新工作项 YAML / 事件 JSONL 分片等场景则依赖上述基元自身的补建。

## 不声明的能力

- **断电一致性**：commit marker 之前的部分写入（payload 已写、journal 未写；journal 已写、commit 未写）若发生断电，恢复协议**只在 commit marker 存在时**重放；commit marker 不存在时通过 `verifyUntouched` 校验后丢弃——但目录 fsync 在 Windows 为 no-op、`atomic.go:17-18` 与 `errors.go:6-9` 明确不保证 power-loss 语义。
- **跨事务隔离**：仅靠项目级锁串行化；不存在 MVCC 或快照读。
- **失败恢复语义**：单进程意外中断可恢复；多进程同时进入 `commitLocked` 由锁阻止，但极端时序（例如锁释放与新事务启动之间）仅通过 `Expect` 守卫保护。
- **只读检查的"无锁"语义**：`InspectUnlocked` 不持有任何锁，并发的首写可能仍在写入；调用方须把读到的字节视作建议值并在真实事务内复检（`inspect.go:83-88`）。
