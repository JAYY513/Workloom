# 可靠文本存储 · 概述

本模块覆盖 `.devsys/` 项目内**领域数据的落盘层**与**M3 工作流/审批/就绪判定三层应用逻辑**、**M4 显式化的读快照与守卫更新路径**：任务（WorkItem）、事件流、Run 记录、决策/发现/工件记录、审批记录、工作流策略文件、就绪判定引擎，以及基于文本扫描的关键字检索。它建立在 [存储基元](存储错误语义.md) 的事务与锁之上，向上提供 Go API 与 `internal/app` 包装的共享应用服务，检索另有 CLI 入口；不提供 MCP 工具（由 `internal/mcp` 在 M4.2 之后独立暴露，见 [共享应用与 MCP](../共享应用与MCP/概述.md)）。

## 模块定位

- **做什么**：把领域记录写成稳定键序的 YAML/JSONL 文本文件；分配全局唯一 ID；提供乐观并发更新与不可变版本链；M3 起在工作项之上承接工作流策略加载与 last-known-good 缓存、门禁与质量门、审批生命周期、就绪判定与 next 优先级推荐；M4 起把「读 + 守卫写」模式显式化为 `ReadSnapshot` / `ReadDecision` / `ReadFinding` / `ReadArtifact` / `ReadRun` 与对应的 `UpdateDecision` / `UpdateFinding` / `AppendArtifactVersion` 守卫更新方法。
- **不做什么**：不直接暴露 MCP 工具（由 `internal/mcp` 通过 `internal/app` 间接调用）；不执行 hook（M6）、不做任务派发（M6）。

M2 起在可靠文本存储之上又承接了**调度**与**对账/修复**两块职责：状态机九态图与保守转换（`internal/domain/state.go`）、租约文件 `.devsys/scheduling/<id>.yaml` 下的领取/心跳/释放/重试（`internal/workitem/claim.go`），以及只读检查 / 恢复 / 确认式修复（`internal/storage/inspect.go` + `internal/reconcile/`）。M3 起又承接：

- **工作流策略层** `internal/workflow/`：解析 `.devsys/workflows/<id>.md`（YAML front matter + 提示词正文），校验步骤/转换/门禁/钩子/限额/质量门；评估白名单条件；渲染模板与展开环境变量；last-known-good 缓存（`.devsys/.cache/workflows/`）。
- **审批服务** `internal/approval/`：持久化 `.devsys/approvals/approval-<N>.yaml`，实现 request → decide → consume 生命周期；consume 永远在转换事务的 Guard 内完成，失败即整单回滚。
- **就绪判定** `internal/next/`：纯函数 `Evaluate` 根据待恢复事务、过期/孤儿租约、滞留审查、阻塞、元数据/策略问题、待决审批等风险输出 PASS/CONCERNS/FAIL 判定，并按 §7.4 优先级给出唯一推荐动作。

三者仍全部落在 storage 的事务与锁之上，自身不引入新的锁类型。

M4 起在领域模块层又新增**读快照与守卫更新**的显式 API（`internal/record/update.go` 与 `internal/run/run.go`）：

- `record.ReadDecision / ReadFinding / ReadArtifact` 通过共享泛型 `readSnapshot[T]` 返回解码对象与原 YAML 字节；应用服务把字节哈希为 `version` 字段返回给 CLI/MCP。
- `record.UpdateDecision / UpdateFinding` 接受调用方持有的 `expected []byte`，写锁内 `tx.ReadForExpect` + `ExpectHash` 守卫；并发写 → `storage.ErrConflict`。
- `record.AppendArtifactVersion` 拒绝**并发分叉**——若 `currentID` 已有任何子版本，立即返回 `ErrSuperseded`，要求 re-read head 再 append。
- `run.ReadSnapshot` 同形返回 Run 解码对象与原字节，支撑 `app.RunUpdate` 的 `expect` 守卫路径。

## 本批（M#337，commit 362b637）

M#337 在对账层和工作项存储引入「不可读工作项文件」作为一类新的失败可见信号，并把 CLI / next / prime / project status 收敛到统一的 exit 4 语义：

- `internal/reconcile/reconcile.go` 新增类型 `InvalidFile{Path, Err}`（`String()` = `path: err`），`InspectionReport` 增字段 `InvalidFiles []InvalidFile`（json/yaml tag `invalid_files,omitempty`）。
- `readAllWorkitems` / `buildProposals` 走 `storage.Inspect` 扫 `.devsys/workitems/` 时把单个解码失败的文件记为 `InvalidFile` 并继续扫其余文件，避免一个坏文件把整棵树隐藏（[internal/reconcile/reconcile.go:968-1000](file://internal/reconcile/reconcile.go#L968-L1000)）；`buildProposals` 把 invalid 列表合并进自己的返回值传给 `Doctor`（[internal/reconcile/reconcile.go:894-896](file://internal/reconcile/reconcile.go#L894-L896)）。
- `Doctor` 填充 `rep.InvalidFiles = invalid` 并把 `rep.Note` 追加 `one or more work item files are unreadable; the state cannot be fully trusted`（[internal/reconcile/reconcile.go:226-233](file://internal/reconcile/reconcile.go#L226-L233)）。
- `RepairDryRun` 有 invalid 时直接 `fmt.Errorf("cannot plan repairs: %s", …)` 拒绝，保持 fail-closed——在不可信树上构造的 plan 不可信（[internal/reconcile/reconcile.go:320-333](file://internal/reconcile/reconcile.go#L320-L333)）。
- `internal/workitem/workitem.go`：`Store.List` 把 `items` 初始化为 `[]*domain.WorkItem{}`，空集合返回非 nil `[]`——下游可直接 `len(...) == 0` / 序列化 `[]`，免去 nil 判断（[internal/workitem/workitem.go:133-171](file://internal/workitem/workitem.go#L133-L171)）。
- CLI 渲染：`internal/cli/diagnostics.go` 在 doctor 人类模式打 `INVALID  <path>  <err>` 行；`--json` 编码完整 report 后若 `len(InvalidFiles) > 0` 同样 `exitWithCode(CodeInvalid)`；exit 4 语义在 JSON / 人类两种形态下保持一致（[internal/cli/diagnostics.go:133-173](file://internal/cli/diagnostics.go#L133-L173)）。
- `internal/app/next.go`：`Service.Next` 在 `len(doc.InvalidFiles) > 0` 时直接 `Invalidf(KindInvalid, nil, "next: managed state unreadable: <file>: <err>…", ≤3 条 + `+N more`)；`next` / `prime` / `project status` 同路——不可信状态下不让 next 给出推荐动作（[internal/app/next.go:24-46](file://internal/app/next.go#L24-L46)）。

不可读工作项文件不是 `doctor` 的「提案」而是「证据不可信」信号；与 git 冲突的 `ProposalNoteUnmerged`（M8.2）不同——后者在 dry-run plan 里出现，apply 全 rejected；本批的 `InvalidFiles` 让 doctor / repair / next 在出口上达成一致的 fail-closed 行为。
