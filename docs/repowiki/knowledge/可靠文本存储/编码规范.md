# 编码规范 · 可靠文本存储

本卡汇集可靠文本存储模块已被代码与测试验证的编码规则。

## 命名

- 包名小写单词或缩写：`storage` / `workitem` / `events` / `run` / `record` / `search` / `reconcile` / `workflow` / `approval` / `next` / `domain` / `project` / `registry`。
- 类型 PascalCase：`Store` / `Reader` / `Tx` / `Expect` / `Policy` / `GateEvidence` / `GateResult` / `Approval` / `TransitionError`。
- 函数 PascalCase（导出）/ camelCase（私有）；动词优先：`Open` / `Read` / `Write` / `Resolve` / `Render` / `ExpandEnv` / `ScoreQuality` / `Evaluate`。
- 错误 sentinel `ErrXxx` 前缀；类型化错误 `XxxError` 后缀：`ErrConflict` / `TransitionError` / `WorkflowStepError` / `RenderError`。
- 常量 PascalCase 或 SCREAMING_SNAKE：根据是否「枚举值」决定；状态名 `StatusDraft` / `StatusBacklog` 等。
- 字段遵循 Go YAML tag：`json:"…"` 与 `yaml:"…"` 一致（`storage/serialize.go` 通过 YAML 读时严格）；domain 模型 `yaml:"name,omitempty"` 风格。

## 错误处理

- **错误码优先于错误消息**：调用方脚本按 `codedError.code` 分支，不解析 `message`。
- **错误用结构体携带元数据**：`config.Problem{File, Line, Field, Reason}` / `domain.TransitionError{From, To, Allowed, Reason}` / `workitem.WorkflowStepError{Step, Reason, Allowed}` / `workflow.Issue{File, Line, Field, Reason, Severity}` / `workflow.RenderError{Kind, Variables, Line, Reason}`。
- **wrap with sentinel**：`fmt.Errorf("%w: <detail>", <sentinel>, <args>)`，调用方 `errors.Is(err, storage.ErrConflict)` 取 sentinel。
- **领域错误暴露包级 sentinel**（M3）：`approval.ErrNotFound` / `approval.ErrInvalidInput` / `approval.ErrMismatch` 等，CLI 层 `errors.Is` 分支。
- **parse 错误不暴露为 Go error**：`workflow.Parse` 返回 `(*Policy, []Issue)`，由调用方按 `SeverityError` 判定拒绝——错误结构以 located 数据形式贯穿；这是与 Go 传统 error 模型的有意偏离。

## 事务使用

- **所有动盘必须走 `Store.Write`**：在独占事务里收集 op、`commitLocked` 落盘、释放锁；`os.ReadFile` / `os.WriteFile` 仅用于 `init` 的占位写入与 `readFileMaybe`（[internal/storage/atomic.go](file://internal/storage/atomic.go)）。
- **所有读路径走 `Store.Read`**：共享锁下读回调；调用方**不要**直接 `os.ReadFile` `.devsys/`。
- **CAS 分配**：`nextNumber` 扫目录 `max+1` + `PutYAML(..., ExpectAbsent())`；冲突 `ErrConflict` 重试 ≤ 5 次。
- **乐观更新**：`Update` / `Decide` / `ConsumeTx` / `InvalidateForStatusTx` 等都通过 `tx.ReadForExpect` + `ExpectHash(HashBytes(raw))` 守卫；并发写 `ErrConflict` 永不被静默吞。
- **M3 多事件同事务**：`Tx.AppendJSONLRaw` + `events.AppendBatchTx` 按 shard 分组一次 append；同一 `rel` 在事务内只暂存一次。
- **M3 事务内已暂存查询**：`Tx.Staged(rel)` 用于失效 pass 跳过本事务已写的路径；`approval.InvalidateForStatusTx` 是其消费者。
- **last-known-good**：`workflow.Resolve` 每次重新 `Parse`、不信 mtime；`refreshLastKnownGood` 是 best-effort 通过 `Store.Write` 写 `.devsys/.cache/workflows/<id>.md`，写失败不阻塞 Resolve（缓存可重建）；读取端 `cachedPolicy` 把损坏快照视为缺失。
- **租约 fencing**：`Claim` / `Heartbeat` / `Release` / `UpdateClaimed` / `FenceRunUpdate` / `workflowWrite` 要求调用方提供当前 `Owner + Token + RunID`（token 以本地侧车为准，#342 起）；`workitem.Update` 拒绝状态字段变更。
- **恢复释放绕过 owner/token**：`ReleaseOptions.ForExpired` / `ForOrphan` 是 `workloom recover` 专用的恢复路径——要求证据（`lease_until < now` / 绑定 run 缺失）成立才释放，不要求 owner/token；#342 起新增 run-bound 释放 `ForCompleted` / `ForRefused`，以 run 记录为证明（`BoundRunID` + 终态 / 拒绝证据），同样不要求 owner/token，且不得误杀更新的 claim（[internal/workitem/claim.go:100-122](file://internal/workitem/claim.go#L100-L122)、[internal/workitem/claim.go:448-563](file://internal/workitem/claim.go#L448-L563)）。
- **审批消费原子性**：`approval.ConsumeTx` 永远在调用方写事务（典型是 `changeStatus` 的 Guard）内调用；任一字段不符 abort 整单。
- **审批失效同源**：`approval.InvalidateForStatusTx` 只处理同 `WorkItemID` + 同 `RequestedStatus` + 未 consumed/未 invalidated + 未 rejected 的审批；通过 `Tx.Staged(rel)` 跳过本事务已暂存文件。

## 并发模型

- **单进程互斥**：项目级共享 / 排他锁（`internal/storage/lock.go`）；POSIX `flock` / Windows `LockFileEx`；`ctx.Done()` 立即返回。
- **跨进程 CAS**：每个 `PutYAML` / `AppendJSONL` / `AppendJSONLRaw` 携带 `Expect`；写锁内重读 + 重校验。
- **租约 token**：`newToken` 返回 16 随机字节的 hex 编码（32 字符，128 bit，[internal/workitem/claim.go:1031-1037](file://internal/workitem/claim.go#L1031-L1037)）；**#342（v0.1.4）起不落受管树**——`Claim` 把 token 写进同一事务内的本地侧车 `local/leases/<id>.token`（`stageToken`，`ExpectAny` 容忍中断残留；释放时 `dropToken`），持久化的 `scheduling/<id>.yaml` 与 `workitems/<id>.yaml` 不携带 token；`Heartbeat` / `Release` / `workflowWrite` 经 `tokenFromTx` 对照侧车校验，侧车缺失时回落 persisted 值直到 claim 轮换（[internal/workitem/lease_token.go:13-49](file://internal/workitem/lease_token.go#L13-L49)）。过期由 `doctor` 报告、`recover` 释放；本地操作者（dispatch tick、`workloom recover`）经 `Store.LeaseToken` 读取当前 token（[internal/workitem/lease_token.go:78-100](file://internal/workitem/lease_token.go#L78-L100)）。
- **不要跨设备同时领取**：设备交接前必须停写（README + `config` 卡的 Schema 与错误契约）。

## 工作流编码规则（M3）

- **条件白名单**：`factWhitelist` 是唯一字段集合；未知字段在 `Parse` 报错，**不**运行时。
- **运算符白名单**：`==` `!=` `<` `>` `in` `exists`；`<` `>` 仅 int；`in` 仅 string；`exists` 仅 `workitem.parent_id`。
- **字符串字面量**支持单/双引号；`in` 字面量去重；空成员拒绝；引号不平衡在 `Parse` 报错。
- **复合表达式拒绝**：`&&` / `||` / `()` 在 `parseCondition` 显式拒绝（`compound expressions are not supported; conditions are a single comparison`）。
- **模板渲染**：`Render` / `ExpandEnv` 严格失败，缺失变量列出全部（去重升序），不返回部分输出、不静默空串。
- **环境变量不落盘**：`Parse` 不解析 `$VAR`；`ExpandEnv` 在使用时由调用方（M6 hook 执行）解析；workflow 包**没有**写盘路径。
- **LKG 缓存路径**：`.devsys/.cache/workflows/<id>.md`，本地、可删除、可重建、不提交；`.cache/` 在 `.gitignore` 与 `search` 排除表内。
- **解析 ID 形状校验**：`^[a-z][a-z0-9-]*$`；`Resolve` 在文件 IO 前先校验（防 `../` / 大写 / 斜杠）。
- **gate fail-closed**：`Policy.CheckGate` 列全所有 unmet 项，永不 fail-open；`RequireApproval` 在 M3.3 阶段恒 `false`，由 M3.7 接 `approval.MatchingGate`（[internal/approval/approval.go:369-385](file://internal/approval/approval.go#L369-L385)）；b89ffae 起 `GateEvidence` 新增 `ApprovalNote` 字段，`CheckGate` 在 `RequireApproval` 缺失且 `ApprovalNote != ""` 时把这条说明追加到 missing 文案末尾（[internal/workflow/gate.go:18-21](file://internal/workflow/gate.go#L18-L21)、[internal/workflow/gate.go:73-77](file://internal/workflow/gate.go#L73-L77)），判定与退出码不变；#342 起 missing 文案附补救命令（`artifact %q is required — register one: workloom artifact register …`、缺 comment 给 `workloom workitem comment …`），让被拒的 claim 直接知道下一步。
- **质量门计分（#342）**：`ScoreQuality` 的长度分量用 `weightedLen` 计显示宽度——中日韩表意文字按双倍计（`unicode.Is(unicode.Han, r)`），避免中文标题/描述被阈值静默扣分；验收语言分量由结构化 `acceptance_criteria` 直接满足（有 criteria 不再重复要求「验收 / acceptance」关键词）；改进文案附补全命令（[internal/workflow/quality.go:29-46](file://internal/workflow/quality.go#L29-L46)、[internal/workflow/quality.go:77-98](file://internal/workflow/quality.go#L77-L98)）。

## 审批编码规则（M3）

- **生命周期事件**：`approval_requested` / `approval_approved` / `approval_rejected` / `approval_consumed` / `approval_invalidated`，全部走 `domain.Event`。
- **消费在 Guard 内**：CLI 不暴露「单独消费」子命令——`approval reject` 通过 `workitem.Transition` 的 Guard 完成状态变更（[internal/cli/cli.go:944-978](file://internal/cli/cli.go#L944-L978)）。
- **同源失效**：离开 `from` 状态时 `InvalidateForStatusTx` 把同源未消费、未失效、未 rejected 审批标记为 `invalidated_at`，事件并入同批。
- **scope 双值**：`stage_gate`（门禁）/ `action`（危险动作，M16.2 后接入消费）；`Request` 校验 `scope == action` 时不能携带 `Stage`。
- **重复请求拒绝**：`findOpenApproval` 防同 (work item, stage, requested status) 已有未消费、非失效、非 rejected 开放审批，避免永悬。

## next 编码规则（M3）

- **纯函数**：`Evaluate(Input) Report` 不持状态、不访问 storage；CLI `workloom next` 负责组装 Input。
- **固定优先级**：`recover_claim` → `review` → `start` → `start_backlog` → `milestone_review` → `report_done`，先命中先返回。
- **风险信号顺序**：过期租约 → 孤儿领取 → 不可读调度文件 → 滞留审查 → 阻塞 → 元数据非法 → 策略非法 → 待决审批 → 检查受限。
- **exit 恒 0**：评估成功即 0，便于脚本按 `verdict` 分支。
- **不可信状态不输出业务事实**：待恢复事务或无锁文件时 `InspectionOK = false`，CLI 不列举 workitems。
- **b89ffae 与 claim 同源**：`next.QualityBlocks(items, PolicySource)` 调 `workflow.ScoreQuality` + `policy.QualityGateBlocks` 命中时产出 `RiskQualityBlocked`，`recommend` 在 `ActionStart` 推荐但 reason 写明 `score X below min_score Y + improvements`；CLI `workloom next` 与 `project status` 同样使用这条路径。
- **b89ffae default_policy 单一解析点**：`app.policyForWorkItem(ctx, wi)` 是项目级 `default_policy` 的唯一入口；未绑定策略实例的工作项按它过质量门/阶段门/提示词/工作区钩子；config.yaml 非法或默认策略缺失时 claim fail closed。

## 本批（M#337，commit 362b637）

M#337 在工作项读取路径与对账探针两侧各加了一处「不可信集合的稳定序列化 / 收集语义」，对应的编码约定：

- **空集合非 nil**：`workitem.Store.List` 把 `items` 初始化为 `items := []*domain.WorkItem{}`（[internal/workitem/workitem.go:133-171](file://internal/workitem/workitem.go#L133-L171)）。所有「多条记录读」家族的入口契约改为：空集合返回 `(non-nil empty slice, nil)`；下游 `len(...) == 0` 判定与 JSON 序列化 `[]` 不再需要 nil 守卫。这与 `reconcile.readAllWorkitems` 仍可 nil 的边界**有意保留**：对账子路径需要「无文件」与「空文件集合」区分，`Store.List` 面向消费者统一非 nil。
- **解码失败继续扫**：reconcile 的 `readAllWorkitems` / `buildProposals` 在 `storage.Inspect` 回调内 `domain.DecodeYAML`：成功 → 追加；失败 → `InvalidFile{Path: rel, Err: derr.Error()}` + `continue`。**不**抛错、**不**写盘、**不**触发 `Recover`。这是与「事务内 `DecodeYAML` 失败 → `ErrConflict`」的对比：探针路径只需「完整不可信集合」，写路径必须 fail-closed。
- **`RepairDryRun` fail-closed**：`buildProposals` 返回 `len(invalid) > 0` 时 `RepairDryRun` 直接 `fmt.Errorf("cannot plan repairs: %s", …)` 拒绝（[internal/reconcile/reconcile.go:320-333](file://internal/reconcile/reconcile.go#L320-L333)）——在不可信树上构造的 plan 不可信。错误信息列出全部无效文件，便于人工定位。`RepairApply` 永远不会在 `InvalidFiles` 路径上被调用。
- **CLI exit 4 收敛**：CLI doctor `runDoctor` 在人类模式打 `INVALID  <path>  <err>` 行（[internal/cli/diagnostics.go:157-159](file://internal/cli/diagnostics.go#L157-L159)）；`--json` 编码完整 report 后若 `len(InvalidFiles) > 0` 同样 `exitWithCode(CodeInvalid)`（[internal/cli/diagnostics.go:133-136](file://internal/cli/diagnostics.go#L133-L136)），人类模式末尾同样 `exitWithCode(CodeInvalid)`（[internal/cli/diagnostics.go:172-174](file://internal/cli/diagnostics.go#L172-L174)）。`INVALID` 行是 CLI 侧的诊断输出，**不**改 `Invalidf(KindInvalid)` 的语义。`next` / `prime` / `project status` 同路 `Invalidf(KindInvalid)`，exit 4 / `KindInvalid` 全链路一致。
