# 执行命令族
本卡描述 M6 在 `internal/app.Service` 落地的**执行层命令族**——`WorkspacePrepare / Remove / List`、`Dispatch`、`RunExec`、`RunPrompt`、`RunVerify`、`RunFinish`；每条都是 CLI / MCP 双入口共用的业务入口，执行层的 `internal/{harness,workspace,dispatch,retry,prompt}` 在这里被串成一次 attempt 的完整生命周期。**本轮（v0.1.9）**并入两条 onboarding 入口 `Setup` 与 `MCPInstall`（只编排既有 Service 方法与文件读写，不发起 attempt），并给 `RunVerify` / `RunFinish` 补上 Git 可选的 `Skipped` 分支。

## Dispatch（[internal/app/dispatch.go](file://internal/app/dispatch.go)）

`Service.Dispatch(ctx, DispatchRequest)` 是 §4.8 调度 tick 的统一入口。流程：

```text
mergeConflict(root)                 # M8.2：未解决 merge 时阻断整个 tick（blocked + notice）；探针失败降级为 notice，不伪装为 conflict
  ↓ blocked
return Preconditionf("dispatch blocked: …")    # exit 3；dry-run 同门，recover 前拦下，replay/到期释放等下一 tick
  ↓ ok（notice 可能附 unmerged 路径/未完成 merge 名）
storage.Recover(ctx)
  ↓
retrySweep(ctx, items, req)       # 失败/超时/停滞 attempt 收尾，可复现退避
  ↓
dispatchCaps(ctx, items)          # ResolveCaps(policies) → dispatch.Caps
  ↓
Plan(in)                          # dispatch.Plan 纯函数；输出 Report{Decisions, Started}
  ↓
对每个 Decision.Action == start 的候选：
  dispatchOne(ctx, wiID, command, ...) # claim → workspace prepare → spawn → mark running
```

`retrySweep`（[internal/app/dispatch.go:478-570](file://internal/app/dispatch.go#L478-L570)）：

- 读 `.devsys/runs/*.yaml` 找到每个 `WorkItemID` 当前 attempt 的 `Run`。
- `sweepTrigger(run, threshold, now)`：
  - exit code != 0 → `failed`，可重排。
  - `TimedOut == true` → `timeout`，可重排。
  - `lastProgress(now - threshold) < now` → `stalled`，先结束 attempt 再重排。
  - cancelled → 只释放租约，不重排。
- `queueNextAttempt` 计算 `retry.Delay(base, max, attempt, workitemID)` 给下一次 attempt 设 `next_attempt_at`；达到 `policy.limits.max_attempts` 上限则释放租约，记 `attempts_exhausted` 事件。

`dispatchOne`（[internal/app/dispatch.go:288-353](file://internal/app/dispatch.go#L288-L353)）：

- `workitemClaim`（同事务）拿租约；claim 失败 → 释放回 ready / blocked（按原状态）。
- `WorkspacePrepare` 在 attempt 启动前确保 worktree 存在；run 记录与 workspace 绑定。
- `defaultSpawner` 调 `os/exec.Command` 启动子进程；`attempt` 在 stdout/stderr log 文件落地。
- `markRunning`（[internal/app/runexec.go:568-588](file://internal/app/runexec.go#L568-L588)）写 `run.status=running`。


**M8.3 run 流回落**：tick 推断下一轮/最近一轮/最近 exit/已历阶段时调 `readRunStream(root, runID)`（[internal/app/runstream.go:91-115](file://internal/app/runstream.go#L91-L115)）——先查 `.devsys/runs/<id>.jsonl`，缺失则回落到 `.devsys/archive/runs/<id>.jsonl`（归档只收终态 run，活流此后不再写入，live-wins-or-fallback 严格成立；torn tail 仍返回断尾前的记录）。M8.4 无关此路径。

## RunExec（[internal/app/runexec.go](file://internal/app/runexec.go)）


`Service.RunExec(ctx, RunExecRequest)` 驱动一次 attempt round：

```text
Workspace.Prepare(run.Workspace)        # 根内不变量 + symlink 逃逸校验
  ↓
RunHook(before_run, ctx)                # before_run 失败 → abortAttempt（run.failed + workspace_hook_failed 事件）
  ↓
prompt.Assemble(...)                    # Sectioned text + Hash + Refs
  ↓
writePromptFile(...)                    # .devsys/local/runs/<id>/round-<N>.md（可选）
  ↓
harness.ByName(req.Harness).Start      # spawn + 流 + stdin 投递
  ↓
loop Lines() → stream.write + sink     # 每 128 行 sync；控制记录立即 sync
  ↓
Session.Wait(ctx) → Result              # 退出码 / timed_out / canceled / err
  ↓
terminalStatus(res) + recordExecOutcome # succeeded/failed/timeout/stalled
  ↓
advancePhase(stopped) + markFinished
```

关键常量：

- `syncEvery = 128`（[internal/app/runexec.go:25](file://internal/app/runexec.go#L25)）：每 128 行 + 控制记录 + 末次 flush——crash 至多丢 127 行。
- `stopGrace = 10 * time.Second`（[internal/app/runexec.go:29](file://internal/app/runexec.go#L29)）：stop 信号发出后给 attempt 10s 自洽退出。
- `continuationDelay = 30 * time.Second`（[internal/app/runexec.go:34](file://internal/app/runexec.go#L34)）：干净轮次写 `continuation_due_at`，M6.4 dispatch 调度。
- `runStream`（[internal/app/runexec.go:788-811](file://internal/app/runexec.go#L788-L811)）：流式事件 writer；`openRunStream` 重建断尾（[internal/app/runexec.go:758](file://internal/app/runexec.go#L758)）。

**行级流**：每行 `Line` 经 `stream.write` → `tx.AppendJSONLRaw` 落到 `.devsys/runs/<id>.jsonl`；同时镜像给 `RunExecRequest.Sink`（CLI sink → stdout/stderr；MCP sink 走 SDK 流）。

**阶段记录**：`advancePhase(stream, runID, phase)` 写 `recordExecPhase` 事件——phase ∈ {`workspace_prepared`, `prompt_assembled`, `run_started`, `run_stopped`, `run_finished`}。`run_exec_started` 事件携带 `adapter / command / argv / cwd / timeout_ms`；`run_finished` 携带 `exit_code / timed_out / canceled / duration_ms`。

**终止守卫**：用户 Ctrl-C 或 `--timeout` 到期 → `signal.NotifyContext` 取消 → `Session.Stop(ctx)` → `killProcessTree`（POSIX 进程组 / Windows Job）。POSIX 先 `SIGTERM`，`stopGrace` 后再 `SIGKILL`；Windows 立即 `TerminateJobObject`。

## Next（[internal/app/next.go](file://internal/app/next.go)）

`Service.Next(ctx)` 是 `workloom next` / MCP `workitem_next` 的统一入口——**只读、零写入**：不写 lock、不 recover、不创建文件、不动 `.devsys/` 任何东西。本批把质量门与 claim 同源纳入 `Next` 的判定：

```text
reconcile.Doctor(ctx, root)               # 检 pending transactions / 不信任事实 → 报告降级
  ↓
config.Diagnose(root)                     # 抽 metadata + config；md.Config.DefaultPolicy → in.DefaultPolicy
  ↓
workflow.Load(root)                       # plain read；解析失败的策略仍计入 present/parsed
  ↓
policyIDs(policies) → in.PolicyIDs        # 列出项目里所有声明的策略名
  ↓
for wi in in.WorkItems:
  if wi.Workflow.ID != "" && !present[wi.Workflow.ID]:
    in.PolicyProblems += "wi references missing policy %q"
  if in.DefaultPolicy != "" && !present[in.DefaultPolicy]:
    in.PolicyProblems += "default_policy %q has no .md"
  ↓
in.QualityBlocks = next.QualityBlocks(items, resolvePolicy)   # 与 claim 同源
  ↓
return next.Evaluate(in), items, nil
```

关键不变式：

- **policy 体走 `workflow.Load` 的 plain read**：解析失败的策略仍进 `parsed[id]`（仅当 `res.Policy != nil`），但其 `Issue` 已是 `PolicyProblems` 风险——`claim` 在质量门里直接拒绝，本卡里 `Next` 看到的就是「已有 risk + 该 wi 走不进 `QualityBlocks` 的 happy 路径」。
- **resolver 由 `next.QualityBlocks` 闭包组装**：先取 `wi.Workflow.ID`，为空则回落到 `DefaultPolicy`，都为空 → 返回 `("", "", nil)`，`Next` 把该 wi 当作「无策略管辖」参与判定（与 `claimNotice` 同源语义）。
- **`retry_queued` 也参与门判**：本批新增 `retry_pending` 风险种类，对应 retry 时点已排到但尚未执行的工作项（与 `next.Evaluate` 的 ready 判定正交）。
- **推荐原因（recommended reason）**：被门挡下的 wi 在 Report 里带 `quality_blocked` 风险 + 形如 `workitem update --id <id> --acceptance <…> --expect <hash>` 的补救命令（与 `claim` 失败时 `run fail` 给出的命令同源，便于 agent 一键 recover）。

CLI / MCP 语义：`workloom next` 始终 exit 0（与 `project status` / `project blueprint` 同族），推荐动作 + 风险细节走 stdout / JSON envelope；MCP `workitem_next`（session 档，core/standard 都暴露）通过 `fail` 把 `Next` 错误翻译为 `toolError.code`。

## RunFinish（[internal/app/run.go:295-414](file://internal/app/run.go#L295-L414)）

`Service.RunFinish(ctx, RunFinishRequest)` 写终态 attempt：

```text
read Run                          # expected version 守卫（checkExpect；不符 → exit 4 invalid）
isTerminalRun(status)             # 已终态 → Preconditionf("run %s already ended as %s") → exit 3
  ↓
if Outcome == RunSucceeded:
    check = verifyCompletion(r)   # 本轮：Skipped=true 表示 Git 证据不适用
    switch case check.Advanced, req.Force, check.Skipped:   # run.go:321
      → r.Verification.Advanced = check.Advanced（Skipped 时仍为 false）
        req.Force → r.Verification.VerifiedBy = &req.By
      否则:
        reason = check.Reason（空则 "the completion check found no advance"）
        refuseCompletion(ctx, r, req.Actor, reason, check)
        return Preconditionf("run %s cannot be marked succeeded: …")  # exit 3
  ↓
r.Status = Outcome; r.FinishedAt = now; req.Note → r.Result.Errors
事件 eventType：completion_verified（推进）/ completion_overridden（force）/
              run_finished（failed / canceled，以及本轮 Skipped 的 succeeded）
succeeded → 释放本 run 绑定的租约（ForCompleted，只有 lease.RunID == r.ID 才动）
  ↓
return RunGet(r.ID)               # 返回最新 RunView
```

前置 Usage 校验（`Usagef` → exit 2）：`RunID/Actor/Reason` 任一为空；`Outcome` 不在终态枚举；`Force` 未带 `By`（`forcing an outcome requires --by <reviewer>: an exception has to be traceable`）。

终态枚举（[internal/app/run.go:254-262](file://internal/app/run.go#L254-L262)）：`RunSucceeded / RunFailed / RunTimedOut / RunStalled / RunCanceled`。`RunExec` 在收到 `Result{TimedOut/Canceled}` 时自己升 timeout / canceled；`RunFinish` 处理 succeeded / failed / canceled 三类由 caller 决定的结局。

**本轮（cc5de1f，Git 可选）**：`succeeded` 的守卫分支加了 `check.Skipped`（[internal/app/run.go:321](file://internal/app/run.go#L321)）——非 Git 项目或目录工作区里 `run complete` **不再被拒绝**：run 正常写 succeeded 且 `Advanced` 保持 false，事件仍是 `run_finished`（[:362](file://internal/app/run.go#L362)），文案 verdict 记 `git check not applicable`（[:371](file://internal/app/run.go#L371)）。Git + 已绑定 worktree 的路径完全不变。

`refuseCompletion`（[internal/app/runverify.go:87-114](file://internal/app/runverify.go#L87-L114)）：

- 保留 run 记录——写 `Verification.Advanced=false` + `Verification.HeadSHAAtComplete=check.CurrentHead`，claim_head / current_head 都留着；**run 不改状态、保持非终态**（留给 reviewer 收尾），workspace binding 也不动。
- 写事件 `completion_refused`（`subject_type=run`，content `claim head <sha>, current head <sha>: <reason>`）。
- `routeToReview`（[internal/app/runverify.go:116-180](file://internal/app/runverify.go#L116-L180)）先把本 run 绑定的租约还给 reviewer（`ForRefused` + `BoundRunID=r.ID`，只动这一条租约），再走**与手工 transition 相同的 stage gate**：门禁挡住 → 写 `review_gate_blocked` 事件并保持原状态（返回 `routed=false`，CLI 文案据此改口）；通过 → transition 到 `review`（reason `completion refused: <reason>`）——`next.Evaluate` 的 `stale_review` 风险随后把 reviewer 拉进来。**没有** `review_routed` 事件。

`Force --by reviewer` 路径：仅 `Outcome=RunSucceeded` 时接受；`RunFinish` 跳过守卫的分支直接写 succeeded + `VerifiedBy=reviewer`，并写事件 `completion_overridden`（content 末尾 `; accepted by <reviewer>`）——把人工复核作为最后一道闸门。

## Setup（本轮新增，[internal/app/setup.go:43-198](file://internal/app/setup.go#L43-L198)）

`Service.Setup(ctx, template)` 是 `workloom setup` 的唯一业务入口，**只编排既有 Service 方法**（不新增第二条写路径）：

```text
template 空 → DefaultSetupTemplate（"quick-fix"）；不在 WorkflowTemplates() → Usagef（exit 2）
1 ProjectCreate(ctx, "")           → init 行（created N paths / already initialized）
2 .devsys/workflows/<t>.md 存在 → workflow 行 Skipped（"<t> already present; left in place"）
  不存在 → WorkflowInitTemplate(t)（失败 → workflow 行 + 原错误）
3 Wire(ctx, false) + WriteSkill()  → wire 行（created/updated AGENTS.md；skill wrote N files / already installed）
4 config.Diagnose(root)            → 有问题 → config 行 + Invalidf(KindInvalid)（exit 4，Next=`workloom config check`）
5 WireCheck()                      → 属 app 的 5 行（.devsys / schema / registry / AGENTS.md / skill）任一 !OK
                                     → wire-check 行 + Preconditionf（exit 3，Next=`workloom wire --check`）
                                     mcp 行只记录（不影响 Ready）
6 SessionStart(ctx, {Compact:true})→ prime 行（推荐命令 / reason）
7 ProjectBlueprint(ctx)            → nil → blueprint 行 "no blueprint declared; ask for project goals, then
                                     `workloom project update --blueprint-artifact <artifact-id>`"；非 nil → artifact id
8 reconcile.Doctor(ctx, {})        → InvalidFiles → doctor 行 + Invalidf(KindInvalid)
                                     否则 doctor 行（clean / N pending transactions → `workloom recover` / inspection note）
  ↓
Ready = true（以上硬步骤全部通过）；Next = 蓝图缺失提示（优先）拼上 session 推荐命令
```

- **幂等**：`Wire` 三次运行字节一致、`WorkflowInitTemplate` 以 `storage.ExpectAbsent()` 写入、`WriteSkill` 不覆盖 hand-written 文件——重复 `setup` 的第二次运行只报 `already initialized` / `Skipped` / `already wired`。
- **失败即停**：任一步返回 error，后续步骤不再执行，`view.Steps` 记录失败点，`Ready=false`（`blueprint` / `mcp` 两行 `OK=false` 只是报告，不 gate `Ready`）。
- **不注册 MCP**（`setup` 只在报告里显示 mcp 检查行），也不声明蓝图——两件事分别是 `workloom mcp install` 与 `workloom project update --blueprint-artifact`。
- CLI 渲染（[internal/cli/setup.go:17](file://internal/cli/setup.go#L17)）：人类可读打 `[v]/[x] <name>: <detail>` + `Workloom is ready.` + `next: …`；`--json` 走 `{ok, …SetupView, error?}`；`--quiet` 抑制人类可读行。

## MCPInstall（本轮新增，[internal/app/mcpinstall.go:63-162](file://internal/app/mcpinstall.go#L63-L162)）

`Service.MCPInstall(ctx, req)` 把 `devsys` 条目注册进 MCP 客户端配置——**纯文件读写，不调用执行层**：

```text
scope 空 → "user"；非 user/project → Usagef("unknown scope %q (expected user or project)")
bin = req.Bin 或 os.Executable()（ToSlash）；home = req.HomeDir 或 os.UserHomeDir()
未知 client → Usagef("unknown client %q (expected codex, claude or opencode)")
req.Apply && req.DryRun → Usagef("`--apply` and `--dry-run` are mutually exclusive")
writing := Apply && !DryRun（默认两者皆 false → 预览）
  ↓ per client（顺序 codex → claude → opencode）
未检出（无 config 文件且 binary 不在 PATH）且未显式 --client → status=not-detected
  ↓ Announce(client, path)              # CLI 打印 "target <client>: <path>"
codex    → installCodexTOML（追加/替换 [mcp_servers.devsys] 及其子表）
claude   → installClientJSON(path, "mcpServers", claudeMCPInstallEntry(bin), …)
opencode → installClientJSON(path, "mcp", opencodeMCPInstallEntry(bin), …)
  ↓
changed && !writing → "planned"；changed → "installed"；未变 → "skipped"；err → "failed"（其余客户端继续）
```

- 注册条目由 `mcpServeArgs()`（[internal/app/mcpinstall.go:55-57](file://internal/app/mcpinstall.go#L55-L57)）给出：`["mcp","serve","--profile","session,executor","--tier","core"]`；条目**名仍是 `devsys`**——二进制改名 `workloom` 不改变注册名与配置键。
- 目标路径（[internal/app/mcpinstall.go:167-182](file://internal/app/mcpinstall.go#L167-L182)）：user scope = `~/.codex/config.toml` / `~/.claude.json` / `~/.config/opencode/opencode.json`；project scope = `<root>/.codex/config.toml` / `<root>/.mcp.json` / `<root>/opencode.json`（即 `wire --check` 扫的同一组文件）。
- **拒绝路径（fail closed，即使 `--force`）**：Codex 行内 `mcp_servers = {...}` 表与时提示 ``config uses an inline mcp_servers table; add the [mcp_servers.devsys] block manually, or use `workloom wire --print-mcp codex` ``；非严格 JSON（JSONC / 尾逗号）提示 ``not valid strict JSON (comments or trailing commas are refused, never rewritten): edit manually, or use `workloom wire --print-mcp` ``——外科式写入保证插入点之外的字节逐字保留。
- 退出语义：`MCPInstall` 只在参数错（`Usagef`）/ 定位二进制失败（`Internalf`）时返回 error；**单个客户端失败不影响整次命令**——该行 `Status=failed` + `Detail=<err>`，CLI exit 仍为 0。

## Dispatch 预检与拒绝落账（本批 #336）

`dispatchOne` 在 `workitemClaim` 之前先调 `preflightAttempt`（[internal/app/dispatch.go:354-390](file://internal/app/dispatch.go#L354-L390)）：

- `assigned_harness` 非空 → 必须 `harness.ByName` 已知名；未知名 → `Usagef`。
- 否则 shell 模式：必须 `dispatch_command` 非空**或**带 `--` 命令；都缺 → `Usagef`。
- 非 shell harness：必须 `Probe` 返回成功；`Probe` 未安装 → `Usagef`。

拒绝**直接**写 `notice`，**不**调用 `workitemClaim`，因此不占 concurrency cap；只有预检通过的 attempt 才走 `claim → workspace prepare → spawn → mark running`。这与 `retrySweep` 的"先收尾再排期"思路一致——本批把"claim 之前就拒"也正式化。

## `refuseAttempt` 拒绝落账（本批 #336）

`internal/app/runexec.go:469-547` 新增 `refuseAttempt`——`RunExec` 在 `openRunStream` 之前 Usage/Precondition 拒绝的统一落账路径：

```text
Usagef / Preconditionf → refuseAttempt(ctx, r, req, cause)
  ├─ tx.Write 更新 run: status=failed, finished_at, result.errors=<cause>
  ├─ 写 run_failed 事件（subject_type=run, content=cause）
  └─ releaseFailedClaim(wiID, token, req, cause)  ← 与 retrySweep 同语义
```

- `abortAttempt`（before_run 钩子失败时调）改接入 `refuseAttempt`，行为统一。
- **禁止**把空 run 标 `finished`——证据保留，reviewer 仍能看到 attempt 上下文。
- ad-hoc `run exec` 没有租约时只记录失败（不调 `releaseFailedClaim`，因为没有 lease）。

CLI/MCP 翻译：`refuseAttempt` 内部已经完成所有落账；调用方拿到原始 Usage/Precondition error 返回，CLI exit 仍为 2/3、MCP `code` 仍为 `usage` / `precondition`。

## `workflow init --template` 与 `WorkflowInitTemplate`（本批 #337）

`internal/app/workflow_init.go`（新文件，package app）从仓库根 `templates.go` 通过 `//go:embed docs/examples/workflows/*.md` 暴露的 `workloom.WorkflowTemplatesFS` 读模板；提供两个方法：

- `WorkflowTemplates() []string`——按 id 排序返回（现行为 4 个：`architecture-change`、`feature-development`、`quick-fix`、`reference-template`，来自 `docs/examples/workflows/*.md` 的 go:embed）。
- `WorkflowInitTemplate(ctx, id)`——读 `<id>.md`、写 `.devsys/workflows/<id>.md`：
  - 未知 id → `Usagef("unknown workflow template %q (available: …)", id, …)`。
  - 已存在（`tx.ReadForExpect` 返回 exists=true）→ `Usagef("policy %q already exists at %s; edit it in place instead of re-initializing", id, display)`。
  - 写事务 `tx.Put(rel, data, storage.ExpectAbsent())`——以 absent 为期望，存在即冲突（与其它写路径同一版本守卫）。

CLI 路由（`internal/cli/cli.go`）：`workflow init --template <id>`（usage 列 4 个模板 id）；`runInit` 第 1 步提示从「写 workflows/<id>.md」改为指 `workflow init --template`。

```bash
$ workloom workflow init --template quick-fix
{"template":"quick-fix","path":".devsys/workflows/quick-fix.md"}
```
