# 执行命令族
本卡描述 M6 在 `internal/app.Service` 落地的**执行层命令族**——`WorkspacePrepare / Remove / List`、`Dispatch`、`RunExec`、`RunPrompt`、`RunVerify`、`RunFinish`。每条都是 CLI / MCP 双入口共用的业务入口；执行层的 `internal/{harness,workspace,dispatch,retry,prompt}` 在这里被串成一次 attempt 的完整生命周期。

## Dispatch（[internal/app/dispatch.go](file://internal/app/dispatch.go)）

`Service.Dispatch(ctx, DispatchRequest)` 是 §4.8 调度 tick 的统一入口。流程：

```text
mergeConflict(root)                 # M8.2：未解决 merge 时阻断整个 tick（blocked + notice）；探针失败降级为 notice，不伪装为 conflict
  ↓ blocked
return Preconditionf("dispatch blocked: …")    # exit 3；dry-run 同门，recover 前拦下，replay/到期释放等下一 tick
  ↓ ok（notice 可能附 unmerged 路径/未完成 merge 名）
storage.Recover(ctx)
  ↓
retrySweep(ctx, items, req)       # 失败/超时/停滞 attempt 收尾，可复现退避
  ↓
dispatchCaps(ctx, items)          # ResolveCaps(policies) → dispatch.Caps
  ↓
Plan(in)                          # dispatch.Plan 纯函数；输出 Report{Decisions, Started}
  ↓
对每个 Decision.Action == start 的候选：
  dispatchOne(ctx, wiID, command, ...) # claim → workspace prepare → spawn → mark running
```

`retrySweep`（[internal/app/dispatch.go:369-454](file://internal/app/dispatch.go#L369-L454)）：

- 读 `.devsys/runs/*.yaml` 找到每个 `WorkItemID` 当前 attempt 的 `Run`。
- `sweepTrigger(run, threshold, now)`：
  - exit code != 0 → `failed`，可重排。
  - `TimedOut == true` → `timeout`，可重排。
  - `lastProgress(now - threshold) < now` → `stalled`，先结束 attempt 再重排。
  - cancelled → 只释放租约，不重排。
- `queueNextAttempt` 计算 `retry.Delay(base, max, attempt, workitemID)` 给下一次 attempt 设 `next_attempt_at`；达到 `policy.limits.max_attempts` 上限则释放租约，记 `attempts_exhausted` 事件。

`dispatchOne`（[internal/app/dispatch.go:231-279](file://internal/app/dispatch.go#L231-L279)）：

- `workitemClaim`（同事务）拿租约；claim 失败 → 释放回 ready / blocked（按原状态）。
- `WorkspacePrepare` 在 attempt 启动前确保 worktree 存在；run 记录与 workspace 绑定。
- `defaultSpawner` 调 `os/exec.Command` 启动子进程；`attempt` 在 stdout/stderr log 文件落地。
- `markRunning`（[internal/app/runexec.go:466-484](file://internal/app/runexec.go#L466-L484)）写 `run.status=running`。


**M8.3 run 流回落**：tick 推断下一轮/最近一轮/最近 exit/已历阶段时调 `readRunStream(root, runID)`（[internal/app/runstream.go:87-118](file://internal/app/runstream.go#L87-L118)）——先查 `.devsys/runs/<id>.jsonl`，缺失则回落到 `.devsys/archive/runs/<id>.jsonl`（归档只收终态 run，活流此后不再写入，live-wins-or-fallback 严格成立；torn tail 仍返回断尾前的记录）。M8.4 无关此路径。

## RunExec（[internal/app/runexec.go](file://internal/app/runexec.go)）


`Service.RunExec(ctx, RunExecRequest)` 驱动一次 attempt round：

```text
Workspace.Prepare(run.Workspace)        # 根内不变量 + symlink 逃逸校验
  ↓
RunHook(before_run, ctx)                # before_run 失败 → abortAttempt（run.failed + workspace_hook_failed 事件）
  ↓
prompt.Assemble(...)                    # Sectioned text + Hash + Refs
  ↓
writePromptFile(...)                    # .devsys/local/runs/<id>/round-<N>.md（可选）
  ↓
harness.ByName(req.Harness).Start      # spawn + 流 + stdin 投递
  ↓
loop Lines() → stream.write + sink     # 每 128 行 sync；控制记录立即 sync
  ↓
Session.Wait(ctx) → Result              # 退出码 / timed_out / canceled / err
  ↓
terminalStatus(res) + recordExecOutcome # succeeded/failed/timeout/stalled
  ↓
advancePhase(stopped) + markFinished
```

关键常量：

- `syncEvery = 128`（[internal/app/runexec.go:23](file://internal/app/runexec.go#L23)）：每 128 行 + 控制记录 + 末次 flush——crash 至多丢 127 行。
- `stopGrace = 10 * time.Second`（[internal/app/runexec.go:27](file://internal/app/runexec.go#L27)）：stop 信号发出后给 attempt 10s 自洽退出。
- `continuationDelay = 30 * time.Second`（[internal/app/runexec.go:32](file://internal/app/runexec.go#L32)）：干净轮次写 `continuation_due_at`，M6.4 dispatch 调度。
- `runStream`（[internal/app/runexec.go:649-654](file://internal/app/runexec.go#L649-L654)）：流式事件 writer；`openRunStream` 重建断尾（[internal/app/runexec.go:684](file://internal/app/runexec.go#L684)）。

**行级流**：每行 `Line` 经 `stream.write` → `tx.AppendJSONLRaw` 落到 `.devsys/runs/<id>.jsonl`；同时镜像给 `RunExecRequest.Sink`（CLI sink → stdout/stderr；MCP sink 走 SDK 流）。

**阶段记录**：`advancePhase(stream, runID, phase)` 写 `recordExecPhase` 事件——phase ∈ {`workspace_prepared`, `prompt_assembled`, `run_started`, `run_stopped`, `run_finished`}。`run_exec_started` 事件携带 `adapter / command / argv / cwd / timeout_ms`；`run_finished` 携带 `exit_code / timed_out / canceled / duration_ms`。

**终止守卫**：用户 Ctrl-C 或 `--timeout` 到期 → `signal.NotifyContext` 取消 → `Session.Stop(ctx)` → `killProcessTree`（POSIX 进程组 / Windows Job）。POSIX 先 `SIGTERM`，`stopGrace` 后再 `SIGKILL`；Windows 立即 `TerminateJobObject`。

## Next（[internal/app/next.go](file://internal/app/next.go)）

`Service.Next(ctx)` 是 `devsys next` / MCP `workitem_next` 的统一入口——**只读、零写入**：不写 lock、不 recover、不创建文件、不动 `.devsys/` 任何东西。本批把质量门与 claim 同源纳入 `Next` 的判定：

```text
reconcile.Doctor(ctx, root)               # 检 pending transactions / 不信任事实 → 报告降级
  ↓
config.Diagnose(root)                     # 抽 metadata + config；md.Config.DefaultPolicy → in.DefaultPolicy
  ↓
workflow.Load(root)                       # plain read；解析失败的策略仍计入 present/parsed
  ↓
policyIDs(policies) → in.PolicyIDs        # 列出项目里所有声明的策略名
  ↓
for wi in in.WorkItems:
  if wi.Workflow.ID != "" && !present[wi.Workflow.ID]:
    in.PolicyProblems += "wi references missing policy %q"
  if in.DefaultPolicy != "" && !present[in.DefaultPolicy]:
    in.PolicyProblems += "default_policy %q has no .md"
  ↓
in.QualityBlocks = next.QualityBlocks(items, resolvePolicy)   # 与 claim 同源
  ↓
return next.Evaluate(in), items, nil
```

关键不变式：

- **policy 体走 `workflow.Load` 的 plain read**：解析失败的策略仍进 `parsed[id]`（仅当 `res.Policy != nil`），但其 `Issue` 已是 `PolicyProblems` 风险——`claim` 在质量门里直接拒绝，本卡里 `Next` 看到的就是「已有 risk + 该 wi 走不进 `QualityBlocks` 的 happy 路径」。
- **resolver 由 `next.QualityBlocks` 闭包组装**：先取 `wi.Workflow.ID`，为空则回落到 `DefaultPolicy`，都为空 → 返回 `("", "", nil)`，`Next` 把该 wi 当作「无策略管辖」参与判定（与 `claimNotice` 同源语义）。
- **`retry_queued` 也参与门判**：本批新增 `retry_pending` 风险种类，对应 retry 时点已排到但尚未执行的工作项（与 `next.Evaluate` 的 ready 判定正交）。
- **推荐原因（recommended reason）**：被门挡下的 wi 在 Report 里带 `quality_blocked` 风险 + 形如 `workitem update --id <id> --acceptance <…> --expect <hash>` 的补救命令（与 `claim` 失败时 `run fail` 给出的命令同源，便于 agent 一键 recover）。

CLI / MCP 语义：`devsys next` 始终 exit 0（与 `project status` / `project blueprint` 同族），推荐动作 + 风险细节走 stdout / JSON envelope；MCP `workitem_next`（session 档，core/standard 都暴露）通过 `fail` 把 `Next` 错误翻译为 `toolError.code`。

## RunFinish（[internal/app/run.go:291-381](file://internal/app/run.go#L291-L381)）

`Service.RunFinish(ctx, RunFinishRequest)` 写终态 attempt：

```text
read Run                          # expected version 守卫
isTerminalRun(status)             # 已终态 → exit 4
  ↓
if Outcome == RunSucceeded:
    if !req.Force:
        check = verifyCompletion(r)
        if !check.Advanced:
            refuseCompletion(...) # 写 run.status=failed + workspace.unbound + workitem → review
            return error         # Kind: workflow → exit 4
  ↓
recordExecOutcome(r, ...)         # 写 terminal status + finished_at + 终态事件
finishAttempt(r, status, ...)     # Tx.Write + tx.Staged 防覆盖
```

终态枚举（[internal/app/run.go:253-261](file://internal/app/run.go#L253-L261)）：`RunSucceeded / RunFailed / RunTimeout / RunStalled / RunCanceled`。`RunExec` 在收到 `Result{TimedOut/Canceled}` 时自己升 timeout / canceled；`RunFinish` 处理 succeeded / failed / canceled 三类由 caller 决定的结局。

`refuseCompletion`（[internal/app/runverify.go:75-102](file://internal/app/runverify.go#L75-L102)）：

- 保留 run 记录（advanced=false + claim_head / current_head 都保留）——人仍能查证据。
- `routeToReview`（[internal/app/runverify.go:104-144](file://internal/app/runverify.go#L104-L144)）把 workitem 推到 `review` 状态——`next.Evaluate` 的 `stale_review` 风险信号会触发 reviewer 介入。
- 事件 `review_routed` 写明 reason / check 摘要。

`Force --by reviewer` 路径：仅 `Outcome=RunSucceeded` 时接受；`RunFinish` 跳过 `verifyCompletion` 直接写 succeeded + reviewer 身份——把人工复核作为最后一道闸门。
