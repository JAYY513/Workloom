## `storeError` 翻译（`internal/app/workitem.go:485-522`，本批新增两条分支）

所有写路径（`WorkitemClaim` / `Transition` / `Update` / `AddDependency` / `RemoveDependency` / `WorkitemRelease` / `WorkitemStart` 等）共用 `storeError` 把底层 `error` 翻译为 `*app.Error`，分支语义：

| 触发 | 翻译 | CLI 退出码 | MCP `code` | 说明 |
|---|---|---|---|---|
| `workitem.ErrBadID` | `Usagef("%v", err)` | `2` | `usage` | id 形状非法——caller 错误（id 含非法字符 / 长度异常），不是受管状态不可信 |
| `storage.ErrNotInitialized` / `workitem.ErrNotFound` / `approval.ErrNotFound` / `record.ErrNotFound` / `run.ErrNotFound` | `Preconditionf("%v", err)` | `3` | `precondition` | 项目未 init / 记录不存在 |
| `storage.ErrConflict` | `Invalidf(KindWorkitem, nil, "%v (the file changed after your read: re-read it and retry, or repeat with --latest where the command offers it)", err)` | `4` | `invalid` | CAS 写冲突——message 末尾附出路文案，避免「version conflict alone」让 operator 瞎试 |
| 其它 `error` | `Invalidf(KindWorkitem, nil, "%v", err)` | `4` | `invalid` | 受管状态不可信兜底 |

>`storage.ErrConflict` 的典型场景：`workitem.transition` / `workitem.update` 等拿了一个旧 `--expect` 哈希、或 dispatch 子进程先一步改了同一条 run 记录（`run fail` 报此错时常为该路径）。`--latest` 是单操作员场景下「重新读取」的显式表达，仍然走 CAS，不绕过不变量。

## 调用脚本分支约定

脚本与客户端**只信 `code` 字段**：

- `usage` (CLI exit 2)：修正参数（`workitem.ErrBadID` 也归此——重写 id 再发）。
- `precondition` (CLI exit 3)：运行 `workloom init` / `workloom recover` / 重新 `get` 取新 version。
- `internal` (CLI exit 1)：重试或上报。
- `invalid` (CLI exit 4)：按 `problems[]` 修复受管状态，或按 `message` 处理拒绝原因（门禁未满足、审批失效等）；`storage.ErrConflict` 时按 message 末尾的「重新读取重试 / `--latest`」出路执行。


### `ProjectUpdate.BlueprintArtifactID` 校验分类（本批新增）

| 检查 | 错误类型 | CLI 退出码 | MCP `code` | 文案 |
|---|---|---|---|---|
| `record.KindArtifact.ValidID(id)` 形态错 | `Usagef` | `2` | `usage` | `blueprint artifact id %q is not a valid artifact id` |
| `record.New(s.Root).GetArtifact(ctx, id)` 返回 `record.ErrNotFound` | `Preconditionf` | `3` | `precondition` | `artifact %q not found; register it first (…workloom artifact register --path <file> --name <name>…)` |

### `Next` 在 invalid managed state 下 `Invalidf(KindInvalid)`（本批新增）

`internal/app/next.go:29-46` 在 `len(doc.InvalidFiles) > 0` 时**直接** `Invalidf(KindInvalid, nil, "next: managed state unreadable: <file>: <err>…")` 返回 `Invalid`：

- 触发条件：`reconcile.InspectionReport.InvalidFiles` 非空——work item 文件解码错误、文件不可读等。
- 文案：列出 ≤3 条 `f.String()`（path + err），超过则追加 `(+N more)`。
- CLI 退出码：`4`（`Invalid` class）；MCP `code: invalid`。
- 语义：在 next 上下文，**verdict 由残缺的事实**推出——所以这条不写 risk，直接拒绝返回，与「基于未列出的 items 给建议」的危险等价；`prime` / `session` / `project status` 走同一 `Invalidf(KindInvalid)` 路径（`internal/cli/diagnostics.go` 的 doctor 同样：人读 `INVALID <path> <err>` 行 + `exitWithCode(4)`；`--json` 编码后亦 `exit 4`）。
