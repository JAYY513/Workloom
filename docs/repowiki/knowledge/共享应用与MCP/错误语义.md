## 调用脚本分支约定

脚本与客户端**只信 `code` 字段**：

- `usage` (CLI exit 2)：修正参数（`workitem.ErrBadID` 也归此——重写 id 再发）。
- `precondition` (CLI exit 3)：运行 `workloom init` / `workloom recover` / 重新 `get` 取新 version。
- `internal` (CLI exit 1)：重试或上报。
- `invalid` (CLI exit 4)：按 `problems[]` 修复受管状态，或按 `message` 处理拒绝原因（门禁未满足、审批失效等）；`storage.ErrConflict` 时按 message 末尾的「重新读取重试 / `--latest`」出路执行。

- **跟进任务三条全归 `usage`**：都是 caller 传来的参数不合法，修正输入即可重试；`Usagef` 的语义正是「schema 表达不了的无效输入」。父项**不存在**则走 `WorkitemGet` 的既有 `Preconditionf`（exit 3）——那是状态问题，不是参数问题。
- **路径逃逸归 `precondition` 而非 `invalid`**：文件确实存在，只是不该被这个项目读——属于「环境/前提不满足」，与 `run verify` 里的「没有 `.devsys/`」同类。若归 `invalid`（exit 4）会误导 operator 去「修受管状态」，而真正要改的是传入的 artifact id。
- **策略错配归 `KindWorkflow` 而非 `usage`**：已选策略是**受管状态的一部分**（`project.yaml.default_policy` 或实例上的 workflow id），不是命令行拼写。`KindWorkflow` 同样 `Class=invalid`（exit 4），但保留了「这与工作流有关」的展示类型，且两条文案都直接给出可执行的出路——`workflow start --id <id> --policy intake --actor <actor> --reason "classify task"`（triage 分支）与 `workflow start --id <id> --policy <recommended> --actor <actor> --reason "accept recommendation"`（高置信度分支），后者还附 `signals=` 列出命中的信号，避免「凭什么说我该换策略」无从查证。

| `config.Diagnose` 报 problems | `Invalidf(KindInvalid, problems, "invalid managed state (%d problems)")` | `4` | `invalid` |

`blueprint` 与 `mcp` 两行 `OK=false` 只是**报告**（不写、不 gate `Ready`），不产生错误——`setup` 仍 exit 0。

`MCPInstall`（[internal/app/mcpinstall.go:69-184](file://internal/app/mcpinstall.go#L69-L184)）：

| 触发 | 翻译 | CLI 退出码 |
|---|---|---|
| `--scope` 不是 user / project | `Usagef("unknown scope %q (expected user or project)")` | `2` |
| `--client` 出现未知名字 | `Usagef("unknown client %q (expected codex, claude or opencode)")` | `2` |
| `--apply` 与 `--dry-run` 同时给出 | ``Usagef("`--apply` and `--dry-run` are mutually exclusive")`` | `2` |
| `os.Executable()` / `os.UserHomeDir()` 失败 | `Internalf("locate workloom binary: %v")` / `Internalf("locate home directory: %v")` | `1` |
| 单客户端配置不可读 / JSONC / Codex 行内 `mcp_servers` 表 / 目标不是 object | **不返回 `*app.Error`**——该客户端结果 `MCPInstallResult{Status:"failed", Detail:<err>}`，其余客户端继续 | `0`（整次命令仍算成功） |
| **本批**：`--apply` 已写盘、但启动探针失败（`!OK && !Skipped`） | ``Preconditionf("registration written, but `workloom mcp serve` did not start: %s", detail)`` | `3` |

要点：`mcp install` 的「拒绝」是**结果行**语义而不是错误信封——脚本要判断必须看 `results[].status`（`installed` / `planned` / `skipped` / `failed` / `not-detected`），退出码只反映参数错与内部错。这正是「无法安全合并就 fail closed」的表达：写入被拒，但命令不整体失败。

**探针失败 ≠ 单客户端 `failed`（本批新增）**——两条路径不要混：

- 单客户端 `failed`（JSONC / 行内 `mcp_servers` 表 / 配置不可读）是**该行**的结果，其余客户端继续，整次命令仍 exit 0；
- 启动探针失败是**整次命令**的失败：`--apply` 已经把 `devsys` 条目写进配置文件，但注册出来的命令起不来（[internal/app/mcpinstall.go:180-182](file://internal/app/mcpinstall.go#L180-L182)）→ `Preconditionf`（exit 3），**配置保留**（`registration written, but … did not start`）让 operator 决定；报告行与 `probe` 字段照常输出（人类模式先打报告再返回错误，[internal/cli/mcp.go:113-116](file://internal/cli/mcp.go#L113-L116)）。
- 探针只在有客户端被处理时跑：`--dry-run` 也跑但**不写盘**，因此不会产生这条退出码；`DEVSYS_MCP_PROBE=0` → `Skipped`（不 spawn）——`Skipped` 属「没检查」，既不触发 exit 3，也绝不当作通过。
