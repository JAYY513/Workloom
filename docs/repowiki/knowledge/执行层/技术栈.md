# 执行层 · 技术栈

执行层在 Go 1.26 + 现有依赖之上**只新增一个非默认依赖**：`golang.org/x/term`（vendored），仅用于 POSIX `proc_unix.go` 的 `IsTerminal` 探针；进程树终止由 `os/exec` + 平台 syscall（POSIX `Setpgid` + `kill -PGID` / Windows `JobObject` + `TerminateJobObject`）实现，**不引入**第三方进程管理库。其余选型都是 Go 标准库。

## 选型一览

| 组件 | 选型 | 版本/来源 | 用途 |
|---|---|---|---|
| 进程创建 | `os/exec` | Go 标准库 | Shell 与三个 CLI 适配器的 argv 启动；`Cmd.Stdin` / `Cmd.Stdout` / `Cmd.Stderr` 三路分流；`Cmd.Wait()` 收集退出 |
| 平台 syscall | `syscall` | Go 标准库 | POSIX `SysProcAttr{Setpgid: true}` 创造进程组；`syscall.Kill(-pid, SIGTERM/SIGKILL)` 终止整棵进程树 |
| Windows Job | `golang.org/x/sys/windows` | vendored（随 `golang.org/x/term` 引入） | `CreateJobObject` + `SetInformationJobObject`（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）+ `AssignProcessToJobObject` + `TerminateJobObject` |
| TTY 探针 | `golang.org/x/term` | vendored（[go.mod](file://go.mod) 新增） | POSIX `IsTerminal(fd int) bool` 用于 shell 适配器的 Probe 报告 host shell；不影响 Windows 路径（Windows 走 `cmd.exe`） |
| 路径净化 | `path/filepath` + `os.Lstat` | Go 标准库 | `internal/workspace/path.go` 的 `resolveExisting` 沿最深存在祖先解 symlink；不存在的尾部无法被 symlink 替换 |
| 行缓冲 | 自实现 `lineWriter`（64KB chunk） | Go 标准库 `bufio` 同形 | `internal/harness/shell.go` 把字节流切成 `Line{Stream, Text}`；超长行按 rune 边界切 chunk 永不断 rune；UTF-8 安全 |
| Hash | `crypto/sha256` | Go 标准库 | `prompt.Prompt.Hash` 由 `Assemble` 渲染后 `sha256.Sum256(text)` 得到；与 `storage.HashBytes` 共用同一编码 |
| YAML | `gopkg.in/yaml.v3` | vendored（M0 沿用） | Policy / Hook 配置的解析入口（`internal/workflow/parse.go`）由工作流策略持有；执行层不直接解析 |
| 平台拆分 | `proc_unix.go` / `proc_windows.go` | Go build tag `_unix` / `_windows` | `internal/harness` 同名同签名 `killProcessTree(cmd *exec.Cmd) error`；POSIX 走进程组，Windows 走 JobObject |
| UTF-8 行尾 | `\n`（LF） | Go 标准库 `strings.Builder` | `prompt.Assemble` 与 `harness.shell` 都按 LF 切行；shell 适配器读取时 `bufio.Scanner` 不切 CRLF |

## 不引入的依赖

- **不引入** `github.com/creack/pty`、`github.com/buildkite/agent` 等 pty/进程管理库——harness 适配器以**非交互**为前提（§9.2 `Capabilities.NonInteractive = true`），不需要 PTY；流式输出由 `cmd.StdoutPipe` + 自实现 `lineWriter` 完成。
- **不引入** YAML 第三方之外的 JSON / TOML 库；`prompt.Prompt` 的序列化走 `strings.Builder` + sha256，不经 JSON 编码（与 §11.2 refs 协议一致）。
- **不引入** goroutine 池；每个 attempt 一个独立 `*exec.Cmd`，由 shell 适配器持有；M6.4 dispatch tick 在每次 tick 重新 `Plan` 后串行/并发启动 attempt（受 caps 约束）。
- **不引入** context 取消库；统一用 `context.Context` + `signal.NotifyContext`（CLI 层）；harness 适配器 `Stop(ctx)` 通过 ctx 取消触发进程树终止。

## 平台差异：进程树终止

`internal/harness/proc_unix.go`（POSIX：Linux/macOS）：

- 启动时 `exec.Cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}` 让子进程成为新进程组的 leader。
- 终止时 `syscall.Kill(-cmd.Process.Pid, signal)` 向**负 PID** 发信号，整组进程收到。
- 顺序：先 `SIGTERM`，`stopGrace=10s` 后再 `SIGKILL`（`internal/app/runexec.go:27`）。

`internal/harness/proc_windows.go`（Windows）：

- 启动时 `windows.CreateJobObject` 创建 Job，`SetInformationJobObject` 配 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`——Job handle 关闭时所有进程被强制终止。
- `AssignProcessToJobObject` 把子进程加入 Job；`TerminateJobObject` 立即终止整棵树。
- 不依赖 PID；用 `unsafe.Pointer` + Win32 结构体（来自 `golang.org/x/sys/windows`）。

两种实现的 Go 签名一致（`killProcessTree(cmd *exec.Cmd) error`），由 `internal/harness/shell.go` 的 `kill()` 调用——一个调用点，两种实现，shell 适配器不感知平台。

## `golang.org/x/term` 的最小用途

POSIX shell 适配器的 `Probe(ctx)`（[internal/harness/shell.go:46-61](file://internal/harness/shell.go#L46-L61)）需要报告 host shell：

```go
shell := "/bin/sh"
if term.IsTerminal(int(os.Stdin.Fd())) {
    // POSIX interactive shell still calls /bin/sh — but the report mentions
    // it is reachable as a TTY, not blind argv.
}
```

`term.IsTerminal` 仅做 fd 检查（POSIX `isatty(3)`），不读 stdin、不分配伪终端，**不改变** devsys 任何路径上的行为——它只是让 Probe 的可用性报告更精确。Windows 路径不引入 `golang.org/x/term`（编译时 `//go:build windows` 排除 term 包）。

## 离线构建

执行层**没有**运行时拉取；`go.mod` / `go.sum` 与 `vendor/` 同步提交：

```sh
GOFLAGS=-mod=vendor GOPROXY=off go build ./...
GOFLAGS=-mod=vendor go test ./internal/harness/... ./internal/workspace/... ./internal/dispatch/... ./internal/retry/... ./internal/prompt/...
```

`smoke-m6.{sh,ps1}` 通过 stub codex 覆盖适配器链；不需要真实模型提供方。
