# 执行层 · 技术栈

执行层在 Go 1.26 之上**没有第三方依赖**：`internal/harness` / `workspace` / `dispatch` / `retry` / `prompt` 只 import 标准库与仓库内包（[go.mod](file://go.mod) 里已**没有** `golang.org/x/term`；`golang.org/x/sys` 只是 MCP Go SDK 的 indirect 依赖，`internal/**` 不 import 它）。进程树终止由 `os/exec` + 平台手段实现：POSIX 用进程组信号，Windows 用系统自带的 `taskkill /T /F /PID`。

## 不引入的依赖

- **不引入** `github.com/creack/pty`、`github.com/buildkite/agent` 等 pty/进程管理库——harness 适配器以**非交互**为前提（§9.2 `Capabilities.NonInteractive = true`），不需要 PTY，也没有 PTY 可分配：输出直接挂在 `cmd.Stdout` / `cmd.Stderr` 上，由自实现 `lineWriter` 切行，os/exec 负责复制。
- **不引入** 任何 YAML / JSON / TOML 解析库：policy 与 hook 的解析在 `internal/workflow`（`gopkg.in/yaml.v3`，M0 沿用），执行层只消费已解析的结构；`prompt.Prompt` 的文本由 `strings.Builder` 渲染后 `sha256` 取 hash，不做 JSON 编码（结构化输出由 CLI / MCP 层用标准库 `encoding/json` 负责）。
- **不引入** goroutine 池；每个 attempt 一个独立 `*exec.Cmd`，由 shell 适配器持有；M6.4 dispatch tick 在每次 tick 重新 `Plan` 后串行/并发启动 attempt（受 caps 约束）。
- **不引入** context 取消库；统一用 `context.Context` + `signal.NotifyContext`（CLI 层）；attempt 的 ctx 取消监听 goroutine 与 `Stop(ctx)` 都会走到 `kill()` → `killTree` 终止整棵进程树（[internal/harness/shell.go:159-166](file://internal/harness/shell.go#L159-L166)）。

## 平台差异：进程树终止

`internal/harness/proc_unix.go`（`//go:build !windows`，POSIX：Linux/macOS）：

- `configureProcessGroup(cmd)` 设 `cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}`，让子进程成为新进程组的 leader。
- `killTree(proc)`：`syscall.Getpgid(proc.Pid)` 取进程组，再 `syscall.Kill(-pgid, syscall.SIGKILL)` 向**负 PGID** 发信号，整组进程收到；取不到进程组时退回 `proc.Kill()`。
- 没有 SIGTERM/宽限期这一步：停止就是 `SIGKILL` 整组；`stopGrace = 10 * time.Second` 是 `internal/app/runexec.go:27-29` 里**等待**被停 attempt 收尾的上限，不是终止信号之间的间隔。

`internal/harness/proc_windows.go`（`//go:build windows`）：

- `configureProcessGroup(cmd)` 是 **no-op**：Windows 没有进程组，也不为它引入依赖。
- `killTree(proc)`：`taskkill /T /F /PID <pid>` 遍历子进程树（`Process.Kill()` 只收直接子进程），stdout/stderr 丢进 `io.Discard`；`taskkill` 失败退回 `proc.Kill()`。
- 不依赖 JobObject，也不 import `golang.org/x/sys/windows`。

两种实现的 Go 签名一致（`configureProcessGroup(cmd *exec.Cmd)` / `killTree(proc *os.Process) error`），由 `internal/harness/shell.go` 的 `kill()`（`stopOnce.Do` 内）调用——一个调用点，两种实现，shell 适配器不感知平台（[internal/harness/shell.go:237-248](file://internal/harness/shell.go#L237-L248)）。

## host shell 探针：`Probe` 不需要 TTY 检查

`Shell.Probe(ctx)`（[internal/harness/shell.go:46-61](file://internal/harness/shell.go#L46-L61)）不探测 TTY，也不 import 任何 term 包：它按 `runtime.GOOS` 选一个名字（非 Windows 为 `sh` / hint `POSIX`，Windows 为 `cmd` / hint `Windows`），Detail 固定为 `argv passthrough on <goos> (<hint>)`，Version 是 `exec.LookPath(name)` 解析出的路径。

```go
name, hint := "sh", "POSIX"
if runtime.GOOS == "windows" {
    name, hint = "cmd", "Windows"
}
```

- shell 不在 PATH 时仍返回 `Installed: true`（argv 直通不依赖 shell），只在 Detail 后追加 `; <name> not on PATH`。
- 三个 CLI harness 的 `Probe` 走 `exec.LookPath(a.bin)` + `--version`（超时 `probeTimeout = 10s`）：不在 PATH → `Installed: false, Detail: "<bin> is not on PATH"`；`--version` 失败 → `Installed: true` + Detail `"<name> found at <path> but --version failed: <err>"`，**不**把可用性降级（[internal/harness/cli.go:41-55](file://internal/harness/cli.go#L41-L55)）。

## 离线构建

执行层**没有**运行时拉取；`go.mod` / `go.sum` 与 `vendor/` 同步提交：

```sh
GOFLAGS=-mod=vendor GOPROXY=off go build ./...
GOFLAGS=-mod=vendor go test ./internal/harness/... ./internal/workspace/... ./internal/dispatch/... ./internal/retry/... ./internal/prompt/...
```

`smoke-m6.{sh,ps1}` 通过 stub codex 覆盖适配器链；不需要真实模型提供方。
