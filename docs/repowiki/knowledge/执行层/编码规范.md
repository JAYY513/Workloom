# 执行层 · 编码规范

下列规则已在 `internal/harness / workspace / dispatch / retry / prompt` 的源码中**至少两处验证**——是新增代码的默认契约，违反任何一条都会在 PR review 中被驳回。

## 1. 适配器接口稳定性

`Adapter` 与 `Session`（[internal/harness/harness.go:96-126](file://internal/harness/harness.go#L96-L126)）的导出方法签名固定：

- `Adapter{ Name() string; Capabilities() Capabilities; Probe(ctx) (Availability, error); Prepare(ctx, ws Workspace) error; Command(req Request) (Command, error); Start(ctx, cmd Command) (Session, error) }`
- `Session{ Lines() <-chan Line; Wait(ctx) (Result, error); Stop(ctx) error }`

**禁止**：在 `Adapter` 上新增方法而不更新所有实现；CLI 适配器**不**重新实现 `Probe` / `Start`——统一委托 shell。新增 harness 必须经 `Names()` 注册；`ByName` 拒绝未知名字（`internal/harness/cli.go:164-179`）。

## 2. Session 不持有 Adapter 状态 / 不可重入

每个 attempt 一个 `*shellSession`；shell 适配器自身（`*Shell`）**不持有任何 per-attempt 状态**——这是 §9.2 "adapter 永远无状态" 的 Go 形态。`Session.Lines()` 返回只读 `<-chan`；调用方只读、不关。

`Stop(ctx)` 终止后 `Wait` 仍能拿到完整 `Result`；**重复 Stop 是 no-op**（`kill()` 一次性触发）。`Wait` 后再次 `Stop` 也无副作用。

## 3. 进程树终止——一个实现，一个调用点

`internal/harness/shell.go` 的 `(*shellSession).kill()`（[internal/harness/shell.go:237-248](file://internal/harness/shell.go#L237-L248)）是**唯一**终止调用点：`Stop`、`cmd.Timeout` 的定时器回调、ctx 取消监听 goroutine 三处都只通过它收口（[internal/harness/shell.go:153-166](file://internal/harness/shell.go#L153-L166)、[internal/harness/shell.go:210-223](file://internal/harness/shell.go#L210-L223)）。`kill()` 由 `stopOnce sync.Once` 一次性触发；触发后关闭 `discard`，尚未发出的 line 直接丢弃（不阻塞写 goroutine）。

平台差异（POSIX 进程组 / Windows `taskkill`）由 `proc_unix.go` / `proc_windows.go` 同签名 `killTree(proc *os.Process) error` 承载，进程组在 `configureProcessGroup(cmd *exec.Cmd)` 里配置。**禁止**在 shell 适配器内直接调 `os.Process.Kill()` 或 `syscall.Kill()`——只走 `killTree`（`proc.Kill()` 只作为 `killTree` 内部的兜底，不是调用方的手段）。

## 4. 流式行缓冲——64KB chunk，不断 rune

`lineWriter`（[internal/harness/shell.go:295-318](file://internal/harness/shell.go#L295-L318)）按 rune 边界切 chunk：

- `lineBuffer = 64 << 10`（64 KiB）：超过此长度的单行按 rune 边界切多 chunk 发出——单行不会耗尽内存，也不会丢输出。
- `incompleteTail(b)`（[internal/harness/shell.go:329-361](file://internal/harness/shell.go#L329-L361)）报告末尾被切短的 rune 字节数；下一次写入优先用其把 rune 拼完整。

**禁止**用 `bufio.Scanner` 默认 64KB 上限直接切——会丢字节；禁止把整行 `ReadString('\n')` 进 `Line.Text`（超长行会被截断）。

## 5. stdin 投递——失败是 evidence，不是 spawn 失败

`feedStdin(pipe, payload, sess)`（[internal/harness/shell.go:170-178](file://internal/harness/shell.go#L170-L178)）单独 goroutine 写 prompt 到 stdin，**写失败不返回 spawn 错误**——它往 stderr 流发一行 `workloom: stdin write failed: <err>`，attempt 仍走完自己的生命周期。理由：进程可能已退出（自己的退出码就是 attempt 的真值），stdin 写不进去不应掩盖 attempt 结果。

**禁止**在 `Start` 里 `io.ReadAll(stdin)` 等 prompt 完整写入——会因 pipe 满而阻塞。

## 6. Plan 纯函数——输入不可变

`Plan(in Input) Report`（[internal/dispatch/plan.go:83-158](file://internal/dispatch/plan.go#L83-L158)）**不修改** `in.Items` / `in.Status` / `in.Dependencies` 任何字段；返回 `Report` 列出每个候选的处置。`ResolveCaps` 同理。

**禁止**：

- 在 Plan 内部发起任何 I/O（读 git / 调 harness / 写 storage）。
- 在 Plan 内部更新工作项状态、调度态、Run 记录。
- 把 attempt 启动结果回写到 `Report`——attempt 启动是 caller（`internal/app.dispatchOne`）的事。

如果测试断言里出现 `&Report{... Started: ["WLM-1"]}` 同时 `MockSomeSideEffect`，说明边界已破——拆。

## 7. Plan 顺序——总序，三键决胜

排序键：`priority desc → created_at asc → id asc`（id 是工作项标识符，本系统 `^[A-Z]+-\d+$` 字典序）。

- 优先级降序：高优先级先起；同优先级按 created_at 升序（最老先起）；同 created_at 按 id 字典序决胜。
- §17.4 SPEC 未要求决胜项；本系统用 id 决胜是为了 §15.4 "到期判定在 tick 时求值" 的可复算性——同一状态、同一时钟总产生同一 Plan 输出。
- 不引入随机数；不引入"先来先服务"以外策略。

## 8. Retry seed + attempt —— 可复现 jitter

`Delay(base, max, attempt, seed)`（[internal/retry/backoff.go:38-67](file://internal/retry/backoff.go#L38-L67)）的可复现边界：

- `seed` = 工作项标识符（不是随机数）。
- `attempt` 起步为 1（"第一次重试 = 第二次 attempt"）。
- `jitter = derivedFraction(seed, attempt, 20)`：由 `sha256(seed || ":" || attempt)` 取前 8 字节做 `binary.LittleEndian.Uint64`，模 20 得到 [0, 20)。**派生**，不是 `math/rand`。

**禁止**：把 `rand.New(...)` 注入此函数；禁止把 `time.Now().UnixNano()` 当 jitter 来源——重启调度器必须能复算同一到期时间。

## 9. Prompt section 顺序固定

`Assemble`（[internal/prompt/prompt.go:164-229](file://internal/prompt/prompt.go#L164-L229)）的 section 顺序（首轮）：`# 任务` → `# 工作流策略正文`（无挂载策略时渲染 `noPolicyBody`，[internal/prompt/prompt.go:149](file://internal/prompt/prompt.go#L149)） → `len(Remaining)>0` 时追加 `# 工作流步骤` → `# 当前状态` → `# 上下文引用` →（可选）`# 知识基线` → `# 汇报协议`。续轮（Round>1）：`# 任务`（任务行而非整段简报） → `# 上一轮以来的变化` → `# 未完成项` → `# 汇报协议`（缩略版：「沿用首轮协议」）。section 之间空一行；body 内 `\n` 末尾不补空行。

**禁止**：

- 在 section 之间插入额外空行——`renderSections` 拼装时已加固定 `\n\n`。
- 改变 section 标题文本——hash 必须稳定。
- 把 task body / policy body 直接 inline 到 Prompt.Text——Prompt 只携带**身份**（id + title）；body 由 agent 读 `workitem_get` / `workflow_get` / `artifact_get` 取（§11.2 refs 协议）。

## 10. Prompt hash 稳定

`Prompt.Hash` 由 `sha256.Sum256([]byte(Prompt.Text))` 得到（小写 64 hex）。同一 `(Task, Policy, State, Context, since)` → byte-identical text → same hash。任何改变渲染路径的修改都必须保证：

- 同一输入的 hash 与现有 reference fixture（如果存在）一致。
- 新增 section 必须出现在 §9 顺序的固定位置。
- 模板里不引入 `time.Now()` / `os.Hostname()` / 进程 pid 等非确定性来源。

## 11. Workspace 根内不变量——Validate 先于一切

`workspace.Validate(root, path)`（[internal/workspace/path.go:48-84](file://internal/workspace/path.go#L48-L84)）必须在 `RunExec` 启动 attempt 前调用。`Validate` 把 root / path 都 `filepath.Abs` + `filepath.Clean` + 沿最深存在祖先解 symlink，然后比较：

- 同 root（Windows 大小写不敏感 `samePath`）→ 拒绝。
- 不在 root 内 → 拒绝。
- 是 root 本身 → 拒绝。

**禁止**：

- `filepath.Rel` 后用 `strings.HasPrefix("..")` 判断越界——符号链接逃逸。
- 直接 `os.Stat` 后信任路径——`EvalSymlinks` 才能穿透 symlink。

## 12. Key 净化——hash 后缀抗碰撞

`workspace.Key(identifier)`（[internal/workspace/key.go:36-53](file://internal/workspace/key.go#L36-L53)）规则：

- 每个非 `[A-Za-z0-9._-]` rune 映射为 `_`（**一 rune 一 `_`**——多字节字符不复制）。
- 净化未改、且 usable（不是 `""`、`"."`、`".."`、不以 `.` 结尾、不在 `reservedKeyNames`、≤ `keyMax=64`）→ 直接返回净化结果。
- 否则 `disambiguated`：净化结果（按 `keyMax - len(keyHash) - len(keySeparator)` 截断）+ `--` + sha256(identifier)[:16] hex（`keyHash=16`，64 bits 熵的碰撞抗性下限，见 key.go 注释）。

**禁止**：

- 用完整 sha256 当后缀——超 `keyMax`，破坏跨平台路径可用性。
- 把 `..` 或 `.` 当合法 key——污染父目录或当前目录。
- 把 reserved Windows 设备名（`CON / PRN / AUX / ...`）当合法 key——Windows 会拒绝以这些名字创建目录。

## 13. Hook 走 harness shell —— 流/超时/进程树一致

`RunHook`（[internal/workspace/hook.go:97-157](file://internal/workspace/hook.go#L97-L157)）把 hook command 包装为 `Command{Argv: hookArgv(command)}`（POSIX `sh -c` / Windows `cmd /c`）并委托 `harness.NewShell().Start(ctx, cmd)`——hook 与 attempt 走**完全相同**的流式输出、60s 默认超时（`defaultHookTimeout`）、进程树终止。

输出经 `tailBuffer`（`hookOutputTail=4KB`，保留最后 4 KiB）截断，存到 `HookReport.Output`（[internal/workspace/hook.go:167-191](file://internal/workspace/hook.go#L167-L191)）——一份 hook 输出足以解释失败，又不至于把 state 文件灌满。

**禁止**：

- `os/exec` 直接 `Run(cmd)`——失去流/超时/进程树语义。
- 把 hook 输出整段写回 `.devsys/`——state 文件不该承担日志职责。

## 14. error 风格

- `workspace.HookError{ Name, ExitCode, TimedOut, Canceled, Timeout, Output }`：暴露失败分类（`ExitCode < 0` = 没能跑起来 / 被信号杀死）与输出尾段（[internal/workspace/hook.go:53-80](file://internal/workspace/hook.go#L53-L80)）。
- `workspace.GitError{ Args, Output, Err }`：暴露 git 命令 argv + combined output；`Unwrap()` 让调用方可 `errors.Is`。
- `workspace.ErrGitMissing`：哨兵错误（`"git is not available on PATH"`）；**不再是入场券**——`Ensure` 只在 `requireGit()` 通过且 `rev-parse --is-inside-work-tree` 为 true 时进 worktree 分支，否则落目录工作区（[internal/workspace/git.go:31-46](file://internal/workspace/git.go#L31-L46)），仓库内没有把它映射到退出码的调用点。
- `harness` 不导出错误类型——`Result{ExitCode int, Err string}` 已经够用；`Err != ""` 是 spawn/wait 失败（如 `"output streams stayed open after the command exited"`），与 `ExitCode != 0` 是两件事，`ExitCode = -1` 表示被信号杀死或从未启动（[internal/harness/shell.go:250-284](file://internal/harness/shell.go#L250-L284)）。

## 15. 工作区两形态——`GitProject` 是唯一 git 判定

`workspace.Workspace` 有两种形态，判据只有 `Branch`：非空 = git worktree，空 = 目录工作区（[internal/workspace/workspace.go:26-35](file://internal/workspace/workspace.go#L26-L35)）。由此：

- **Git 判定只写一处**：`GitProject(dir)` = `requireGit()` 通过且 `git rev-parse --is-inside-work-tree` 为 true（[internal/workspace/git.go:38-46](file://internal/workspace/git.go#L38-L46)）。`Ensure` / `Remove` / `List` 都调它分叉，**不**各自 `exec.LookPath("git")` 或去读 `.git`——「机器上没有 git」与「有 git 但在仓库外」对工作区是同一件事。
- **`Ensure` 不在任何路径上要求 git**：顶层没有 `requireGit()`；`GitProject` 为假即走 `ensureDirectory`（只 `os.MkdirAll` + `after_create`，失败 `os.RemoveAll` 回退）（[internal/workspace/workspace.go:57-77](file://internal/workspace/workspace.go#L57-L77)、[internal/workspace/workspace.go:147-177](file://internal/workspace/workspace.go#L147-L177)）。
- **hook env 的 branch 可以是空串**：目录工作区调 `HookEnv(projectRoot, path, "", identifier, hook)`，`DEVSYS_BRANCH` 因空串而**不注入**（[internal/workspace/workspace.go:356-370](file://internal/workspace/workspace.go#L356-L370)）；`RunExec` 传的是 `r.Workspace.Branch`，目录工作区因此同样没有该变量。
- **分支操作留在 git 分支内**：`addWorktree` / `removeWorktree` / `pruneWorktrees` / `worktreeBranches` / `HeadSHA` / `BranchSHA` 只在 `GitProject` 为真的路径上调用（[internal/workspace/workspace.go:288-298](file://internal/workspace/workspace.go#L288-L298)、[internal/workspace/workspace.go:329-336](file://internal/workspace/workspace.go#L329-L336)）。
- **不要为目录工作区伪造证据**：`bindWorkspaceToRun` 只在 `ws.Branch != ""` 时读 `HeadSHA`，目录工作区记录**空** claim head 而不是编一个（[internal/app/workspace.go:111-125](file://internal/app/workspace.go#L111-L125)）。
