## 适配器 ↔ Shell 委托关系

`cliAdapter`（[internal/harness/cli.go:21-27](file://internal/harness/cli.go#L21-L27)）只持有两个差异点：

1. **`name` 与 `caps`**：每个 harness 自己的 `Name()` 与 `Capabilities()`。
2. **`buildCommand(req Request) (Command, error)`**：把 harness 专属的 argv 形态（codex `-`、opencode positional、claude `-p`）翻译成结构化 `Command`。

**不**重新实现：Prepare（统一调 shell.Prepare）、Start（统一调 shell.Start）、Probe（统一调 `codex --version` / `opencode --version` / `claude --version`，超时 10s `probeTimeout`）。这保证流式输出、行缓冲、stdin 投递、进程树终止**只有一个实现**。

## Plan 的纯函数契约

`dispatch.Plan(in Input) Report` 是**纯函数**（[internal/dispatch/plan.go:90-155](file://internal/dispatch/plan.go#L90-L155)）：

- **输入**：`Input{Now, Items, Status, Dependencies, Caps, StallThreshold}`，全部由 `internal/app` 在写锁外组装后传入。
- **输出**：`Report{Decisions: []Decision{ID, Action: start|skip, Reason}, Started: []string}`。`Decisions` 列出每个候选的处置；`Started` 列出本 tick 实际可起的 id。
- **不变量**：`Plan(in) == Plan(in)` 同一时钟、同一状态产生同一输出——这是 §15.4 "到期判定在 tick 时求值" 可被复算验证的基础。
- **顺序**：priority desc → created_at asc → id asc（确定性全序，SPEC 未要求决胜项）。
- **门禁顺序**：先 precondition（blocked_by / dispatchable status），再 cap（先 Global 后 PerStatus）；blocked/not-yet-due 报告原因，over-cap 不阻塞其它候选。

`ResolveCaps(policies []Caps) Caps`（[internal/dispatch/plan.go:182-209](file://internal/dispatch/plan.go#L182-L209)）同样纯函数：多策略取最严合并；缺失声明视为 `DefaultGlobalCap = 1`，所以**一个沉默策略会把整个队列钉到 1**——这条边界在 spec.md §5.3 与 docs/M6-一致性自检.md §17.4 同时记录。

## Retry 与 Prompt 的可复现设计

`retry.Delay(base, max, attempt, seed)`（[internal/retry/backoff.go:38-67](file://internal/retry/backoff.go#L38-L67)）的核心约束：

- `seed` = 工作项 ID（确定性）；`attempt` = 第 N 次重试（1 = 第一次重试 = 第二次 attempt）。
- `jitter` 取 `derivedFraction(seed, attempt, jitterPercent=20)`：**派生**自 seed+attempt，不是 `math/rand` 抽取。重启后同一 `(seed, attempt)` 永远得到同一 jitter——这正是 §15.4 "退避上限 + 抖动可复现" 的实现边界。
- 抖动是 delay 自身的 ≤20%；growth 仍是指数（每步至少 ×2 floor）；`delay+jitter` clamp 至 `max`。

`prompt.Assemble(in Input) (Prompt, error)`（[internal/prompt/prompt.go:164-229](file://internal/prompt/prompt.go#L164-L229)）的核心约束：

- 同一 `(Task, Policy, State, Context, since)` → byte-identical text → 同一 `Hash`。
- 首轮（Round=1）输出全 brief：任务 → 工作流策略正文（无挂载策略时写入 `noPolicyBody` 兜底文案，避免空 section 假装策略加载失败） → `len(Remaining)>0` 时插入「工作流步骤」section → 当前状态 → 上下文引用 →（可选）知识基线 → 汇报协议；续轮只输出 changes + remaining + 任务沿用 + 「沿用首轮协议」缩略版。
- `Refs` 是**身份+标题**，绝不携带 body——agent 按需通过工具面（`context_get` / `workitem_get` / `artifact_get`）读 body。`refs(in)` 列出本轮指向的指针，按 section 顺序去重；`Run.input_context_refs` 即从此写入。
- `protocol` 常量钉死报告契约（[internal/prompt/prompt.go:154-160](file://internal/prompt/prompt.go#L154-L160)）：经 `devsys ...` 或同名 MCP 工具汇报；`decision create --by <身份>` 标识决策者、`workitem block --reason <原因>` 显式受阻、`approval request --stage <阶段>` 在策略要求时取审批；exit 0 = 本轮成功，非零 = 失败（写 stderr）——让 agent 不依赖 harness 自己的 transcript。
