# 知识层 · 生成器契约与适配器

本卡描述 M5 知识层**生成器契约**（`internal/knowledge/generator.go`）：层与外部生成器（首选 RepoWiki）之间的输入协议——生成器是什么、它接受哪些参数、Scope 怎么落地、为什么**不**走 shell。

## 契约形状

`Scope`（[internal/knowledge/generator.go:30-37](../知识层/架构设计.md)）：

```go
type Scope struct {
    FormatVersion int      `json:"format_version"`     // 恒 1（生成器必须按此版本解析）
    Project       string   `json:"project"`            // 项目根（绝对路径）
    Mode          string   `json:"mode"`               // "full" / "affected"
    Baseline      string   `json:"baseline,omitempty"` // state.Baseline.Commit
    Head          string   `json:"head,omitempty"`     // 当前 HEAD commit
    Pages         []string `json:"pages"`              // 需要生成的页面路径（项目内）
}
```

`FormatVersion = 1`（[generator.go:15](../知识层/架构设计.md)）是契约版本。升到 2 时 Generator 必须先读 `format_version`，不接受旧版 scope 才往下走——这是契约**唯一**的版本信号。

## argv 的拼装

`GeneratorCommand(command, scopePath, projectRoot)`（[generator.go:43-53](../知识层/架构设计.md)）：

```go
argv := strings.Fields(command)                  // 切分用户配置
return append(argv,
    "--project", projectRoot,                    // 项目根（绝对路径）
    "--scope-file", scopePath,                   // scope 文件路径（绝对路径）
    "--format-version", strconv.Itoa(FormatVersion),
), nil
```

例：用户配置 `repowiki refresh`，`projectRoot=/repo`，`scopePath=/repo/.devsys/knowledge/refresh-scope.json`：

```text
repowiki refresh --project /repo --scope-file /repo/.devsys/knowledge/refresh-scope.json --format-version 1
```

`strings.Fields` 按 ASCII 空白切分——多空白会被合并；引号包裹的字段**不**保留空白（生成器配置应避免）。理由：避免第二套 shell 解析层（cmd.exe / sh / PowerShell 各自有 quoting 规则）。

## Scope 落地文件

`ScopeFile = Dir + "/refresh-scope.json" = ".devsys/knowledge/refresh-scope.json"`（[generator.go:26](../知识层/架构设计.md)）。

`WriteScope`（[generator.go:56-65](../知识层/架构设计.md)）走 `storage.AtomicWrite`（同源 transaction 原语）：

- 序列化（`json.MarshalIndent`，缩进 2）；
- 末尾换行；
- 写文件权限 0644；
- 失败时包成 `fmt.Errorf("write %s: %w", ScopeFile, err)`。

生成器启动时**总是**先读 scope 文件——这避免了：

- 超长 Pages 列表压爆 argv；
- scope 字段后续扩展（新的 `Mode`、`FormatVersion` 子字段）不影响 argv 形状；
- scope 在刷新失败后可作为审计材料被读取。

## 不走 shell 的语义

`exec.CommandContext(ctx, argv[0], argv[1:]...)` 直接调用 CreateProcess：

- **没有 shell 展开**：环境变量、`~`、`*`、`$(...)` 都不展开；
- **没有管道/重定向**：`<`、`>`、`|` 都不解析；
- **Windows 不走 `cmd /c`**：`CreateProcess` 直接接收程序路径。

副作用：

- Linux/macOS 上脚本必须可执行（`chmod +x`）+ shebang 行（`#!/usr/bin/env bash`）；
- Windows 上**生成器必须**是 `.exe` 或 `.cmd`（**不能**直接是 `.sh`）。`scripts/smoke-m5.sh` 演示了包装：

```bash
if [[ "$(uname -s)" == MINGW* || "$(uname -s)" == MSYS* ]]; then
    cat > "$stubs/generator.cmd" <<STUB
@echo off
bash "$workspace/generator" %*
STUB
    generator_cmd="$(cygpath -m "$stubs/generator.cmd")"
else
    generator_cmd="$workspace/generator"
fi
```

`cygpath -m` 把路径转成 Windows 形式（`C:\...`），避免 YAML scalar 需要转义反斜杠。

## 生成器的输出约定

`runGenerator`（[internal/app/knowledge.go:529-539](../知识层/架构设计.md)）把 stdout 与 stderr **合并**写进 `KnowledgeRefreshView.Output`：

- `cmd.Stdout = cmd.Stderr = out`（同一 `*limitWriter`）；
- `out` 上限 `generatorOutputLimit = 256 KiB`，超过截断并追加 `\n[输出超过 %d 字节，已截断]`；
- 一个进程退出非 0 → 整个 refresh 返回 `Preconditionf("knowledge refresh: generator %q failed: %v", view.Generator, err)`（exit 3）。

生成器**应该**在 stdout 打印简洁的状态（smoke 用 `echo "stub generator ran"`）；**不应该**写大段日志——那是 `Output` 字段的带宽极限。

## M5.6 适配器层（Adapter）

M5.6 把「单一生成器 CLI」抽象为可插拔的**适配器**（[internal/knowledge/adapter.go:57-81](../知识层/架构设计.md)）。这是从「`knowledge_generator` 是一条 shell 命令」到「`knowledge_generator` 是某个命名适配器」的小步演进——让层在不动 argv 协议的前提下，换一种方式读生成器的状态、问它是否在位。

### `Adapter` 接口

```go
type Adapter interface {
    Name() string                                  // "repowiki"
    Probe(ctx context.Context) Availability        // 是否安装
    Import(root string) (*State, error)            // 把生成器自己的 state 映射到层
    Generate(ctx context.Context, req GenerateRequest) (GenerateResult, error)
}
```

`Adapters()`（[adapter.go:71](../知识层/架构设计.md)）目前只注册 `Repowiki()`——一个 built-in 实例。`AdapterByName(name)`（[adapter.go:74-81](../知识层/架构设计.md)）按 `strings.EqualFold` 解析用户配置的 `knowledge_generator`：`name == ""` 或未知名字都返回 `(nil, false)`，调用方退回到「直接走 argv」的旧路径——**不**抛错。

### `Probe` 与「可用」语义

`Availability{Installed bool, Detail string}`（[adapter.go:25-29](../知识层/架构设计.md)）是探测结果：

- `Installed=true`：生成器在 PATH 上且能跑（无参调用退出 0）；
- `Installed=false` + `Detail`：原因（不在 PATH / 退出码 / 错误输出）；
- `ProbeTimeout = 10 * time.Second`（[adapter.go:174](../知识层/架构设计.md)）：探测超时上限——一个 hang 在启动的生成器**不能**让 `knowledge status` 一起 hang。

`repowikiAdapter.Probe`（[adapter.go:180-192](../知识层/架构设计.md)）跑 `repowiki` 无参：`exec.LookPath` 失败 → `Installed=false, Detail="repowiki is not on PATH"`；进程退出非 0 → `Installed=false, Detail=<stderr>`；成功 → `Installed=true, Detail=""`。**Probe 不读 state、不读 scan——只看 CLI 能不能回答问题**。

`KnowledgeStatusView`（[internal/app/knowledge.go:45-86](../知识层/架构设计.md)）多三个字段：

```go
Adapter          string `json:"adapter,omitempty"`            // "repowiki"
AdapterInstalled bool   `json:"adapter_installed,omitempty"`  // 探测结果
AdapterDetail    string `json:"adapter_detail,omitempty"`     // 失败原因
```

CI 与 hook 看 `AdapterInstalled=false` 就能区分「没装生成器」（退化）与「装上了但不是二进制」（错误）。

### `Import` 与状态映射

参考生成器把 `sources` 写在自己的 state 文件里（`.repowiki/state.json`），不写在每个页面的 front matter——所以层**必须**把它映射过来，否则那些页面永远是 `unverifiable`。

`repowikiAdapter.Import`（[adapter.go:209-237](../知识层/架构设计.md)）：

```go
state := &State{
    SchemaVersion: StateSchemaVersion,
    Baseline:      Baseline{Commit: external.Git.Commit, Branch: external.Git.Branch},
    Pages:         map[string]PageState{},
    Generator:     "repowiki",
}
for page, entry := range external.Pages {
    if !strings.HasSuffix(page, ".md") { continue }
    state.Pages[repowikiBundleRoot+"/"+page] = PageState{
        Sources:     entry.Sources,
        ContentHash: entry.ContentHash,
    }
}
```

要点：

- **state 文件缺失**返回 `(nil, nil)`——生成器还没跑过不是错误；
- **页面路径前缀 `docs/repowiki/`**：参考生成器的 bundle 根与层认定的页面根是同一处；映射时把 `<page>` 拼成 `docs/repowiki/<page>`，与 `Scan` 的输出对齐；
- **`.md` 过滤**：state 可能包含 index.md、log.md 之外的元数据文件；只把 `.md` 当页面。

### `MergeStates` 逐字段合并

层自己有 `.devsys/knowledge/state.json`（在 schema 升级、跨项目搬运等场景下被手写或被老版本写），生成器自己也有 state。**两者不互斥**：层 state 是「已知页面 + 来源」的权威，生成器 state 是「这一轮跑了什么 + 真实 hash」的快照。`MergeStates(local, imported *State) *State`（[adapter.go:87-125](../知识层/架构设计.md)）把它们合一份：

```go
merged := &State{
    SchemaVersion: local.SchemaVersion,
    Baseline:      local.Baseline,
    Pages:         map[string]PageState{},
    Generator:     local.Generator,
    UpdatedAt:     local.UpdatedAt,
}
// 缺则补
if merged.Baseline.Commit == "" { merged.Baseline.Commit = imported.Baseline.Commit }
if merged.Baseline.Branch == "" { merged.Baseline.Branch = imported.Baseline.Branch }
// 页面：本地的优先，但 sources / content_hash / source_commit 各自补缺
for path, entry := range imported.Pages { merged.Pages[path] = entry }
for path, entry := range local.Pages {
    previous := merged.Pages[path]
    merged.Pages[path] = PageState{
        ContentHash:  firstNonEmpty(entry.ContentHash, previous.ContentHash),
        Sources:      firstNonEmptyList(entry.Sources, previous.Sources),
        SourceCommit: firstNonEmpty(entry.SourceCommit, previous.SourceCommit),
    }
}
if merged.Generator == "" { merged.Generator = imported.Generator }
```

设计点：

- **本地先**：层 state 是页面层的归属——一旦记录了某页，生成器侧记录就被覆盖；
- **`firstNonEmpty` / `firstNonEmptyList` 字段级**：`ContentHash` 单独判空，`Sources` 单独判 nil——避免「页面有 hash 但 sources 被清零」之类的破坏性合并；
- **Generator 字段补缺**：层没记生成器名字时退到导入的；
- **merge 不写盘**：`MergeStates` 是纯函数；写盘的仍然是生成器的 `state --update`。

`Service.knowledgeState`（[internal/app/knowledge.go:648-666](../知识层/架构设计.md)）是这条流水线的入口：load 本地 → 找适配器 → Import → `MergeStates`，三个值（merged、generator 名、err）一并返回给 status / validate / refresh 三处复用。

### `Generate` 与 finalize 的边界

`GenerateRequest{Root, ScopeFile, Pages}` + `GenerateResult{Output, Finalized, AwaitingGeneration, Note}`（[adapter.go:31-54](../知识层/架构设计.md)）是适配器与 `Service.generate`（[internal/app/knowledge.go:507-524](../知识层/架构设计.md)）之间的契约。

`repowikiAdapter.Generate`（[adapter.go:243-276](../知识层/架构设计.md)）：

```go
recorded, err := a.Import(req.Root)         // 1. 先取参考记录
if err != nil { return result, err }
for _, args := range [][]string{{"init"}, {"scan"}} {   // 2. 跑机械步骤
    out, err := runRepowiki(ctx, req.Root, args...)
    ...
}
pending, err := a.pendingPages(req, recorded)          // 3. 比对磁盘
if len(pending) > 0 {
    result.AwaitingGeneration = pending                // 4. 不 finalize
    result.Note = "..."
    return result, nil
}
out, err := runRepowiki(ctx, req.Root, "state", "--update")  // 5. 仅当全部一致才跑 state --update
result.Finalized = true
```

关键约束：

- **init / scan 之前先 Import**：参考记录必须在 init/scan **之前**取，否则 `state --update` 把同一份「老 state + 新 scan」当成一次全量刷新——会记录「新」的 baseline 在「陈旧」的页面上。Import 的快照挡住了这一步。
- **仅当 scoped 页面与磁盘一致才 finalize**：`pendingPages`（[adapter.go:281-306](../知识层/架构设计.md)）逐页 `HashFile` 比对——`actual != recorded` → pending；不可读或没记录 → 也 pending。
- **不 finalize 时不更新 baseline**：`Note` 字段说明原因；返回 `AwaitingGeneration`，调用方写进 `KnowledgeRefreshView`，CLI 在 `reportRefresh`（[internal/cli/records.go:1203](../项目接入与配置/CLI渲染与交换协议.md)）打 `awaiting generation: <path>`。下一次 refresh 再来时 `Import` 看到的 recorded 仍是同一份老 state——避免 baseline 漂移。

### `Service.generate` 分派

`Service.generate`（[internal/app/knowledge.go:507-524](../知识层/架构设计.md)）是 argv 旧路径与适配器新路径的合流点：

```go
if adapterName == "" {
    return s.runGenerator(ctx, argv)             // 旧路径：直接 exec argv[0]
}
adapter, ok := knowledge.AdapterByName(adapterName)
if !ok {
    return "", Usagef("knowledge_generator %q names an unknown adapter", configured)
}
result, err := adapter.Generate(ctx, knowledge.GenerateRequest{Root: s.Root, ScopeFile: view.ScopeFile, Pages: pages})
view.Finalized = result.Finalized
view.AwaitingGeneration = result.AwaitingGeneration
if result.Note != "" { view.Reason = result.Note }
return result.Output, err
```

- `adapterName == ""`：兼容老配置（用户只配了「一条 shell 命令」，没指名「哪个适配器」）；
- `AdapterByName` 找不到 → `Usagef` 走 CLI exit 2 / MCP `usage`，**不**静默 fallback；
- 输出继续走 256 KiB `limitWriter`（[internal/app/knowledge.go:540-566](../知识层/架构设计.md)）：适配器的 stdout 也受同一上限保护。

### `KnowledgeRefreshView` 新增字段

```go
type KnowledgeRefreshView struct {
    ...
    Finalized         bool     `json:"finalized,omitempty"`          // 新：生成器记录了新 baseline
    AwaitingGeneration []string `json:"awaiting_generation,omitempty"` // 新：scoped 但未写入的页
    ...
}
```

两个字段都是 optional——只有走适配器路径时才有值；走 argv 旧路径时为 `false` / `nil`，`--json` 不出现。

## 与 M6 适配器的关系

生成器契约**只**在知识层用。M6 的 `internal/harness` 暴露的 `Adapter` / `Session` 接口（[执行层 · 适配器协议契约](../执行层/适配器协议契约.md)）是另一份契约——运行 harness 适配器：

- 不是生成器——它产生 Run 的**执行**（spwan agent、读 stream）；
- 适配器协议走 stdin 投递 + JSONL 流；
- 知识层不需要 stdin/stdout JSONL 协议（生成器是 one-shot）。

唯一交叉点是 M6 的 `workspace.RunHook` 走 `harness.Shell`——那是生命周期钩子（`after_create` 等），不是生成器。

## 边界与不做的事

- **不做插件沙箱**：生成器以 devsys 子进程身份运行，能读写整个项目根——管理员责任；
- **不校验生成器签名**：M5 没有签名机制，参考实现（RepoWiki）的真实性由项目配置决定；
- **不支持多生成器并行**：单次 refresh 调一个 generator，多次 refresh 可串行；层不调度并发。
