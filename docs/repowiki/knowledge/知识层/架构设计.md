## 关键流程

### 知识状态裁决（`knowledge status`）

```mermaid
flowchart TD
    A[CLI: knowledge status] --> B[svc.KnowledgeStatus]
    B --> C{project ok?}
    C -- 否 --> X1[exit 3/4 precondition/invalid]
    C -- 是 --> D[md.Config.KnowledgeGenerator?]
    D --> E[LoadSnapshot 探测 IndexReady]
    E -- err not exist --> F[IndexReady=false]
    E -- err 其它 --> X1[invalid: KindKnowledge]
    F --> G[Scan root 候选根 → report.Pages]
    G -- err --> X1[internal]
    G -- ok --> H{report.Errors > 0?}
    H -- 是 --> X1[invalid: KindKnowledge + Problems]
    H -- 否 --> I[LoadState]
    I -- err NotExist --> J[state=nil]
    I -- err 其它 --> X1[invalid]
    J --> K{view.Pages == 0?}
    K -- 是 --> L[Status=missing, exit 11]
    K -- 否 --> M[Head root → view.Head/Branch]
    M -- err --> X1[precondition: ErrNoGit]
    M -- ok --> N[Evaluate report.Pages state]
    N -- err ErrNoGit --> X1[precondition]
    N -- err 其它 --> X1[internal]
    N -- ok --> O[view.ChangedFiles/Affected/Unverifiable/FreshPages]
    O --> P{Affected 非空 或 Unverifiable 非空?}
    P -- 是 --> Q[Status=stale, exit 10]
    P -- 否 --> R[Status=fresh, exit 0]
```

**裁决语**：
- `fresh`：每页要么无变化，要么无 sources 也无 baseline 时被标 `unverifiable`——而`unverifiable`也是 stale（"cannot tell" ≠ fresh）。
- `stale`：有 `affected` 或 `unverifiable`；`Reason` 含「`%d page(s) affected by %d changed file(s)`」或「`%d page(s) have no sources or baseline, so they cannot be called fresh`」。
- `missing`：层还没生成页面，或生成器未配置（`view.Pages == 0`）。

**退出码契约**（方案 §12.5）：

| Status | exit | 含义 | 来源 |
|---|---|---|---|
| `fresh` | 0 | 所有页面都对得上工作树 | `CodeOK`（无） |
| `stale` | 10 | 至少一页 affected 或 unverifiable | `CodeStale` 常量（新增） |
| `missing` | 11 | 页面层不存在或生成器未配置 | `CodeMissing` 常量（新增） |

`codedExit{code}` 是新增的错误类型，stdout 已写好报告，退出码承载状态——`render` 把它解包后**直接**返回 `code`，不再走 `toCoded` 的错误分支。

**续跑语义**：
- `ResumePending` 把 `pending[]` 中"已记录 `content_hash` 且磁盘一致"的页剔除（无需重生成）；记录哈希为空或与磁盘不一致的页继续 `remaining`。
- `run.lock` 是 OS 锁：刷新进程死时锁自动释放。`run.json` 是 checkpoint：保留 `pending`，让下一轮只跑未完成页。
- `Phase` 三态：`generating`（运行中）/ `finished`（成功）/ `failed`（generator 退出非零）；失败 checkpoint 不清，下一轮接续。

### Sync 探针（`internal/knowledge/syncgit.go`，M8.1）

`syncgit.go` 给出四个**只读** git 探针——整文件无写操作、不 fetch、不改 git 状态、不触碰 `.devsys/`，只服务于观察面（`sync status` 与 Dispatch tick 顶端 merge 门控等只读复用）：

- `Upstream(root string) (string, error)`（[syncgit.go:19-39](file://internal/knowledge/syncgit.go#L19-L39)）：先 `rev-parse --abbrev-ref HEAD` 拿到当前分支；若分支非空且非 detached，**先**查 `git config --get branch.<name>.remote`——配置缺失直接返回哨兵 `ErrNoUpstream`（[syncgit.go:15](file://internal/knowledge/syncgit.go#L15)），不进入 `rev-parse @{u}`；有配置则 `rev-parse --abbrev-ref --symbolic-full-name @{u}` 解析上游名（仅本地 refdb 读取，**不 fetch**，不触发任何网络）。调用方把 `ErrNoUpstream` 当作 handoff blocker 而非命令失败。
- `AheadBehind(root string) (ahead, behind int, err error)`（[syncgit.go:44-60](file://internal/knowledge/syncgit.go#L44-L60)）：`git rev-list --left-right --count HEAD...@{u}`，按 `strings.Fields` 取两段计数并 `strconv.Atoi` 解析；字段数或解析失败一律作为 error 返回（不静默给 0,0）。
- `PorcelainStatus(root string) ([]PorcelainEntry, error)`（[syncgit.go:84-118](file://internal/knowledge/syncgit.go#L84-L118)）+ `PorcelainEntry{XY, Path, Orig, Unmerged}`（[syncgit.go:62-73](file://internal/knowledge/syncgit.go#L62-L73)）：`git status --porcelain=v1 -z --untracked-files=normal`，按 NUL 分隔；`XY` 前两位取自 entry 前 2 字节；rename/copy（`R*`/`C*`）按规范多吃一段 source 路径到 `Orig`；`unmergedXY(xy)`（[syncgit.go:75-82](file://internal/knowledge/syncgit.go#L75-L82)）判定七种未合并 XY（`DD/AU/UD/UA/DU/AA/UU`）写入 `Unmerged`。空结果统一返回 `[]PorcelainEntry{}`（非 nil），torn/异常 entry 作为 error。
- `MergeHeads(root string) ([]string, error)`（[syncgit.go:120-146](file://internal/knowledge/syncgit.go#L120-L146)）：先 `rev-parse --absolute-git-dir` 拿到 git 目录，再对 `MERGE_HEAD / CHERRY_PICK_HEAD / REBASE_HEAD / REVERT_HEAD / rebase-merge / rebase-apply` 六个文件名/目录逐一 `os.Stat`——任意存在的就收集进返回切片；不存在即不出现。**仅存在性检查**，不读内容、不修改 git 状态。

**只读语义**：四个函数都走 `git(... args)`（调用 `exec.Command("git", ...)`，不会改写工作树/索引/refdb），加上 `os.Stat` 的纯本地文件检查——任何调用方都拿到「这一刻的快照」，不带副作用。`mergeConflict(root)`（[internal/app/dispatch.go:237-263](file://internal/app/dispatch.go#L237-L263)）组合 `PorcelainStatus` + `MergeHeads`：有 unmerged 路径或未完成 merge 头部时阻断 Dispatch tick（precondition exit 3）；探针失败一律降级为 notice（不伪装为 conflict），等下一 tick 再判。

- 退出码契约只在 CLI 用：`knowledge_status` 工具结果正常返回，`KnowledgeStatusView.Status` 字段也带状态——MCP 客户端按 `view.Status` 而不是工具结果码分支。

**生成器契约**：
- 生成器是「带参数的程序」，**不**走 shell：`strings.Fields(command)` 切分后直接 argv；Windows 用 `cygpath -m` 把脚本包装成 `.cmd` 转发到 bash（smoke 脚本里的 fallback）。
- Scope 通过 `--scope-file <rel>` 落地文件，避免超长 argv。
- `FormatVersion = 1`：升到 2 时 Generator 必须在 scope 文件里读到 `format_version: 2` 才接受——这是契约的唯一版本信号。

## 关键决策

- **索引层 = 本系统的活，页面层 = 生成器的活**：这是 §12.6 的核心分工。层永远不会向 generator 发「请给我写这个页」之外的指令，generator 也不会触碰 `.devsys/` 下的 state/snapshot。
- **退出码 10/11 复用既有 0**：M4 之前的所有命令用 `0/1/2/3/4`；M5 把 `10/11` 留给知识层——`codedExit` 是为此而设的错误类型，避免误用 `*codedError` 的字段（那会污染 `toCoded` 的错误路径）。
- **hash 整文件 vs hash body**：front matter 与 body 都计入 `content_hash`；`Page.Hash()`（body only）只在比较"这次写了什么"时用——但保护机制 (`Skips`) 走 `HashFile`（整文件），与生成器记录的 `content_hash` 字段对齐。
- **不需要 DB 索引**：方案 §12.2 把索引上限定为 1 MiB 单文件、不超过目录列表的实际可读规模——任何更大的项目应分库或换数据库，本系统不为此做投机。
- **`Unverifiable` 仍是 stale**：`Cannot tell` 不是 fresh；CI 退出码 10——这避免了「`stale` 假装 `fresh`」的伪装，让 hook 永远拦得住。
- **`--force` 仍记录 override**：保护被覆盖的事实必须留在 `Skipped[]`（含 `Overridden`），便于审计——这是层对"管理员主动覆盖"留的痕迹。
- **索引排除顺序**：默认目录 → 密钥名 → `.gitignore` → 自定义忽略 → 1 MiB 上限；密钥名即使同时被 `.gitignore` 排除，reason 仍写「密钥名模式（同时被 .gitignore 排除）」——审计不能被忽略链隐藏。
- **本批（v0.1.9，ca58d27→19b9149）无代码变更**：`internal/knowledge/**` 与 `internal/app/knowledge.go` 自 690b294 起未动，知识层的行为、退出码 0/10/11 与 scope 协议都不变；只有 `internal/cli/records.go` 的 knowledge usage/注释串随主命令改名同步为 `workloom knowledge …`（`devsys knowledge …` 仍可用——`devsys` 是同一二进制的兼容别名，[cmd/devsys/main.go:1-3](file://cmd/devsys/main.go#L1-L3)）。本页复核后确认不含安装/仓库口径的过时陈述（`GOPRIVATE` / 私有仓库 / `gh auth` 全文零命中），因此只校准来源提交与描述，不改写正文。
