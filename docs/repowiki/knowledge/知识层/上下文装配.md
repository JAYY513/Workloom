# 知识层 · 上下文装配

本卡描述 M5.6 知识层在 `context get --task`（CLI）与 `context_for_workitem`（MCP）上的「任务上下文」装配：把工作项（`workitem`）的描述与「该任务会触碰的文件路径」映射到**这一任务应该读哪些知识页**，并把每一页的「新鲜度」单独标出。同一任务两次装配**字节级一致**——给 agent 复看的世界必须与首次一样。

## 入口

核心实现：`internal/app/context.go` 的两段函数——

- `knowledgeContext(ctx, item, paths)`：单工作项知识分支（[context.go:283-378](../知识层/架构设计.md)），把工作项 + 路径 → `KnowledgeContext`；
- `TaskContext(ctx, id, paths, limit, refresh)`：方案 §11.1 三层装配（[context.go:104-112](../知识层/架构设计.md)），把项目摘要 + 工作项上下文 + 知识分支叠成一份 `TaskContext`。

调用方：

- CLI：`context get --task <id> [--path a,b]`（[internal/cli/records.go:812-824](../项目接入与配置/CLI渲染与交换协议.md)）+ `context workitem --id <id> [--path a,b]`（[internal/cli/records.go:876-917](../项目接入与配置/CLI渲染与交换协议.md)）；
- MCP：`context_for_workitem` 工具（[internal/mcp/tools_context.go:30-48](../共享应用与MCP/工具与Profile.md)）+ `context_get`（仍只走 ContextView，不带 --task）。

两 CLI 入口都通过 `splitPaths(list)`（[internal/cli/records.go:964-972](../项目接入与配置/CLI渲染与交换协议.md)）解析 `--path a,b`：trim 空项 + 去空字符串。MCP `paths` 字段直接走 JSON 数组，语义与 `--path` 同。

## `TaskContext` 三层装配（方案 §11.1）

```go
type TaskContext struct {
    Summary ContextView         `json:"summary"`  // 第一层：项目 + 状态 + 计数 + verdict + next + risks + 近期记录引用 + notices
    Task    WorkitemContextView `json:"task"`     // 第二层：workitem + decisions/findings/artifacts/comments + KnowledgeContext
}

func (s *Service) TaskContext(ctx context.Context, id string, paths []string, limit int, refresh bool) (TaskContext, error) {
    summary, err := s.context(ctx, limit, refresh)
    if err != nil { return TaskContext{}, err }
    task, err := s.ContextForWorkitem(ctx, id, paths)
    if err != nil { return TaskContext{}, err }
    return TaskContext{Summary: summary, Task: task}, nil
}
```

关键约束：

- **summary 与 task 字段分明**：`Summary` 是项目级视图（不引用 workitem），`Task` 是任务级视图——两者独立组装，agent 可以单独读 `Task.Knowledge`；
- **`paths` 只传 task**：summary 不接收 paths——项目级视图按 `recent_*` 选，与任务无关；
- **`limit` 只传 summary**：`context(ctx, limit, refresh)` 控制 `recent_*` 引用条数；`Task` 的引用数由工作项自身决定（每个关联记录都返回）；
- **`refresh` 语义**：与 `context refresh` 同——`refresh=true` 走 `reconcile.Doctor` 重新组装 policy 评估；`refresh=false` 走 LKG 缓存的策略；
- **字节级稳定**：两次同一任务的 `TaskContext` 视图，结构体序列化后**逐字段相等**。`MatchTrigger` 与 `MatchSources` 都是 deterministic 操作；matched 集合用 `refs[page.Path]` map 去重；返回时按 `for _, page := range matched` 顺序遍历——这是 `Scan` 给定的稳定序。

### CLI 渲染（`runContextTask`）

`runContextTask`（[internal/cli/records.go:919-961](../项目接入与配置/CLI渲染与交换协议.md)）打 4 行块：

```text
project: <Name> (<ID>)  phase: <Phase>  readiness: <Verdict>
task: <ID>  <Status>  <Type>  <Title>
  decision: <ref>  <title>
  finding:  <ref>  <title>
  artifact: <ref>  <title>
  notice:   <text>
  knowledge: <Notice>             # 来自 KnowledgeContext.Notice（Degraded / freshness unavailable）
  knowledge: <path>  <description>  (trigger: <触发词>)          # 或 (sources: <src> covers <path>)
  knowledge: <path>  <description>  (sources: <src> covers <path>)  [stale]
```

`[stale]` 标签贴到 stale=true 的页——agent 读它时知道这页描述的是较早代码，应优先以代码为准。

## 三阶段选页

`knowledgeContext`（[context.go:283-378](../知识层/架构设计.md)）：

```mermaid
flowchart TD
    A[knowledgeContext item paths] --> B[project + Scan root → report]
    B -- err --> X1[internal]
    B -- ok --> C{report.Pages == 0?}
    C -- 是 --> D[Degraded=true + Notice 'degrade to records and events'; return]
    C -- 否 --> E[knowledgeState md → state]
    E -- err --> X2[internal]
    E -- ok --> F[文本 = title+description+type+workflowID+workflowStep; lowercase]
    F --> G[phase1: 遍历 pages, trigger 命中 → record MatchTrigger]
    G --> H[phase2: 遍历 pages, sources 命中 paths → record MatchSources]
    H --> I{matched 空?}
    I -- 是 --> J[返回空 pages + Baseline]
    I -- 否 --> K[Evaluate matched state → freshness]
    K -- err ErrNoGit --> L[Notice='freshness unavailable: ...'; 返回 matched 原样]
    K -- err 其它 --> X3[internal]
    K -- ok --> M[逐页 ref.Stale = freshness.Pages[i].Stale]
    M --> N[返回 KnowledgeContext]
```

**关键约束**：

- **per-page freshness**：`Evaluate` 只对 `matched` 跑——不是整层。理由：用户问的是「这任务相关的页面是否还描述当前代码」，不是「整个 wiki 是不是 fresh」。
- **matched 为空**：仍返回空 pages，但 `Baseline` 仍填（来自 `state`），`Degraded=false`（页面层**存在**，只是这任务无关）。
- **`Degraded` 只在「无页面层」时为 true**——其它情况（matched 空 / freshness 失败）**不**视为降级，只是空页或 stale。

## 文本拼接

任务文本（`text`）是 lowercase 的：

```text
text = lower(title + "\n" + description + "\n" + type + "\n" + workflowID + "\n" + workflowStep)
```

`workflowID(item)` / `workflowStep(item)`（M3 引入的字段 `item.Workflow`）从工作项抽取——若工作项不在工作流里则返回空串；这与 `type`（`task` / `bug` / `feature` 等）一起被 `internal/knowledge/trigger.go: WorkItemText`（[trigger.go:30-41](file://internal/knowledge/trigger.go#L30-L41)）用 `"\n"` 拼接并 lowercase 一次。`text = knowledge.WorkItemText(item)`（[context.go:303](file://internal/app/context.go#L303)）。

`triggerHit(triggers, text)`——M7.1 起由 `internal/knowledge/trigger.go: TriggerHit(triggers []string, lowerText string) (string, bool)`（[trigger.go:14-25](file://internal/knowledge/trigger.go#L14-L25)）实现：`internal/app/context.go`（`knowledgeContext`，[context.go:318](file://internal/app/context.go#L318)）与 `internal/view/build.go: relatedItems`（[build.go:789-799](file://internal/view/build.go#L789-L799)）共用这一份实现，行为与抽取前逐字节一致：

```go
for _, trigger := range triggers {
    trimmed := strings.TrimSpace(trigger)
    if trimmed == "" { continue }
    if strings.Contains(text, strings.ToLower(trimmed)) {
        return trimmed, true
    }
}
return "", false
```

- 子串匹配（不是分词）；
- 触发词 lowercased 与文本 lowercased 比对（**不**保留大小写敏感）；
- 第一个命中的触发词作为 `Reason`（如 `存储层`）；
- 同一页先匹配到 trigger 后再匹配 sources 时**不**覆盖——`refs[page.Path]` 已被设过则跳过。

## sources 命中

```go
for _, page := range report.Pages {
    sources := page.Sources
    if len(sources) == 0 {
        if entry, ok := state.Mapping(page.Path); ok {
            sources = entry.Sources
        }
    }
    for _, source := range sources {
        hit := ""
        for _, path := range paths {
            if knowledge.Match(source, path) {
                hit = source + " covers " + path
                break
            }
        }
        if hit != "" {
            record(page, MatchSources, hit)
            break
        }
    }
}
```

- `paths` 来自 CLI/MCP 调用方——通常是「这次任务会碰的文件路径」列表（如 `internal/store/a.go`）；
- `knowledge.Match` 走 `.gitignore` 风格语法（见[索引快照与匹配器](索引快照与匹配器.md)）；
- sources 为空时回退到 `state.Mapping(page.Path).Sources`——这是为什么生成器把 sources 写在 state 里更可靠（方案 §12.5）；
- 一个 page 命中 sources 后 `break`——只记第一条 source/path 配对。

## `RecordRef` 与 `KnowledgePageRef` 的边界

`ContextView`（[context.go:21-31](../知识层/架构设计.md)）有四类引用：

| 字段 | 类型 | 来源 |
|---|---|---|
| `RecentDecisions` | `[]RecordRef` | `internal/record`（决策记录） |
| `RecentFindings` | `[]RecordRef` | `internal/record`（发现记录） |
| `RecentArtifacts` | `[]RecordRef` | `internal/record`（工件） |
| `RecentEvents` | `[]EventRef` | `internal/events` |
| `Knowledge` | `KnowledgeContext` | **M5 新增**——独立分支，不与上面四类混编 |

知识层与领域记录是两个数据源：知识是「文档」，记录是「事实」。两者在 `ContextView` 中并列，不相互依赖。`Degraded` 只影响知识分支——记录分支仍正常返回。

M5.6 把 `Knowledge` 字段嵌进 `WorkitemContextView`（[context.go:53-66](../知识层/架构设计.md)），与 `Notices` 并列——agent 拿到的 `task` 视图里就有 `Knowledge.Pages`，不必再调 `knowledge_status`。

## 退出码

`context get --task` 没有专门退出码——沿用 M4 的 `ContextGet`：

- 成功：`exit 0`；
- 工作项不存在：`exit 4`（`GetWorkitem` 的 precondition 已被 `requireProjectRoot` 翻译）；
- `--task` 后无 ID：`exit 2`（`errUsage`）；usage 行（[internal/cli/records.go:819](../项目接入与配置/CLI渲染与交换协议.md)）从 `context get [--limit N]` 升级为 `context get [--limit N] [--task <workitem-id> [--path a,b]]`。

`context workitem --id <id> [--path a,b]` 同样走 `runKnowledge` 翻译——成功 0；`--id` 缺/空 → `errUsage("context workitem --id <workitem-id> [--path a,b]")` exit 2。

## `anyBaseline` 与「无 baseline」提示

`anyBaseline(pages, state)`（[context.go:382-391](../知识层/架构设计.md)）：

```go
func anyBaseline(pages []*knowledge.Page, state *knowledge.State) bool {
    for _, page := range pages {
        if page.SourceCommit != "" { return true }
        if entry, ok := state.Mapping(page.Path); ok && entry.SourceCommit != "" { return true }
    }
    return false
}
```

命中规则：matched 页中**任一页**有 in-page `SourceCommit` 或 mapping 里的 `SourceCommit`——即可下结论。**全部**没有时，`KnowledgeContext.Notice = "the knowledge layer records no baseline: no page can be called current (方案 §12.5)"`。

这个分支独立于 `Degraded`：Degraded 表示层**未生成**，Notice 表示层**生成了但所有相关页都没记 commit**——前者退化、后者只是 stale。

## 与 `Notices` 的区别

`ContextView.Notices []string`（[context.go:32](../知识层/架构设计.md)）是顶层字段——M4 已存在，承载 LKG fallback 等一般性提示。`KnowledgeContext.Notice` 是知识分支的局部提示：

- `degrade to records and events`：层没生成；
- `freshness unavailable: <err>`：`Evaluate` 报 `ErrNoGit`。

两者不冲突——`Notices` 顶层收其它来源，`KnowledgeContext.Notice` 收知识层自身的提示。

## 触发词匹配的归属（M7.1）

`context get --task` 的 trigger 命中与文本拼接——原先内联在 `internal/app/context.go` 的 `triggerHit` 与「`title + "\n" + description + "\n" + type + "\n" + workflowID + "\n" + workflowStep` 拼接——M7.1 抽到 `internal/knowledge/trigger.go`：

- `TriggerHit(triggers []string, lowerText string) (string, bool)`（[trigger.go:14-25](file://internal/knowledge/trigger.go#L14-L25)）：trim + lowercased 子串命中；第一个匹配的 trim 后的触发词作为返回。
- `WorkItemText(item *domain.WorkItem) string`（[trigger.go:30-41](file://internal/knowledge/trigger.go#L30-L41)）：title + description + type + workflowID + workflowStep，newline 拼接后 lowercase 一次。

调用方：

- `internal/app/context.go: knowledgeContext`（[context.go:283-378](file://internal/app/context.go#L283-L378)）：`text = knowledge.WorkItemText(item)`（[context.go:303](file://internal/app/context.go#L303)）→ `knowledge.TriggerHit(page.Triggers, text)`（[context.go:318](file://internal/app/context.go#L318)）。
- `internal/view/build.go: relatedItems`（[build.go:789-799](file://internal/view/build.go#L789-L799)）：视图层的「知识页 ↔ 工作项」关联，先 `relatedTexts(items)` 预计算每工作项的 `WorkItemText`（[build.go:777-786](file://internal/view/build.go#L777-L786)），再 `TriggerHit(triggers, texts[i])` 命中。

归属说明：匹配语义（大小写、TrimSpace、子串命中）现在属于知识层；`internal/app` 是上下文装配的调用方，`internal/view` 是视图聚合的调用方。抽取前后行为**逐字节一致**——`internal/app` 与 `internal/view` 都是先一次性 lowercase 文本，再调 `TriggerHit`，函数体内不再重复 `ToLower`。

## 边界与不做的事

- **不做语义相似度**：仅子串与路径匹配；不调用嵌入、不调用 LLM。
- **不缓存**：每次 `context get --task` 都重新 `Scan` + `Evaluate`——页面列表不大、git diff 走缓存（`loadChanges(commit)` memoized）。
- **不分页**：`matched` 是全集——大页面层的开销是 `Scan` 的 IO，匹配本身 O(pages × paths × sources)。
