# 知识层 · 上下文装配

本卡描述 M5 知识层在 `context get --task`（CLI）与 `context_for_workitem`（MCP）上的「任务上下文」装配：把工作项（`workitem`）的描述与「该任务会触碰的文件路径」映射到**这一任务应该读哪些知识页**，并把每一页的「新鲜度」单独标出。

## 入口

`internal/app/context.go: knowledgeContext(ctx, item, paths)` 是核心实现；调用方：

- CLI：`context get --task <id>` 在 [internal/cli/records.go](../项目接入与配置/CLI渲染与交换协议.md)；
- MCP：`context_for_workitem` 工具在 [internal/mcp/tools_context.go:36-48](../共享应用与MCP/工具与Profile.md)。

两入口都先把工作项路径（如 `internal/store/a.go`）解析出来，再传给 `knowledgeContext`。

## 三阶段选页

`knowledgeContext`（[context.go:283-372](../知识层/架构设计.md)）：

```mermaid
flowchart TD
    A[knowledgeContext item paths] --> B[project + Scan root → report]
    B -- err --> X1[internal]
    B -- ok --> C{report.Pages == 0?}
    C -- 是 --> D[Degraded=true + Notice 'degrade to records and events'; return]
    C -- 否 --> E[knowledgeState md → state]
    E -- err --> X2[internal]
    E -- ok --> F[文本 = title+description+type+workflowID+workflowStep; lowercase]
    F --> G[phase1: 遍历 pages, trigger 命中 → record MatchTrigger]
    G --> H[phase2: 遍历 pages, sources 命中 paths → record MatchSources]
    H --> I{matched 空?}
    I -- 是 --> J[返回空 pages + Baseline]
    I -- 否 --> K[Evaluate matched state → freshness]
    K -- err ErrNoGit --> L[Notice='freshness unavailable: ...'; 返回 matched 原样]
    K -- err 其它 --> X3[internal]
    K -- ok --> M[逐页 ref.Stale = freshness.Pages[i].Stale]
    M --> N[返回 KnowledgeContext]
```

**关键约束**：

- **per-page freshness**：`Evaluate` 只对 `matched` 跑——不是整层。理由：用户问的是「这任务相关的页面是否还描述当前代码」，不是「整个 wiki 是不是 fresh」。
- **matched 为空**：仍返回空 pages，但 `Baseline` 仍填（来自 `state`），`Degraded=false`（页面层**存在**，只是这任务无关）。
- **`Degraded` 只在「无页面层」时为 true**——其它情况（matched 空 / freshness 失败）**不**视为降级，只是空页或 stale。

## 文本拼接

任务文本（`text`）是 lowercase 的：

```text
text = lower(title + "\n" + description + "\n" + type + "\n" + workflowID + "\n" + workflowStep)
```

`workflowID(item)` / `workflowStep(item)`（[context.go:373-417](../知识层/架构设计.md)）从 `item.Workflow`（M3 引入的字段）抽取——若工作项不在工作流里则返回空串。`type`（workitem 自己的 kind：`task` / `bug` / `feature` 等）也参与。

`triggerHit(triggers, text)`（[context.go:374-380](../知识层/架构设计.md)）：

```go
for _, trigger := range triggers {
    trimmed := strings.TrimSpace(trigger)
    if trimmed == "" { continue }
    if strings.Contains(text, strings.ToLower(trimmed)) {
        return trimmed, true
    }
}
return "", false
```

- 子串匹配（不是分词）；
- 触发词 lowercased 与文本 lowercased 比对（**不**保留大小写敏感）；
- 第一个命中的触发词作为 `Reason`（如 `存储层`）；
- 同一页先匹配到 trigger 后再匹配 sources 时**不**覆盖——`refs[page.Path]` 已被设过则跳过。

## sources 命中

```go
for _, page := range report.Pages {
    sources := page.Sources
    if len(sources) == 0 {
        if entry, ok := state.Mapping(page.Path); ok {
            sources = entry.Sources
        }
    }
    for _, source := range sources {
        hit := ""
        for _, path := range paths {
            if knowledge.Match(source, path) {
                hit = source + " covers " + path
                break
            }
        }
        if hit != "" {
            record(page, MatchSources, hit)
            break
        }
    }
}
```

- `paths` 来自 CLI/MCP 调用方——通常是「这次任务会碰的文件路径」列表（如 `internal/store/a.go`）；
- `knowledge.Match` 走 `.gitignore` 风格语法（见[索引快照与匹配器](索引快照与匹配器.md)）；
- sources 为空时回退到 `state.Mapping(page.Path).Sources`——这是为什么生成器把 sources 写在 state 里更可靠（方案 §12.5）；
- 一个 page 命中 sources 后 `break`——只记第一条 source/path 配对。

## `RecordRef` 与 `KnowledgePageRef` 的边界

`ContextView`（[context.go:13-27](../知识层/架构设计.md)）有四类引用：

| 字段 | 类型 | 来源 |
|---|---|---|
| `RecentDecisions` | `[]RecordRef` | `internal/record`（决策记录） |
| `RecentFindings` | `[]RecordRef` | `internal/record`（发现记录） |
| `RecentArtifacts` | `[]RecordRef` | `internal/record`（工件） |
| `RecentEvents` | `[]EventRef` | `internal/events` |
| `knowledge` | `KnowledgeContext` | **M5 新增**——独立分支，不与上面四类混编 |

知识层与领域记录是两个数据源：知识是「文档」，记录是「事实」。两者在 `ContextView` 中并列，不相互依赖。`Degraded` 只影响知识分支——记录分支仍正常返回。

## 退出码

`context get --task` 没有专门退出码——沿用 M4 的 `ContextGet`：

- 成功：`exit 0`；
- 工作项不存在：`exit 4`（`GetWorkitem` 的 precondition 已被 `requireProjectRoot` 翻译）；
- `--task` 后无 ID：`exit 2`（`errUsage`）。

## 与 `Notices` 的区别

`ContextView.Notices []string`（[context.go:37-39](../知识层/架构设计.md)）是顶层字段——M4 已存在，承载 LKG fallback 等一般性提示。`KnowledgeContext.Notice` 是知识分支的局部提示：

- `degrade to records and events`：层没生成；
- `freshness unavailable: <err>`：`Evaluate` 报 `ErrNoGit`。

两者不冲突——`Notices` 顶层收其它来源，`KnowledgeContext.Notice` 收知识层自身的提示。

## 边界与不做的事

- **不做语义相似度**：仅子串与路径匹配；不调用嵌入、不调用 LLM。
- **不缓存**：每次 `context get --task` 都重新 `Scan` + `Evaluate`——页面列表不大、git diff 走缓存（`loadChanges(commit)` memoized）。
- **不分页**：`matched` 是全集——大页面层的开销是 `Scan` 的 IO，匹配本身 O(pages × paths × sources)。
