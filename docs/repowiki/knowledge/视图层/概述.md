# 视图层 · 概述

本模块是 M7 里程碑**只读视图层**（方案 §17）：把 `.devsys/` 状态文件 + git 状态 + 知识层状态装配成一份**视图快照**（`view.Model`），交给 `workspace view/build/serve` 三种形态作为稳定数据面。M7.1 装配、M7.2 离线静态站（`internal/sitestatic.Build` + `workloom workspace build --static`）、M7.3 本地只读服务（`internal/sitestatic.RenderPage` + `workloom workspace serve`）与 M7.4 知识新鲜度提示渲染（`sitestatic.freshnessHint` 派生字段）共同构成「一次装配、所有节都可信」的数据契约；视图域 = `workloom workspace`，与执行工作区 `workloom worktree` 是不同概念。

## 模块定位

- **做什么**：
  - **装配 `view.Model`**（`internal/view/build.go` 的 `Build(ctx, root, opts)`，M7.1）：读 `.devsys/project.yaml`、`.devsys/state/current.yaml`、`.devsys/state/milestones.yaml`、`.devsys/workitems/*.yaml`、`.devsys/runs/*.yaml`、`.devsys/runs/*.jsonl`、`.devsys/decisions|findings|artifacts/*.yaml`、`.devsys/approvals/*.yaml`、`.devsys/workflows/*.md`、`.devsys/knowledge/{state.json,snapshot.json}` + 项目配置的 page roots + git HEAD/branch/changes，按节填出 `Project/Progress/Runs/Records/Knowledge` 五节 + 顶层 `Trust/Baseline/Sources/Problems`。每节带 `Provenance.Sources`（项目相对路径，目录以 `/` 结尾）；顶层 `Sources` 是各节 sources 的 `sortedUnique` 并集 + git 基线。**这是 M7.2/M7.3 的唯一数据入口**。
  - **信任态分类**（`view.Trust.State` 三态，M7.1）：`ok`（共享锁下读取）/ `advisory_unlocked`（无锁文件，退回 `storage.InspectUnlocked`，仍渲染业务事实）/ `pending_transaction`（存在待恢复事务，按方案 §15.4 不渲染业务事实，列出事务 ID 并提示 `workloom recover`）。三种状态是视图对「这一份快照能信多少」的明示答案。
  - **§7.4 就绪判定嵌入进度节**（`view.Progress.Readiness`，M7.1）：通过 `next.Evaluate(next.Input{...})` 复算 `workloom next` 的 verdict/reasons/risks/fixes/next，传入与 `next` 同样的工作项/里程碑/事务/租约/metadata 缺陷/policy 缺陷/审批参数；视图在此基础上多传 `PolicyIDs`（声明的策略 id）+ `DefaultPolicy`（项目级默认策略）+ `QualityBlocks: next.QualityBlocks(items, facts.policyOf(default))`——`QualityBlocks` 让 ready 工作项的质量门判定与 `workitem claim` 同源，视图判放过的事 `claim` 也判放过、`rep.Risks` 里 `RiskQualityBlocked` 出现时即意味着 `claim` 必拒——视图与就绪判定共用一份实现，不会彼此偏离；v0.1.3 起再增传 `HasBlueprint`（project.yaml 是否声明 blueprint artifact，供空项目风险判定）+ `DeadAttempts`/`InFlight`（由 `attemptSignals` 复用 `next.ClassifyAttempts` 对每个工作项最新 run 与事件流行数分类，与 `workloom next` 同一份）——僵死领取（recover_claim 档）与在飞尝试的 CONCERNS 信号在视图与 CLI 间不分叉。
  - **git 基线**（`view.Baseline`，M7.1）：`Available/Commit/Branch/Dirty *bool/ChangedFiles/Reason`；git 不可用时 `Available=false`、脏位 `nil`（不假装 false），原因写 `Reason`。
  - **知识新鲜度嵌入知识节**（`view.Knowledge`，M7.1）：复用 `internal/knowledge` 的 `Scan/LoadState/Head/Changes/Evaluate/AdapterByName/MergeStates`——状态机裁决 `fresh/stale/missing/unavailable`；其中 `unavailable`（如无 git）是「问题答不出来」而不是「新鲜」（方案 §12.5）。
  - **运行事件流的断尾报告**（`view.RunEntry.StreamTorn`，M7.1）：通过 `storage.InspectJSONL` 判定「run 的事件流是否未完整闭合」，**只报告不修复**——修复属 M6.1 的 run 写入侧职责。
  - **确定性聚合**（M7.1）：模型无墙钟字段（`Options.Now` 只喂就绪判定，不落 JSON）；列表先定序（runs 按 started_at 倒序再 id、decisions/artifacts 按 created_at 倒序再 id、findings 按 id、pages 按 path、items 按 id）再按 `DefaultLimit=50`（`--limit` 覆盖）截断并置 `Truncated`；同一状态两次构建 marshal 出来**逐字节相同**。
  - **离线静态站渲染**（M7.2，`internal/sitestatic`）：`Build(m, out, generatedAt)` 把 `view.Model` 落成自包含站点——6 页按 `PageFiles`（[internal/sitestatic/static.go:24-39](file://internal/sitestatic/static.go#L24-L39)）顺序 `index/tasks/workflows/runs/records/knowledge.html` + `assets/style.css` + `data/model.json`，共 8 个文件，零 JavaScript、零外部引用（纯本地样式表 + 相对链接）；模板用 `html/template` 全转义。`DefaultOutRel=".devsys/dist/site"`（[internal/sitestatic/static.go:39](file://internal/sitestatic/static.go#L39)）落在 `.devsys/dist/` 下，受 `.gitignore` 保护不污染 git freshness 信号。`ResolveOut` 拒绝把 `.devsys/` 自身、项目根、`.git/` 当输出目录（错误映射到退出码 2）。
  - **本地只读服务渲染**（M7.3，`internal/cli/workspace_serve.go`）：`serveHandler` 每请求现装一次 `view.Build`（无快照缓存、运行期零写入），再用 `sitestatic.RenderPage`（[internal/sitestatic/render.go:17](file://internal/sitestatic/render.go#L17)）/ `sitestatic.ModelJSON` / `sitestatic.Stylesheet` 与 `Build` 落盘**逐字节一致**地回答 `/`、`/<page>.html`、`/assets/style.css`、`/data/model.json`、`/api/view`、`/healthz`。非 GET/HEAD 一律 `405 Method Not Allowed` + `Allow: GET, HEAD`。缺省 `127.0.0.1:8080`（[internal/cli/workspace_serve.go:25-28](file://internal/cli/workspace_serve.go#L25-L28)）；非环回 host 必须显式 `--allow-remote`，否则 usage 错误退出码 2。
  - **知识新鲜度提示渲染**（M7.4，`internal/sitestatic/static.go:171-185`（[static.go:171-185](file://internal/sitestatic/static.go#L171-L185)））：`freshnessHint(k view.Knowledge)` 是纯渲染函数——`fresh` 不显示；`stale`→「知识已过期」+ `workloom knowledge refresh`；`missing`→「知识页面层缺失」+ `workloom knowledge refresh --full`；`unavailable`→「知识新鲜度不可判」+ 空命令。结果通过 `siteData` 的四个派生字段 `ShowFreshness/FreshnessTitle/FreshnessText/FreshnessReason/FreshnessCmd` 喂模板，模板只开关「是否显示」，不写判决字符串。CLI 文本脸只新增 `workloom knowledge refresh [--full]` 提示行，JSON 信封与退出码不变；底层判定复用 `internal/knowledge.Evaluate`，不复制状态机。
  - **本批（v0.1.9，ca58d27→19b9149）**：主命令改名 `workloom`（入口 `cmd/workloom/main.go`），`devsys` 保留为**同一二进制的兼容别名**（入口 `cmd/devsys/main.go`，install 脚本同时装两个名字，[scripts/install.sh:92-98](file://scripts/install.sh#L92-L98)）；视图层示例与内部输出串（`workloom recover` / `workloom init` / `workloom knowledge refresh [--full]`）统一改名，`view.Model` 契约、JSON 信封与退出码 0/2/3 不变。另：Git 本轮起为**可选能力**——非 Git 项目也是合法的 `.devsys/` 项目，视图对应 `Baseline.Available=false` 与 `Knowledge=unavailable` 两个既有降级分支（Git 项目的 worktree 分支前缀仍是 `devsys/<key>`，[internal/workspace/workspace.go:24](file://internal/workspace/workspace.go#L24)）。
- **不做什么**：
  - **不恢复事务**（M7.1）：即使存在 pending transaction，视图也只 `report` + `pendingReadiness`（FAIL + `workloom recover` 修复项），从不调用 `reconcile.Recover` 或 `storage.RecoverPending`。
  - **不修复断尾事件流**（M7.1）：`streamTorn` 只查 `storage.InspectJSONL` 的 `Complete` 标志位；写入侧的截断（`storage.RepairTornTail`）不归本层。
  - **不写 `.devsys/.cache/`**（M7.1）：`storage.Read` 会建锁并写缓存，本层只走 `storage.Inspect`（在已有锁文件上取共享锁，不创建）与 `storage.InspectUnlocked`（无锁文件时降级）。
  - **不起进程**（不探测生成器，M7.1）：生成器适配层的 `Probe(ctx)`（如 `repowiki adapter probe`）需要跑进程，本层从不调用——知识层用 `AdapterByName + Import` 读适配器的**已落盘** state 即可。
  - **view 包不渲染页面，渲染在 sitestatic 包（同仓 Go）**：M7.2/M7.3 的渲染层都是 `internal/sitestatic`（M7.2 落盘、M7.3 通过 `RenderPage` 实时装配），`internal/view` 只输出 JSON 信封 + `workspace view` 一行一事实的人类输出。
  - **不接管执行工作区**（M7.1）：执行工作区是 `workloom worktree`（方案 §4.8，包 `internal/workspace`）——Git 项目落成仓库的 linked worktree（分支前缀仍是 `devsys/<key>`），非 Git 项目落成**目录工作区**（无分支，[internal/workspace/workspace.go:1-4,57-66](file://internal/workspace/workspace.go#L57-L66)、[ensureDirectory](file://internal/workspace/workspace.go#L147)）；它与 `workloom workspace view`（视图域，方案 §17）是两个不同的概念——CLI 帮助文本（[internal/cli/cli.go:82](file://internal/cli/cli.go#L82)）与本卡都对两者做了区分。
  - **M7.3 不写盘**：`workspace serve` 运行期所有响应都从内存装配，进程退出后没有遗留状态；它也不缓存 `view.Model`。
  - **M7.4 不复制判定**：视图层只复用 `internal/knowledge.Evaluate` 与 `view.Knowledge.Status`，`freshnessHint` 只决定「显示什么文本 + 给哪个命令」，不在渲染侧重做状态机。
