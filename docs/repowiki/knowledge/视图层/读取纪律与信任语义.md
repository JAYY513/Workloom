# 视图层 · 读取纪律与信任语义

视图层的**第一性原则**是「**只读**」：任何装配都不应留下磁盘痕迹、任何修复动作都不应属于本层。本卡梳理「零写入契约」的精确含义、测试层的三种验证手段、`advisory_unlocked` 与 `pending_transaction` 的语义差、知识节 `missing` 与 `unavailable` 的区别、以及「确定性」在工程上的兑现方式。

## 零写入契约

**包级承诺**（[internal/view/view.go:1-15](file://internal/view/view.go#L1-L15)）：

> The package never writes. Reads go through storage.Inspect — a shared lock on an existing lock file, never created — with storage.InspectUnlocked as the fallback for copies where no writer ever ran (a read-only mount of a fresh checkout). It never recovers transactions, never repairs torn tails, never touches `.devsys/.cache/` and never probes a generator (a probe runs a process).

具体落到代码：

| 不做的动作 | 替代做法 | 位置 |
|---|---|---|
| 不创建 `.devsys/local/lock` | `inspectSnapshot` 先 `st.Inspect`，缺锁文件时退 `st.InspectUnlocked`，**永不**调 `st.Lock` | [collect.go:23-29](file://internal/view/collect.go#L23-L29) |
| 不写 `.devsys/.cache/` | 装配只走 `Inspect`/`InspectUnlocked` + `storage.Reader.Read`；从不调 `storage.Read`（会建锁并写缓存） | 装配全文 |
| 不恢复事务 | `pendingReadiness` 走 `next.Evaluate` 报 FAIL + `devsys recover` 修复项；从不调 `reconcile.Recover` / `storage.RecoverPending` | [build.go:159-165](file://internal/view/build.go#L159-L165) |
| 不修复断尾事件流 | `streamTorn` 仅查 `storage.InspectJSONL` 的 `Complete` 标志位；从不调 `storage.RepairTornTail` | [build.go:435-443](file://internal/view/build.go#L435-L443) |
| 不探测生成器 | 知识层只读 `AdapterByName + Import` 拿适配器**已落盘**的 state；从不调 `Adapter.Probe`（Probe 起进程） | [build.go:648-665](file://internal/view/build.go#L648-L665) |
| 不写 `.devsys/workspaces/` | 装配路径不引用 `internal/workspace`（那是执行工作区） | import 列表 |
| 不写 LKG 缓存 | 政策读取走 `workflow.Load`（明文），不走 `workflow.Resolve`（会写 LKG） | [build.go:311-344](file://internal/view/build.go#L311-L344) |

## 三种「零写入」验证手段

测试层用三种独立手段验证「不写」：

### 1. 文件指纹前后比对（`TestBuildWritesNothing`）

`internal/view/view_test.go:308-318` + `fingerprint`（[view_test.go:486-520](file://internal/view/view_test.go#L486-L520)）：

```text
before := fingerprint(root)        # sha256 整文件 + 大小 + mtime
build(root)
after  := fingerprint(root)
要求 before == after（含 lock 文件）
```

`fingerprint` 遍历 root 下每个文件（除 `.git/`），按 `size + mtime + sha256` 三元组记录；任何被改动/新增/删除的文件都会触发 `diffFingerprints` 报错。

**保证**：`Build` 不修改**任何**文件，包括 `.devsys/local/lock`、`.devsys/.cache/*`、运行事件流尾、知识层 state、git 索引。

### 2. 整树只读副本（`TestBuildOnAReadOnlyCopy`）

`internal/view/view_test.go:349-378`：

```text
source := fixture(t)                 # 含 lock 文件的完整 fixture
copyTree(t, source, copyRoot)        # 复制到新目录
filepath.WalkDir(copyRoot, ...)      # 逐文件 os.Chmod(path, 0o444)
t.Cleanup(...)                        # 测试结束 chmod 回 0o644
m := build(t, copyRoot)
要求 m.Progress.Items == 2 && m.Runs.Entries == 1 && m.Knowledge.Status == KnowledgeFresh
```

**保证**：即使整个 `.devsys/` 都是 `0o444`（含锁文件），视图仍能装配完整——`storage.Inspect` 不需要写权限，`InspectUnlocked` 也不需要；任何「悄悄写」都会失败。

### 3. 无锁文件时不创建锁（`TestBuildWithoutLockFileStaysReadable`）

`internal/view/view_test.go:320-347`：

```text
root := projectOnly(t)               # 只 init，没写过状态 → 无 lock 文件
lock := .devsys/local/lock
os.Stat(lock) → 必须 ErrNotExist
before := fingerprint(root)
m := build(t, root)
要求 m.Trust.State == TrustAdvisory && !m.Trust.InspectionOK
要求 m.Trust.Note != ""
要求 m.Project.ID != ""              # 仍渲染业务事实
要求 os.Stat(lock) → 仍 ErrNotExist   # 关键：不创建锁
要求 fingerprint(before) == fingerprint(after)
```

**保证**：缺锁文件时视图不会为了「拿到一个锁」而创建它——`inspectSnapshot` 把 `ErrLockUnavailable` 翻译成「降级到 `InspectUnlocked` + advisory=true」而不是「先建锁再读」。

实跑证据（[docs/开发记录.md:365](file://docs/开发记录.md#L365)）：真实 `.devsys` 快照（`docs/examples/m1-devsys/`）两次 `--json` 同 3288 字节；0444 副本上同一模型（除 git 基线）且未创建 `local/lock`。

## 信任态：advisory vs pending

视图把「这一份快照能信多少」分成**三种状态**（[view.go:32-42](file://internal/view/view.go#L32-L42)）：

| 常量 | JSON 值 | 触发 | 业务事实？ | 与 `devsys next` 的差别 |
|---|---|---|---|---|
| `TrustOK` | `"ok"` | `storage.Inspect` 拿到共享锁 + `reconcile.Doctor` 无 pending | 渲染 | 同 `next`：PASS / CONCERNS |
| `TrustAdvisory` | `"advisory_unlocked"` | 锁文件不存在（只读副本/从未写过状态）→ `InspectUnlocked` | **仍渲染** | `next` 更严格：无锁文件即不渲染；视图是快照不是判决（M7.1 偏差 ①） |
| `TrustPending` | `"pending_transaction"` | `reconcile.Doctor` 报 pending **或** `inspectSnapshot` 撞 `*storage.PendingTxnError` | **不渲染**（`emptyBusiness`） | 同 `next`：FAIL + `devsys recover` |

### `advisory_unlocked` 的语义

> 「这一刻的 `.devsys/` 没有写锁保护，所以你看的内容可能正在被改——但版本是确定的（写者必须先 commit）……」

具体行为（[build.go:94-108](file://internal/view/build.go#L94-L108)）：
- `m.Trust.State = "advisory_unlocked"`
- `m.Trust.Note = original + " reads were lock-free: no project lock exists (no writer ever ran), so the snapshot is advisory"`
- `m.Trust.InspectionOK = false`（与 Doctor 报告独立）
- 五节都照常渲染（项目、进度、运行、记录、知识）；baseline 仍读。
- **建议**：渲染层在 `advisory` 时**提示**用户「此视图无锁保护，谨慎对待」，但**不**阻塞渲染。

### `pending_transaction` 的语义

> 「存在待恢复事务，状态文件可能半应用——版本号尚未提交，业务事实不可信……」

具体行为（[build.go:75-82](file://internal/view/build.go#L75-L82) + [build.go:145-154](file://internal/view/build.go#L145-L154)）：
- `m.Trust.State = "pending_transaction"`
- `m.Trust.Pending = pendingIDs(...)`：待恢复事务 ID 列表（来自 Doctor 或 `PendingTxnError.IDs`）。
- `emptyBusiness(m)`：
  - `m.Project.Degraded = true`，`m.Project.Reason = pendingReason`（[build.go:28](file://internal/view/build.go#L28)，文案 `"pending transactions: run `devsys recover` before trusting business state (方案 §15.4)"`）
  - `m.Progress.Degraded = true`，`m.Progress.Reason = pendingReason`
  - `m.Progress.Items = []`，`m.Runs.Entries = []`，`m.Records.Decisions/Findings/Artifacts = []`
  - `m.Knowledge.Status = KnowledgeUnavailable`，`m.Knowledge.Degraded = true`，`m.Knowledge.Reason = pendingReason`
- `m.Progress.Readiness = pendingReadiness(nowFn(), ids)`：走 `next.Evaluate` 产出 `Verdict=FAIL` + `Fixes[0].Command = "devsys recover --actor operator --reason \"recover interrupted state\""`（`recoverCommand` 常量，[build.go:25](file://internal/view/build.go#L25)）。
- **基线仍给**：`m.Baseline` 与 git 状态照常报告——git 与 `.devsys/` 状态独立。
- **建议**：渲染层在 `pending` 时**只渲染** `Trust/Sources/Baseline` 与 `Progress.Readiness.Fixes`，**不**渲染任何业务事实；这是方案 §15.4 的硬约束。

### `devsys next` 与 `view.Model.Trust` 的差别（关键）

| 维度 | `devsys next` | `view.Build` |
|---|---|---|
| `next.Report.Verdict` 在 advisory 下 | **FAIL**（无锁文件即不渲染） | `CONCERNS` 或 `PASS`（业务节照常渲染） |
| `next.Report.Verdict` 在 pending 下 | **FAIL** + recover 修复项 | **FAIL** + recover 修复项（经 `pendingReadiness`） |
| 任务列表 | 只列「可调度的」 | 全部列出（视图不调度） |
| 立场 | 判决（决定下一步做什么） | 快照（呈现当前事实） |

`view.Progress.Readiness` 在 advisory 下与 `devsys next` 的 verdict **可能不同**——这是 M7.1 接受的偏差（[docs/开发记录.md:364](file://docs/开发记录.md#L364) 偏差 ①），原因：M7.1 验收要求「只读副本也能出完整视图」。

## 知识节 missing 与 unavailable

`Knowledge.Status` 四态中，`missing` 与 `unavailable` 都意味着「不能给 fresh 答案」，但**触发条件与降级语义不同**：

### `KnowledgeMissing`（方案 §12.6）

```text
报告: report.Pages == 0          # 无页面层
  - 生成器未配置（md.Config.KnowledgeGenerator 空）
  - 或生成器未跑过（state.json 还没生成）
Status: KnowledgeMissing
Reason: "no page layer: no generator is installed or configured (方案 §12.6)"
```

这是**支持性降级**：视图不报错，用户/agent 应该去配/跑一次生成器。

### `KnowledgeUnavailable`（方案 §12.5）

```text
报告: report.Pages > 0            # 有页面层
  - 但 knowledge.Evaluate 失败（典型：git 不可用）
Status: KnowledgeUnavailable
Reason: "freshness unavailable: " + err.Error()
Degraded: true
```

这是**问题答不出来**：「cannot tell」≠ fresh——CI 不能因此放过。

> 区分要点：`missing` 是「层不存在」，`unavailable` 是「层存在但问不出来」；前者是配置问题，后者是环境问题。

`pending_transaction` 状态下，`emptyBusiness` 把 `Knowledge.Status` 设为 `KnowledgeUnavailable`（[build.go:151-153](file://internal/view/build.go#L151-L153)）——这里取 `Unavailable` 而非 `Missing`，因为 `.devsys/knowledge/state.json` 与 `.devsys/knowledge/snapshot.json` 在事务存在时可能半应用，不能说「层不存在」。

## 确定性：双跑逐字节一致

视图承诺「同一状态两次构建 marshal 出来逐字节相同」（[internal/view/view.go:13-14](file://internal/view/view.go#L13-L14)）。这一性质由五个工程约束共同保证：

### 1. 模型无墙钟字段

`time.Time` 只出现在两类位置：
- **领域对象本身的时间**：`Item.CreatedAt/UpdatedAt`、`RunEntry.StartedAt/FinishedAt`、`RecordRef.CreatedAt`——这些来自文件内容，不来自 `Now`。
- **可选指针**：`Baseline.Dirty`、`Item.LeaseUntil`、`Item.NextAttemptAt`、`RunEntry.FinishedAt`、`RunEntry.Advanced`、`RecordRef.CreatedAt`——同上。

`Options.Now`（[view.go:54-60](file://internal/view/view.go#L54-L60)）只喂 `next.Evaluate`，**不**进入 `view.Model`。测试用 `Options{Now: fixedClock}` 控制时钟（[view_test.go:32](file://internal/view/view_test.go#L32)），但即便换时钟，模型不变。

### 2. `newModel` 预填所有 slice

`newModel`（[build.go:117-140](file://internal/view/build.go#L117-L140)）把**每一个** slice 都初始化为空（`[]string{}`、`[]domain.Milestone{}`、`[]RunEntry{}`、`[]RecordRef{}` 等）——「没找到」是 `[]` 不是 `null`。这避免了 JSON 编码时 `omitempty` slice 字段在「找到 0 项」时消失带来的差异。

### 3. 列表先定序后截断

每个列表节在截断前先排序：

| 节 | 排序键 |
|---|---|
| `Progress.Items` | `id` 升序（[build.go:280](file://internal/view/build.go#L280)） |
| `Runs.Entries` | `StartedAt` 倒序再 `ID` 升序（[build.go:387-392](file://internal/view/build.go#L387-L392)） |
| `Records.Decisions` | `CreatedAt` 倒序再 `ID` 升序（[build.go:466-471](file://internal/view/build.go#L466-L471)） |
| `Records.Findings` | `id` 升序（[build.go:496](file://internal/view/build.go#L496)） |
| `Records.Artifacts` | `CreatedAt` 倒序再 `ID` 升序（[build.go:519-524](file://internal/view/build.go#L519-L524)） |
| `Knowledge.Pages` | `knowledge.Scan` 内部排序（按 path） |
| `Trust.Pending` | `pendingIDs` 内 `sort.Strings`（[build.go:740-747](file://internal/view/build.go#L740-L747)） |

`capList[T]`（[build.go:750-755](file://internal/view/build.go#L750-L755)）只切末尾，不改顺序；`Truncated` 标志告诉调用方「后面还有」。

### 4. `sortedUnique` 路径去重

`Sources`（顶层 + 各节 `Provenance.Sources`）都过 `sortedUnique`（[collect.go:127-139](file://internal/view/collect.go#L127-L139)）：去空、去重、`sort.Strings`。这保证：
- 同一路径被多次 `noteDevsys` 只出现一次。
- 多节访问同一文件（如 `.devsys/project.yaml` 同时被 `project` 与 metadata problems 记录）只贡献一份。
- 两次装配的 `Sources` 数组按字典序排列，逐字节一致。

### 5. map 字段的键序

`Progress.Counts` 是 `map[string]int`；`encoding/json` 对 map 的编码顺序是**字典序**——这是 Go 标准库保证（`json.Marshal` 内部用 `textMarshaler` + 排序），与具体实现无关。

### 测试断言：`TestBuildIsDeterministic`

`internal/view/view_test.go:293-306`：

```go
first  := json.Marshal(build(t, root))
second := json.Marshal(build(t, root))

```
