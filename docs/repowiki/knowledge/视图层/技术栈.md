# 视图层 · 技术栈

视图层在 Go 1.26 + 既有内部包之上**零新增第三方依赖**：没有 git 库、没有 yaml 解析库（领域结构 `domain.DecodeYAML` 已在 M0 沿用）、没有模板引擎、没有渲染框架。本卡梳理非默认选型与「不引入的依赖」，便于 review 时一眼看清克制点。

## 不引入的依赖

- **不引入** `github.com/go-git/go-git` / `github.com/src-d/go-git` 等 Go git 库——git 状态只读 `HEAD`/`abbrev-ref`/`status --porcelain`/`diff`，系统 `git` 二进制足够；间接调用统一在 `internal/knowledge`（[freshness.go:206](file://internal/knowledge/freshness.go#L206)），视图层只调 `Head/Changes`，不直接 exec。
- **不引入** YAML 库替代品——所有 YAML 走 `domain.DecodeYAML`（M0 沿用 `gopkg.in/yaml.v3`），不引入 `github.com/goccy/go-yaml` / `github.com/ghodss/yaml`。
- **不引入** `text/template` / `html/template`——CLI 人类输出是 `fmt.Fprintf` 一行一事实；JSON 信封是 `encoding/json`。M7.2/M7.3 的渲染是 TypeScript/React 的事，与 Go 视图层无关。
- **不引入** JSON 之外的 IDL 库——不引入 Protocol Buffers / FlatBuffers / Cap'n Proto；`view.Model` 是普通 Go 结构 + JSON tag，schema 通过 `SchemaVersion=1` 字段显式版本化。
- **不引入** 同步原语库——同步靠 `context.Context`；并发安全由 storage 层共享锁/无锁读保证。
- **不引入** 模板驱动的代码生成——`Provenance.Sources` 是路径字符串列表，不生成结构体；测试断言也不走 fixture 生成器。

## 关键非默认决策

### 1. 共享锁 vs 裸读

视图层**不**走 `os.ReadFile` 直读 `.devsys/*`——所有读都过 `storage.Inspect`/`InspectUnlocked`。理由：

- `Inspect` 在已有锁文件上取**共享**锁（多读者可并发、写者独享），避免「读到一半被写者改」造成的视图撕裂。
- `InspectUnlocked` 用于锁文件不存在的场景（只读副本 / 新检出），避开「为了读而写锁」破坏只读契约。
- `storage.Reader` 暴露的 `Read` 还承担「目录存在性 + 路径规范化」职责，比裸 `os.Open` 安全。

### 2. git 经 `internal/knowledge` 中转

视图层**不**直接 `exec.Command("git", ...)`——所有 git 调用走 `internal/knowledge.Head/Changes`（[build.go:712-718](file://internal/view/build.go#L712-L718)）。理由：

- 「git 在哪里、git 不可用怎么降级」是知识层的事（M5.3 起就有了 `ErrNoGit` 概念），视图层只消费「commit/branch/changed files」。
- 测试用 `internal/knowledge.freshness_test.go` 的 git 助手（`exec.Command("git", "-C", root, ...)`），视图层自己的 `view_test.go` 仍以相同方式 init/seed（[view_test.go:42-51](file://internal/view/view_test.go#L42-L51)）——但视图层代码**永不**直接 exec git。
- 复用 `internal/knowledge` 让视图层与 `context get --task` 共享同一份基线计算。

### 3. JSONL 断尾检测经 `storage.InspectJSONL`

视图层**不**自己实现「读最后一行看 `\n` 结尾」——直接调 `storage.InspectJSONL`（[build.go:441](file://internal/view/build.go#L441)）。理由：

- `storage.TailStatus.Complete` 是 M5 已建立的语义（`internal/storage/jsonl.go:25-49`）；`true` 表示文件空或末尾有换行，`false` 表示断尾。
- `ErrIncompleteTail` 是写入侧的哨兵（`internal/storage/errors.go:30`），视图层只**消费** `TailStatus`，不消费错误类型——避免与写入路径的语义耦合。
- 复用让「视图报告断尾」与「写入侧拒绝追加」走同一份判断逻辑，不会出现「视图说完整、写入侧说断尾」的不一致。

### 4. `Options.Now` 注入而非全局时钟

`view.Options.Now`（[view.go:54-60](file://internal/view/view.go#L54-L60)）是显式注入点：

- 测试 `Options{Now: fixedClock}` 控制时钟；模型本身不带 `Now`。
- 同一状态两次构建 marshal 出来**逐字节相同**（[view_test.go:293-306](file://internal/view/view_test.go#L293-L306)）；这把确定性保证做到模型层而不是 Build 入口。

### 5. 零渲染依赖

视图层**不**实现任何 HTML/Markdown/ANSI 颜色渲染。CLI 人类输出是 `fmt.Fprintf(stdout, ...)` 一行一事实（[workspace.go:73-132](file://internal/cli/workspace.go#L73-L132)）；M7.2 的静态构建与 M7.3 的 serve 在 TypeScript/React 层独立演化。这是视图层与渲染层的解耦边界——也是为何 `view.Model` 的 JSON 契约如此严格的原因。
