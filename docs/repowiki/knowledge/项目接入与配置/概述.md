# 项目接入与配置

## 模块定位

本模块是 Workloom 的**接入与配置层**：用户与 `devsys` 二进制之间唯一的接触面。负责把命令行参数解析成命令、把命令分发给底层存储与领域模块、把结果按人/机两种格式渲染到 stdout/stderr，并用一个固定退出码族把错误类别告诉调用脚本。

M4 起 `internal/cli` 薄化为「flag 解析 + 渲染 + 退出码翻译」；所有业务分发迁出到共享应用服务 `internal/app`（详见 [共享应用与 MCP](../共享应用与MCP/概述.md)）。`internal/mcp` 在同一服务之上以官方 Go SDK 暴露工具族。MCP 服务端的约束在 [错误语义](../共享应用与MCP/错误语义.md) 与 [工具与 Profile](../共享应用与MCP/工具与Profile.md) 中描述；CLI/MCP 的双入口一致性来自共享服务 + `*app.Error` 的 `Kind/Class` 统一翻译。

M6 起 `internal/cli` 在 M4 薄化渲染层之上**进一步承载执行层 CLI 适配**：`worktree prepare|remove|list` 走 `app.WorkspacePrepare/Remove/List`；`dispatch --once|--watch|--dry-run` 走 `app.Dispatch`（一次 recover + sweep + plan + spawn）；`run exec --harness|--timeout` 走 `app.RunExec`（驱动 harness 适配器）；`run prompt --round|--write` 走 `app.RunPrompt`（组装首轮/续轮文本 + 写 local/）；`run verify` 走 `app.RunVerify`（claim head vs current head）；`run complete|fail|cancel` 走 `app.RunFinish`（终态 + reason + force reviewer accept）。`DEVSYS_PROJECT_ROOT` 决定 `appService()` 绑定哪个项目根——agent 在 workspace（git worktree）内运行时从 `HookEnv` 注入，避免写入 worktree 自带的 `.devsys/`。配置层 `config.yaml` 增 `workspace_root`（默认 `<project>/.devsys/workspaces`）与 `dispatch_command`（默认 `devsys run exec …`）两个可选字段。

| `devsys next` | 否 | 通过 `reconcile.Doctor` + `internal/next.Evaluate` 给出 PASS/CONCERNS/FAIL 与 §7.4 唯一推荐动作；exit 恒 0 |

| **`devsys dispatch --once\|--watch\|--dry-run\|--max`** | 是（中间） | **M6** 一次调度 tick：`recover`（事务恢复）→ `sweep`（失败/超时/停滞 attempt 收尾，可复现退避）→ `plan`（`internal/dispatch.Plan` 纯函数）→ `claim` → `prepare workspace` → `spawn`；`--dry-run` 不创建任何 `.devsys/runs/*.yaml`；`--watch` 前台 Ctrl-C 退出 0。 |
| **`devsys run exec`** | 是 | **M6** 驱动一次 attempt：默认 shell 形态跑 `--` 后的命令；`--harness codex\|opencode\|claude` 走对应 CLI 适配器（stdin 投递 + 进程树终止 + 行缓冲流）；`--timeout` 终止整棵进程树；`--model` 喂给 harness；`--round` 续 session；输出 mirror 到 stdout/stderr。强制 `--actor`/`--reason`；Ctrl-C 取消。 |
| **`devsys run prompt`** | 否 | **M6** 组装一次 round 的提示词预览：`internal/prompt.Assemble` 首轮全 brief、续轮 delta + remaining；`--round` 指定轮号（默认下一个）；`--write` 落到 `.devsys/local/runs/<id>/round-<N>.md`（不提交）；`--json` 暴露 `Hash`（sha256(text)）+ `Refs`。 |
| **`devsys run verify`** | 否 | **M6** 完成校验（只读）：比较 `claim_head`（claim 时记录的分支 head）与 `current_head`（`git rev-parse refs/heads/<branch>`）；任一缺失 → `Advanced=false` + reason。 |
| **`devsys run complete\|fail\|cancel`** | 是 | **M6** 终态 attempt：`complete` 默认走 `RunVerify` 守卫，未 advance → exit 4 + run 进 `failed` + workitem 进 `review`；`--force --by <reviewer>` 接受 verify 拒绝；`fail` / `cancel` 不走 verify，直接写终态 + reason/note。强制 `--actor`/`--reason`；可选 `--expect`。 |

全局开关：

- `--json`：把所有成功结果与错误结构渲染为单行 JSON 写到 stdout/stderr。
- `--jsonl`：列表命令按一行一条 JSON 记录输出（`--jsonl workitem list`、`--jsonl event list` 等）。
- `--quiet`：抑制成功输出（错误仍然写 stderr）。

退出码契约在 [`internal/cli/cli.go:33-44`](../../../internal/cli/cli.go#L33-L44) 固定：

```text
0 OK · 1 Internal · 2 Usage · 3 Precondition · 4 Invalid
```

CLI 与 MCP 共享同一份 `*app.Error.Class()`（usage / precondition / internal / invalid），分别映射到 CLI 的 `2 / 3 / 1 / 4` 退出码与 MCP 的同名 tool error code。知识层预留 10/11（M5 到达；0 fresh / 10 stale / 11 missing）。

M2 在保留 `CodeInvalid = 4`（受管状态不可信）语义同时，扩展了 `CodePrecondition = 3` 的两类新用法（[internal/cli/cli.go:70](../../../internal/cli/cli.go#L70)）：

- workitem 命令收到与 `workitem get` 输出版本哈希不匹配的 `--expect`（hash 长度错误或文件已变更）→ `CodePrecondition`。
- `repair --apply` 收到的 `--confirm` 摘要与当前干跑摘要不一致 → `CodePrecondition`，错误提示要求重跑 `repair --dry-run`。

M3 在同一退出码下扩展了三族新用法：

- workflow / approval / workitem 的领域错误统一升为 `CodeInvalid = 4`，`kind` 分别取 `"workflow"` / `"approval"` / `"workitem"`。
- `workflow check` 把策略文件的结构/类型/必填/交叉引用错误升为 `CodeInvalid`；未知键 warning 不阻断退出码。
- `devsys next` exit 恒 0；脚本按 `--json next` 输出的 `verdict` 分支（PASS / CONCERNS / FAIL）。

M4 进一步把上述所有「领域错误→退出码」翻译收敛到 `toCoded`（[internal/cli/cli.go:99-117](../../../internal/cli/cli.go#L99-L117)）——不再散落在 `workitemError` / `approvalError` / `mapWorkflowError` 三个工具函数里；新加的 `decision / finding / event / artifact / run / context / project` 错误也走同一路径。MCP 服务端的 `fail / failNotice / usageFail` 走相同 `*app.Error` 到 `{code, message, problems, notice}` 的翻译。

M6 进一步在执行层扩展：

- `devsys run exec` 在用户取消（Ctrl-C）或 `--timeout` 到期时**终止整棵进程树**——POSIX 走 `killProcessGroup`（`Setpgid + kill -PGID`），Windows 走 `killProcessTree`（`JobObject + TerminateJobObject`）。
- `devsys run complete` 未通过 verify 守卫时 workitem 进 `review` 状态——`review` 仍是只读，与 `next.Evaluate` 的 `stale_review` 风险信号对接。
- `devsys dispatch --watch` 是前台循环；Ctrl-C 后整体退出码 0（tick 内的失败以 notice 形式回报，不让 watch 整体退出）。
- `DEVSYS_PROJECT_ROOT` 在 HookEnv 与 attempt 启动时被注入，让 worktree 内运行的 agent 把报告写回主仓库的 `.devsys/`，避免与 worktree 自带的副本双写。
- `devsys worktree prepare --run <run-id>` 在写 run 记录时同时记 `claim_head`——这是 `devsys run verify` 的对照点；任何中间分支切换都会让 verify 拒绝。

## 关键边界：读 vs 写

`internal/config` 同时提供两个读取入口，行为差异是本模块契约的核心：

| 入口 | 用途 | 缺文件视为错误？ | 未知 schema_version 行为 |
|---|---|---|---|
| `config.Load(root)` | 写命令前置校验（`init` 入口处先调用；M2 起 `workitem create` 也先调用；M4 起所有 `app.Xxx` 调用前；**M6** 起 `dispatch / run exec / worktree prepare / workspace create` 等也先调用） | 否（缺失文件留待 init 创建） | 报 `Problems`，写命令拒绝并返回退出码 4 |
| `config.Diagnose(root)` | 只读诊断（`config check`） | 是 | 报 `Problems`，命令返回退出码 4 但仍然返回解析结果 |

二者共用同一份 `load(root, reportMissing bool)` 内部函数（[`internal/config/config.go:106-140`](../../../internal/config/config.go#L106-L140)）；选择哪个取决于调用点是否能容忍缺失文件。**写命令从不重新实现校验**，只复用 `config.Load`。

M1 起，`config.Load` 对 `project.yaml` 通过 `domain.DecodeYAML` 解析为 `*domain.Project`（[`internal/config/config.go:142-152`](../../../internal/config/config.go#L142-L152)）；任何未在该包 `projectSpec` 白名单内出现的字段都会被拒绝。

M2 在 `config.Load` 之外引入两类**只读检查**入口，由 `internal/reconcile` 通过 `storage.Inspect` 暴露，**不**经过 `config.Load`：

- `doctor`：通过 `storage.Diagnose` + `storage.Inspect` 列举待处理事务与 `scheduling/` 下的租约；待处理事务存在时 `Orphans` 留空并附恢复提示（[`internal/reconcile/reconcile.go:142-208`](../../../internal/reconcile/reconcile.go#L142-L208)）。
- `repair --dry-run`：基于只读扫描生成 `Plan{Proposals, Digest}`，`Digest` 不含墙钟时间以保证可重复（[`internal/reconcile/reconcile.go:282-304`](../../../internal/reconcile/reconcile.go#L282-L304)）。

M3 又引入三条只读入口：

- `workflow check`：`workflow.Load(root)` 直接解析每份策略文件，输出 issues；不走 `config.Load`、不持锁、不写盘。
- `workflow next`：通过 `workflow.Resolve(ctx, root, id)` 取当前或 LKG 策略，列出候选；与 `storage.Write` 的写入路径隔离。
- `next`：`reconcile.Doctor` + `internal/next.Evaluate` 的组合命令，不创建锁、不触发恢复、不可信状态不输出业务事实。

M4 进一步把「只读上下文」收口到 `internal/app.context.go`：

- `context get|workitem|refresh|compact`：走 `reconcile.Doctor` + `next.Evaluate` + `record.*ListArtifacts / ListDecisions / ListFindings` + `events.Comments` 聚合。
- `session start`：在 `context get` 之上挑选「唯一推荐动作」并给出 `Notices`。
- `knowledge status`：M4 永远返回 `unavailable`（M5 §12.6 达到）。

M6 进一步把**只读执行层诊断**收口到 `internal/app.dispatch.go`：

- `dispatch --dry-run`：调 `Plan(in)` 一次，不 recover、不 claim、不 spawn；输出 `Report{Decisions, Started, Notices}`。
- `run verify`：只读比较 `claim_head` / `current_head`，**不**写任何状态。
- `run prompt --write`：写 `.devsys/local/runs/<id>/round-<N>.md`（.gitignore 保护区域），不写 `.devsys/runs/<id>.jsonl`。

这十二类路径**不**创建项目锁文件、**不**触发事务恢复，与写路径刻意分开。
