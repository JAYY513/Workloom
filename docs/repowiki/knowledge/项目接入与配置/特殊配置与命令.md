# 特殊配置与命令 · 项目接入与配置

## `devsys init`

唯一允许修改受管文件的写命令。它把 `.devsys/` 布局落到 Git 仓库根目录、写入 4 份占位元数据、注册项目路径到用户级注册表，并保证 `.devsys/.gitignore` 至少覆盖 `local/` 与 `.cache/`。子目录不是仓库根时会拒绝执行。

```sh
cd /path/to/your/git-repo
devsys --json init
devsys --quiet init
devsys config check
```

文本模式报告初始化目录、项目名称与 ID、实际创建的路径数量及注册表路径；数量取决于已有布局。JSON 模式返回实际创建路径与登记结果。

幂等行为：

- 缺失的 `.devsys/`、子目录和占位文件会被补建；现存占位元数据不重写。
- `.devsys/.gitignore` 若已存在，只追加缺失的 `local/`、`.cache/` 行，原有内容不变。
- 落盘前先校验现有受管元数据；若已存在的 `project.yaml` / `config.yaml` / `state/*.yaml` 出现未知 `schema_version`、未知键或类型错误，`init` 拒绝改动并报退出码 4。
- 当前目录不在 Git 仓库或 `git` 不可用 → 退出码 3（前置条件），无任何写入。

## `devsys config check`

只读诊断：不加锁、不写盘、不恢复事务。遍历四份受管元数据文件，逐条定位问题，按 `文件:行号: 字段: 原因` 格式化输出。

```sh
devsys config check             # 通过：config ok: 4 files checked
devsys --json config check      # {ok,root,checked,project?,config?}
devsys config check; echo $?    # 0 / 4 / 3
```

四份受管文件（顺序固定）：`project.yaml`、`config.yaml`、`state/current.yaml`、`state/milestones.yaml`。问题示例：

```text
project.yaml:5: unknown_field: unknown key
project.yaml:2: schema_version: unsupported version 99 (...)
config.yaml:2: timeout: unknown key
```

`--json` 模式下问题进入 `error.problems` 数组（`code=4`、`kind=invalid`）；通过时返回完整 `project`、`config` 解析结果。`init` 之前的项目目录 → 退出码 3。

## `devsys search <keyword>`

`.devsys/` 下无索引文本扫描：大小写不敏感子串匹配，单文件最多 5 条命中行，行内容截断 200 字节（UTF-8 安全），排除 `.cache/` 与 `local/`。缺少关键字参数或多于一个位置参数 → 退出码 2。

```sh
devsys search 密码
devsys --json search WLM-2
devsys search no-such-keyword; echo $?   # 0（零命中仍成功）
```

文本输出：`<相对路径>:<行号>: <行内容>`，末尾汇总 `<N> match(es) in .devsys/ for "<keyword>"`。

`--json` 字段：`ok`、`root`、`query`、`matches[]`（`path`、`line`、`text`）、`total`。零命中时 `matches` 是空数组、`total=0`，退出码仍为 0。

## M2 工作项与对账命令

`workitem` 读写工作项状态，`doctor` / `recover` / `repair` 负责对账与修复。写命令都要求 `--actor` 与 `--reason`（写入审计事件）；状态转换与领取用 `--expect <64-hex version>` 提交你读到的版本（`workitem get` 输出），旧快照会被拒绝。**P2 起** `--expect` 与 `--latest` 互斥：`--latest` 是「同一事务里先读最新快照再 CAS」的便捷形态，仍是 CAS——只是把 `get` 那一步封装进命令本身（[internal/cli/cli.go:525-539](file://internal/cli/cli.go#L525-L539) `latestFlag` / `checkLatest`）。
```sh
bin/devsys.exe workitem get WLM-1                                   # 打印字段与 version: <64-hex>
bin/devsys.exe workitem create --title 任务标题 --actor me --reason 建任务 \
    [--description D] [--acceptance "验收点 1,验收点 2"]              # d726ed4: --acceptance 可在 create 直接给验收标准
bin/devsys.exe workitem transition --id WLM-1 --to ready --actor me --reason 拆分完成 [--expect <hash> | --latest]
bin/devsys.exe workitem claim --id WLM-1 --owner me --reason 开工 [--expect <hash> | --latest]
    # b89ffae: claim 与 next 用同一份质量门；未绑定 Workflow 且项目里没有策略文件时打印 warning: gates are not enforced；
    # 工作项绑定的 Workflow 或 .devsys/config.yaml: default_policy 任一参与判定；两者都没有时 claim 不拦。
bin/devsys.exe doctor                                               # 只读：过期/孤儿领取、待恢复事务、修复提议
bin/devsys.exe recover --actor me --reason 恢复中断的领取
bin/devsys.exe repair --dry-run --actor me --reason 盘点             # 打印提议表与 digest
bin/devsys.exe repair --apply --confirm <digest> --actor me --reason 确认修复
```

- 非法状态转换（如 `draft → in_progress`）→ 退出码 4，stderr 列出允许的下一步。
- 版本哈希不匹配（旧视图）→ 退出码 4，重新 `workitem get` 后再试。
- **d726ed4** workitem id 形状非法（含换行 / 路径穿越 / 多行）→ `CodeUsage = 2` + `invalid workitem id <id>`，绝不泄漏「unsafe managed path」（[internal/app/workitem.go:447-484](file://internal/app/workitem.go#L447-L484) `storeError` 路径）。
- **d726ed4** 租约内 `transition` 被 fencing 拒绝时 stderr 直接给 `devsys workitem release --id <id> --owner <o> --token <t> --actor <a> --reason <r>` 出路。
- **c150007** 写命令撞上 `storage: version conflict`（如 `run fail` 时 dispatch 子进程正在写同一 run）→ `CodeInvalid = 4` + 出路：重新读取后重试，或改用 `--latest` 直接基于当前版本写入。
- **b89ffae** `claim` 在 `config.yaml: default_policy` 缺失或 `config.yaml` 非法时 → `CodeInvalid = 4` + `config.yaml is invalid: <problem>; run \`devsys config check\``（fail-closed）。
- `doctor` 是只读对账：不创建锁文件、不触发事务恢复；有待恢复事务时只报告事务、不输出业务事实。
- `recover` 先做确定性事务恢复，再释放过期/孤儿领取（每次释放写 `lease_recovered` 事件）；重复执行不产生重复事件。
- `repair --apply` 需要与当前状态一致的 `--confirm` 摘要；摘要不符或证据漂移 → 退出码 3，不写任何文件。

## M3 工作流命令

```sh
bin/devsys.exe workflow check                                                       # 校验 .devsys/workflows/*.md
bin/devsys.exe workflow start --id WLM-1 --policy quick-fix --actor me --reason begin --expect <hash>
bin/devsys.exe workflow next --id WLM-1                                             # 列出候选与首满足推荐
bin/devsys.exe workflow step-complete --id WLM-1 [--to implement] --actor me --reason go --expect <hash>
bin/devsys.exe workflow pause --id WLM-1 --actor me --reason hold --expect <hash>
bin/devsys.exe workflow resume --id WLM-1 --actor me --reason go --expect <hash>
bin/devsys.exe workflow cancel --id WLM-1 --actor me --reason abort --expect <hash>
```

- 所有实例操作强制 `--actor` / `--reason` / `--expect`；租约活跃时强制 `--owner` / `--token`（与 `workitem claim` / `updateclaimed` 同 fencing 契约）。
- `workflow start` 强制 `--policy`；坏策略（无 LKG）→ exit 4。
- `workflow next` 在 paused 时仍展示候选，但不输出 `next:` 推荐（M3Reviewer5 ⑤）。
- `workflow step-complete --to nope`（未声明目标 / 条件不满足 / 目标 = 当前步骤）→ exit 4，stderr 列出 `allowed next steps`（含 `when` 与 `satisfied`）。
- `workflow check` 缺 `id` / `version` 非法 / `steps[].id` 重复 / `transitions[].from` 未知 / `gates.stages.<status>` 状态非法 → exit 4 + `file[:line][: field]: reason`；未知键 warning 仍 exit 0。
- 实例操作**不**改工作项状态、不动 `scheduling/` 目录；`paused` 实例拒绝推进（exit 4 + `paused`）。

## M3 审批命令
- `approve` / `reject` 在已 `invalidated` / 已非 `pending` 时 exit 4。
- **d726ed4** `approval list` / `approval get` 第二列展示**有效状态**（`approvalState(apr)`，[internal/cli/cli.go:1396-1407](file://internal/cli/cli.go#L1396-L1407)）：已 `consumed_at` 的显示 `consumed`，已 `invalidated_at` 的显示 `invalidated`（原始 `apr.Status` 字段不变；`--json` 模式仍带 `consumed_at` / `invalidated_at` 字段）。脚本应优先按这一列分支。
- **b89ffae** 阶段门 `require_approval` 未满足时若审批已被 `invalidated`（方案 §4.9——离开 requested_status 即作废），`gateEvidence` 把信息写进 `workflow.GateEvidence.ApprovalNote`（[internal/app/workitem.go:556-610](file://internal/app/workitem.go#L556-L610)）：错误形如 `<approval-N> was invalidated at <t> when the work item left "<status>" (方案 §4.9); request a new approval with \`devsys approval request\``。
```sh
bin/devsys.exe approval list [--workitem <id>] [--status pending|approved|rejected]
bin/devsys.exe approval request --id <wi> --stage <stage> [--scope stage_gate|action] [--run <run>] --actor <a> --reason <r>
bin/devsys.exe approval approve --id approval-<n> --by <decider> [--comment <c>]
bin/devsys.exe approval reject --id approval-<n> --by <decider> --reason <r>
```

- `request` 同 (work item, stage, requested status) 重复申请 → exit 4；`--scope action` 不能带 `--stage`。
- `request` 在声明的 `gates.stages.<stage>.require_approval = false` 或未声明时打印 `warning: policy %q declares no require_approval gate for stage %q; nothing will consume this approval`。

- `reject --scope stage_gate` 通过 `rejectStageGate` 在转换事务的 Guard 内同时完成 `approval_rejected` 与工作项 `blocked`（或 `regress:<status>` 回退）；失败整单回滚，审批保持 pending，错误说明 `nothing was changed`。
- `consume` **不**暴露为 CLI 子命令——只有 `workitem transition` 的 Guard 内消费（M3.7 决策）。

## M6 工作区与执行命令

### `devsys worktree`

工作区生命周期（M6 新增）：

```sh
# 创建（idempotent：存在即复用，不重跑 after_create）
bin/devsys.exe worktree prepare --workitem WLM-1 \
    --actor me --reason "start dispatch" [--run run-id] [--branch devsys/my-key]

# 列出（read-only）
bin/devsys.exe worktree list [--workitem WLM-1]

# 删除（before_remove 失败仅记录）
bin/devsys.exe worktree remove --workitem WLM-1 --actor me --reason cleanup [--force]
bin/devsys.exe worktree remove --path /abs/path --actor me --reason cleanup [--force]
```

- `prepare` 把 worktree 路径写到 run 记录（在 `--run` 给出时），并把当前分支 head 记为 `claim_head`——这是 `run verify` 的对照点。
- `remove --path` 强制走 `internal/workspace.Validate(root, path)`——越界路径 exit 3（`smoke-m6` 第一段 PASS）。
- `--force` 用于丢弃工作区本地修改（git worktree `remove --force`）。

### `devsys dispatch`

一次调度 tick（M6 新增，§4.8）：

```sh
# 一次性 tick（默认）
bin/devsys.exe dispatch --once --actor ops --reason tick

# 循环（Ctrl-C 退出 0）
bin/devsys.exe dispatch --watch --interval 30s --actor ops --reason tick

# 预览：不 recover / 不 claim / 不启动；只打印 plan
bin/devsys.exe dispatch --dry-run --actor ops --reason preview

# 限制本 tick 启动数
bin/devsys.exe dispatch --once --max 2 --actor ops --reason tick
```

- tick 顺序：recover（事务恢复）→ sweep（失败/超时/停滞 attempt 收尾）→ plan → claim → prepare workspace → spawn → mark running。
- 每步都有 notice 写入；一次 broken candidate 不阻塞队列。
- `--dry-run` 必须**不**创建任何 `.devsys/runs/*.yaml`（`smoke-m6` 第 2 段 PASS）。

### `devsys run exec|prompt|verify|complete|fail|cancel`

驱动与收尾 attempt（M6 新增）：

```sh
# 任意命令（Shell 适配器）
bin/devsys.exe run exec --id run-... --actor me --reason "smoke test" -- -- sh -c "echo hi"

# Harness 适配器（assigned harness）
bin/devsys.exe run exec --id run-... --harness codex --model gpt-5 \
    --actor ops --reason "acceptance" --timeout 120s

# 提示词预览（不发起 attempt）
bin/devsys.exe run prompt --id run-... [--round N] [--write]

# 完成校验（只读）
bin/devsys.exe run verify --id run-...
# advanced | not advanced [+ reason]

# 终态
bin/devsys.exe run complete --id run-... --actor me --reason "acceptance" \
    [--expect <hash>] [--note "evidence"] [--force --by reviewer]

bin/devsys.exe run fail --id run-... --actor me --reason "tests failed" \
    [--expect <hash>] [--note "exit 9"]

bin/devsys.exe run cancel --id run-... --actor me --reason "stop" \
    [--expect <hash>]
```

- `--harness ∈ {shell, codex, opencode, claude}`：未声明时按 shell 跑 `--` 后的命令；声明后 `Request.Harness` / `Request.Model` 进入适配器，shell 路径被拒绝。
- `--timeout` 终止**整棵进程树**（POSIX 进程组 / Windows Job）。
- `run prompt --write` 落 `.devsys/local/runs/<id>/round-<N>.md`（不提交、可重建）。
- `run verify` 只读不写；advanced/not advanced 经 stdout 行反馈。
- `run complete` 默认走 verify 守卫：未 advance → exit 4 + run 进 `failed` + workitem 进 `review`（`smoke-m6` 第 4 段 PASS）；`--force --by reviewer` 接受 verify 拒绝。
- `run fail` / `run cancel` 不走 verify；写终态 + reason/note。
