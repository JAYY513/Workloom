# 编码规范

本模块聚焦**接入与配置**特有的编码约束；通用 Go 风格由 `gofmt -l cmd internal` 兜底（[README:53-56](../../../README.md#L53-L56)）。

## 1. 错误分类优先于错误消息

**约定**：所有从底层上报的错误必须经过 `codedError` 重新分类，由 `render` 决定怎么渲染、由退出码决定怎么分支。

**验证**：

- `errUsage` / `errPrecondition` / `errInvalid` / `errInternal` 四种构造器（[`internal/cli/cli.go:75-98`](../../../internal/cli/cli.go#L75-L98)）保证新代码不会绕过 4 个已知类别。
- `render` 在遇到非 `codedError` 时自动升级为 `CodeInternal`（[`internal/cli/cli.go:148-151`](../../../internal/cli/cli.go#L148-L151)），但调用方应主动分类以保留类别信息。

**反模式**：在命令实现里 `fmt.Fprintln(stderr, ...)` 直接打错误——这会让 `--json` 输出丢结构化问题，且退出码始终是 1。

## 2. 错误信息结构化，问题携带位置

**约定**：每个用户可修复的缺陷必须能被定位到具体文件、行列与字段。

**验证**：

- `config.Problem{File, Line, Field, Reason}`（[`internal/config/config.go:45-50`](../../../internal/config/config.go#L45-L50)）是结构化输出与文本渲染的唯一来源。
- `Problem.String()` 渲染为 `file[:line][: field]: reason`（[`internal/config/config.go:52-66`](../../../internal/config/config.go#L52-L66)），与测试期望严格一致（[`internal/cli/cli_test.go:218-226`](../../../internal/cli/cli_test.go#L218-L226)）。
- `Problems` 自身实现 `error`，便于 `errors.As` 在 cli 层取出。

**反模式**：在配置校验里返回 `fmt.Errorf("bad yaml")`——丢失行号与字段名，调用方无法定位。

## 3. 写命令在动盘前必须先 `config.Load`

**约定**：任何会修改 `.devsys/` 的命令在执行写入前都要调用 `config.Load(root)`。存在 `Problems` 即拒绝，并把 `Problems` 透传给 `errInvalid`。

**验证**：

- `project.Init` 在 `gitRoot`/`requireSameDir` 通过后立即调用 `config.Load`（[`internal/project/init.go:66-69`](../../../internal/project/init.go#L66-L69)）。
- 回归测试 `TestInitRefusesUnknownSchemaVersion`（[`internal/cli/cli_test.go:292-341`](../../../internal/cli/cli_test.go#L292-L341)）：把 `schema_version: 1` 改为 `99`，再跑 `init` 必须得到 `CodeInvalid` 且不修改磁盘；`config check` 在同状态下仍能跑出诊断。

**反模式**：写命令自己重新解析受管文件——容易出现两份规则、规则漂移。

## 4. 命令实现只关心业务，`render` 关心呈现

**约定**：命令函数（`runInit` / `runConfigCheck`）只返回 `error` 或写完 stdout 后返回 `nil`。渲染（人/机两态、错误位置列表展示、退出码）全部交给 `render`。

**验证**：

- `runInit` 在 `opts.json` 时返回 `json.NewEncoder(stdout).Encode(out)` 错误；否则用 `fmt.Fprintf(stdout, ...)` 写人读输出（[`internal/cli/cli.go:209-243`](../../../internal/cli/cli.go#L209-L243)）。
- `runConfigCheck` 同样分支，但 `--json` 时 `ok` 载荷里多了 `project` 与 `config` 两段解析结果（[`internal/cli/cli.go:275-290`](../../../internal/cli/cli.go#L275-L290)）。

**反模式**：在命令里 `fmt.Fprintln(stderr, "error:", err)`——丢失 `CodeInvalid`/问题列表。

## 5. 稳定序列化：相同输入产生相同字节

**约定**：受管 YAML 文件的字段顺序是 struct 字段顺序；`storage.EncodeYAML` 保证键序稳定；`storage.AtomicWrite` 保证读者永远看到完整文件。

**验证**：

- 占位 YAML 的 Go struct 字段顺序（[`internal/project/tree.go:55-77`](../../../internal/project/tree.go#L55-L77)）即落盘顺序，且与 `config` 包的白名单字段顺序（[`internal/config/validate.go:37-51`](../../../internal/config/validate.go#L37-L51)）一一对应——这两份顺序**必须**同步演进，否则 init 写出的文件会被 `config check` 自己拒绝。
- `registry.Save` 在写入前对 `Projects` 按 `normKey` 排序（[`internal/registry/registry.go:123-126`](../../../internal/registry/registry.go#L123-L126)），保证多次 `init` 在不同顺序下产生的注册表字节相同，便于 diff。

**反模式**：`map[string]any` 编码 YAML——`gopkg.in/yaml.v3` 对 map 的键序不保证，相同输入可能产出不同字节，破坏幂等。

## 6. 出口位置守恒：受管文件永远在仓库根

**约定**：`devsys init` 拒绝在子目录运行；CWD 必须与 `git rev-parse --show-toplevel` 同一目录。

**验证**：

- `requireSameDir` 用 `os.SameFile` 比较 inode（[`internal/project/init.go:146-159`](../../../internal/project/init.go#L146-L159)），不依赖字符串比较。
- 触发时返回 `PreconditionError`，cli 把它升级为 `CodePrecondition`（退出码 3）。

**反模式**：在子目录运行 init 时“自动向上找 .git”——会让人困惑 `.devsys/` 落在哪里，且与 [方案 §14.3] “状态目录永远在仓库根”的约束冲突。
