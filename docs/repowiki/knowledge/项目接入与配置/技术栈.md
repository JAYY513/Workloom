# 技术栈

本模块全部代码都是 Go（接入层无 JS/TS）。下面只列出**接入与配置相关**的有意选型与默认设定；纯标准库用法不再赘述。

## 语言与运行时

| 项 | 值 | 来源 |
|---|---|---|
| Go | 1.26 | [`go.mod:3`](../../../go.mod#L3) |
| 模块路径 | `workloom` | [`go.mod:1`](../../../go.mod#L1) |

Go 1.26 的选用与后续 TypeScript/React 工作区视图**互不干扰**：接入层在编译时即把领域数据固化为可读文本，不暴露运行时给前端。

## 依赖

| 依赖 | 形态 | 用途 |
|---|---|---|
| `gopkg.in/yaml.v3` v3.0.1 | `vendor/` 提交，离线可用 | `config` 解析 + `project`/`registry` 序列化 + `domain.EncodeYAML` / `DecodeYAML` |
| 标准库 | `os/exec` 调 `git`、`io/fs` 错误判定、`path/filepath` 跨平台路径、`encoding/json`（`DisallowUnknownFields`） | 仓库根解析、错误分类、跨平台路径处理、严格 JSON 解码 |

唯一三方依赖被 `go mod vendor` 固化（[`go.sum` 已提交](../../../go.sum)），干净机器无需网络。`vendor/` 目录提交进仓库后，即便离线也能完整构建与运行测试：

```sh
GOFLAGS=-mod=vendor GOPROXY=off go build ./...
GOFLAGS=-mod=vendor GOPROXY=off go test ./...
```

新依赖若必要，需 `GOPROXY=https://goproxy.cn go get <module>`（[README:84-87](../../../README.md#L84-L87) 记录了代理选择理由），随后 `go mod tidy && go mod vendor` 一并提交。

## 构建标识

`internal/version` 提供两个 `-ldflags` 入口：

| 变量 | 默认值 | 覆盖示例 |
|---|---|---|
| `Version` | `0.1.0-dev`（[version.go:13](../../../internal/version/version.go#L13)） | `-X workloom/internal/version.Version=0.1.0` |
| `Commit` | `unknown`（[version.go:16](../../../internal/version/version.go#L16)） | `-X workloom/internal/version.Commit=$(git rev-parse --short HEAD)` |

发布构建命令（[README:60-62](../../../README.md#L60-L62)）：

```sh
go build -ldflags "-X workloom/internal/version.Version=0.1.0 \
                 -X workloom/internal/version.Commit=$(git rev-parse --short HEAD)" \
         -o bin/devsys.exe ./cmd/devsys
```

未传 `-ldflags` 的本地构建保留 `0.1.0-dev` 标识，避免误当正式发布。

## 错误判定：仅靠错误类型与哨兵

接入层不依赖任何错误码字符串或正则匹配；全部靠 `errors.As` + 哨兵：

| 错误来源 | 哨兵 / 类型 | 触发点 |
|---|---|---|
| 项目侧环境错误 | `*project.PreconditionError`（[`internal/project/init.go:23-25`](../../../internal/project/init.go#L23-L25)） | 非 git 仓库、git 不在 PATH、CWD 不是仓库根 |
| 配置侧解析问题 | `config.Problems`（实现 `error`，[`internal/config/config.go:71-79`](../../../internal/config/config.go#L71-L79)） | 写命令前置校验、`config check` 报告 |
| 文件系统错误 | `fs.ErrNotExist` | `init` 判断 `.devsys/` 是否已存在；`config check` / `search` 判断项目是否初始化 |
| 领域层解码错误 | `storage.CheckSchemaVersion` 返回的 `error` | `domain.EncodeYAML` / `DecodeYAML` 末尾 |

## JSON 解码：严格模式

`internal/domain.DecodeJSON` 在解码所有受管领域记录时启用 `DisallowUnknownFields`（[internal/domain/serialize.go:96](../../../internal/domain/serialize.go#L96)），未知 JSON 字段会被立即拒绝。这一约束与 YAML 端的 `projectSpec` 严格校验对称，保证 JSON 与 YAML 路径都不会把“未声明字段”静默落盘。

## 平台差异

接入层显式处理的平台差异只有两处，且**都是判断而不是分支**：

1. **路径大小写**：`registry.samePath` 在 `runtime.GOOS == "windows"` 时使用 `strings.EqualFold`（[`internal/registry/registry.go:148-154`](../../../internal/registry/registry.go#L148-L154)），保证 Windows 上同一项目的不同大小写路径只占一条注册条目。
2. **路径分隔**：`filepath.FromSlash` / `filepath.ToSlash` 在 `internal/project` 与 `internal/registry` 之间传递路径时统一规范化，使报告里的 slash 路径能在 Windows 上正确还原。

其余平台差异（文件锁、目录锁）下沉到 `internal/storage` 的 `fsync_windows.go` / `lock_windows.go` 与 `_unix.go` 对应文件，接入层不感知。

## vendor 模式与离线构建

`vendor/` 已提交（`gopkg.in/yaml.v3` 整个包），无需任何模块代理即可构建与测试。本仓库约定：

| 命令 | 是否要求网络 | 备注 |
|---|---|---|
| `GOFLAGS=-mod=vendor go build ./...` | 否 | 使用 vendor 内置源码；CI 与本地均可 |
| `GOFLAGS=-mod=vendor go test ./...` | 否 | 测试同样走 vendor |
| `gofmt -l cmd internal` | 否 | 静态格式检查 |
| `go vet ./...` | 否 | 静态分析 |

新增依赖时必须 `go mod vendor` 同步 `vendor/modules.txt`，否则 vendor 构建会失败。

## 未选型的备选（有意排除）

- **JSON Schema / OpenAPI 校验库**：M0.4 自己写 `validate.go` 的白名单，理由是受管文件只有四份且字段数固定，不需要引入额外 schema 运行时。
- **结构化日志库（如 zap/zerolog）**：当前命令栈没有日志需求；命令的错误渲染走 stderr 文本 + `--json`，不必引入专用日志通道。
- **配置库（如 viper）**：本项目的配置是**用户手写并可被拒绝**的，不是运行时动态读取；自写白名单能给出明确的 `文件:行号` 定位。
- **CLI 框架（cobra/urfave/cli）**：当前只有 3 个顶层命令，自写 `Run` 足以承载开关解析与退出码契约，引入框架会增加表面且让退出码契约变得不透明。
