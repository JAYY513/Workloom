CLI 层在 M4 后只做三件事：

1. 解析全局开关（`--json` / `--jsonl` / `--quiet`）与位置参数；
2. 按顶层命令 + 子命令分发给对应的 `runXxx` 函数；
3. 调 `svc := appService()` → `svc.Xxx(...)` → `render` 把结果或错误按人/机两种格式写到 stdout/stderr，把退出码交给操作系统。

CLI 不再直接依赖 `internal/{workitem,approval,workflow,...}` 业务包；它们都通过 `internal/app` 这一个入口被消费。MCP 服务同样通过 `internal/app` 暴露工具；`internal/mcp` 不引入新的锁或新的存储后端。

## 错误传递链

M4 起所有业务错误走 `*app.Error`：

```
storage.ErrXxx / domain.TransitionError / workflow.Issue / approval.ErrXxx / record.ErrSuperseded
   ↓
internal/app 包：app.Usagef / Preconditionf / Internalf / Invalidf → *app.Error{Kind, Message, Problems}
   ↓
CLI:    toCoded(err) → *codedError{code, kind, msg, problems}     [internal/cli/cli.go:99-117]
MCP:    fail(err)    → toolError{Code, Message, Problems, Notice} → isError=true tool result
   ↓
render (CLI) / structuredContent (MCP) 决定人/机两种输出
   ↓
stderr JSON: {ok:false, error:{code, kind, message, problems?}}    --json
```

CLI 与 MCP 共用同一份 `app.Error.Class()` → 退出码 / 工具错误码的翻译。调用脚本应当只信 `code` 字段做分支，不要解析 `message`。

`codedError` 的 JSON 形式（`--json` 模式）：

```json
{
  "ok": false,
  "error": {
    "code": 4,
    "kind": "invalid",
    "message": "workflow step \"implement\" refused: no transition condition is satisfied",
    "problems": null
  }
}
```

调用脚本应当只信 `code` 字段做分支，不要解析 `message`。

## 渲染层

[internal/cli/cli.go:178-198](file://internal/cli/cli.go#L178-L198) `render` 决定输出形态：

- `--json`：成功 / 错误信封都走单行 JSON（成功 stdout，错误 stderr）。
- 非 `--json`：成功用人类可读文本（受 `--quiet` 控制），错误走 stderr。

`--quiet` 仅抑制成功输出，错误与 warning 仍然写 stderr——这是 `doctor` / `repair --dry-run` / `workflow check` 等诊断命令可见性约束。

## M3 命令族详解

### `devsys workflow`

`runWorkflowCheck`（[internal/cli/cli.go:388-452](file://internal/cli/cli.go#L388-L452)）：

- `workflow.Load(cwd)` 解析所有 `.devsys/workflows/*.md`。
- `error-severity` issue 升为 `config.Problem` 并通过 `errInvalid(problems)` → exit 4。
- `warning-severity` issue 走 `warning:` 行打印，`--quiet` 仍保留。
- `--json` 输出 `{ok, root, policies[], warnings[]}`。

`runWorkflowStart` / `WorkflowNext` / `WorkflowStepComplete` / `WorkflowSignal`（pause/resume/cancel）通过 `workflowPolicy(ctx, root, wi, policyID, requirePolicy)` 取当前或 LKG 策略，要求 `policy != nil`（start 时要求，next/step-complete 时允许 LKG fallback），然后调 `items.WorkflowStart/Next/StepComplete/Signal`。所有实例操作都强制 `--actor` / `--reason` / `--expect`；租约活跃时强制 `--owner` / `--token`。

### `devsys approval`

`runApprovalList` / `runApprovalRequest` / `runApprovalDecide`（approve / reject）：

- `Request` 调 `approval.New(root).Request(ctx, opts)`，含重复请求检查（`findOpenApproval`）。
- `Approve` 走独立事务 `Decide(ctx, id, opts{Approve: true})`。
- `Reject` 区分 scope：`scope=stage_gate` 走 `rejectStageGate`（在 `workitem.Transition` 的 Guard 内同时完成 `DecideTx(rejected)` 与状态变更）；`scope=action` 走独立事务 `Decide(ctx, id, opts{Approve: false})`。

`rejectStageGate`（[internal/cli/cli.go:942-976](file://internal/cli/cli.go#L942-L976)）：

1. 调 `workitem.ReadSnapshot` 取工作项当前字节作为 `--expect`。
2. 按策略 `on_reject` 决定目标状态（默认 `blocked`，`regress:<status>` 回退）。
3. 构造 `TransitionRequest{TargetStatus: target, Guard: <DecisionTx closure>}`。
4. `items.Transition(ctx, wi.ID, req, raw)`：Guard 内 `DecideTx(rejected)` 失败 → 整单回滚，工作项不动，审批保持 pending。

`runWire`（[internal/cli/cli.go:371-408](../../../internal/cli/cli.go#L371-L408)）→ `app.Wire(dryRun bool)`（[internal/app/wire.go:44-77](../../../internal/app/wire.go#L44-L77)）：把 devsys 纪律块以 `<!-- devsys:begin/end -->` 注入 `AGENTS.md`；幂等（三次运行字节一致）；区段外字节保留（含其它工具的管理块）；`--dry-run` 预览 diff。

### `devsys mcp serve`（M4）

`runMCPServe`（[internal/cli/mcp.go:48-84](../../../internal/cli/mcp.go#L48-L84)）：

1. 解析 `--profile`（默认 `session,executor`，未知名字报错）。
2. `requireProjectRoot()` 验证 `.devsys/`。
3. `mcp.Config{Root, Profiles, ServerVersion, Instructions, Log=stderr}` → `mcp.Run(ctx, cfg, nopReadCloser{stdin}, nopWriteCloser{stdout})`。
4. `nopReadCloser` / `nopWriteCloser` 防止 SDK 关闭进程流。

`Instructions` 字段由 CLI 在 `mcpInstructions` 常量中固定——和 `app.Wire` 的纪律块描述一致；agent 的纪律文本由 `devsys wire` 显式注入 `AGENTS.md`，不在 SDK `initialize` 自动推送。



`runNext`（[internal/cli/cli.go:1323-1437](file://internal/cli/cli.go#L1323-L1437)）：

1. `reconcile.Doctor` 收集待恢复事务 + 过期/孤儿/不可读租约 + `InspectionOK`。
2. 仅在 `InspectionOK && len(pending) == 0` 时列举 `workitems` 与 `pending approvals`（不可信状态不输出业务事实，§15.4）。
3. `config.Diagnose` 收集元数据问题；`workflow.Load` 收集策略问题与「工作项引用缺失策略」交叉核对。
4. `next.Evaluate(in)` 输出 `Report{Verdict, Reasons, Risks, Fixes, Next}`。
5. exit 恒 0；`--json` 输出完整结构。
